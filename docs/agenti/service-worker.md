# Service worker (`mzlab/web/sw.js`)

Browser only: the desktop app serves `mzlab://` and never downloads `sw.js`.

- **App cache** `mzlab-app-<hash>`: the name carries the hash of the published site. `seal_sw` in `tools/build_site.py` writes `static/sw-manifest.json` (`app`, `files`: path -> SHA-256, `nofill`) and puts `app` in `const APPV` of `sw.js`; it runs at the end of `build_site.py` and again with `--build-json` (`.wasm` and packages already in place), so a change in any file is a new cache. The desktop manifest (`manifest.json`) does not contain `sw-manifest.json`.
- **App files: cache first.** A file in the cache is by construction the right version and is not revalidated. A miss goes to the network (first the HTTP cache, then `no-cache` if the SHA-256 is not the manifest's) and is saved ONLY if the SHA-256 matches; the page receives the checked body at once and the save follows in `waitUntil` (with a cold cache ~30 misses before the first paint do not wait for the cache writes; `sw_cache_node.mjs`). Never cached: `api/`, `static/librerie/`, `manifest.json`, `build.json`, `sw-manifest.json`, files outside the manifest.
- **Pages (navigations): network first** (default), 3 s timeout and then the cached copy; at every navigation the manifest is requested again. If it describes another version (different `app`) the worker is "stale": from its cache it serves only the files whose SHA-256 is the one in the new manifest (a deploy changes few files; never a mixed JS/wasm pair), the rest from the network, it saves nothing and asks for `registration.update()`; the new worker (`skipWaiting` + `clients.claim`) replaces it.
  The page comes from the *navigation preload* (`activate` turns it on), requested by the browser together with the manifest and not after it, and is checked against the manifest SHA-256 as in `traer` (otherwise `traer` with `no-cache`; a "stale" worker checks it against the SHA-256 of the new version and does not save it).
- **`?nav=cache` (optional, `measurements-navigation.md`)**: a navigation checked with `?nav=cache` turns it on and the worker remembers it (cache `mzlab-opz`, entry `.nav-cache`; `?nav=network` turns it off, "Start from scratch" deletes it), with a line in the worker console; the preload is turned off. If the cache of this version is complete (`.fill-done`, so every file except `nofill`), the page comes straight from the cache and the manifest is checked in the background.
  The worker does not become "stale" (`fijo`: its pages belong to its version, no file from two versions) and asks for `registration.update()`.
  The new worker, with one already active, fills its whole cache in `install` (without `skipWaiting`; an incomplete fill makes the install fail, the next check retries), leaves the old caches, sends `sw-nuova` to the pages and waits.
  The page shows a `role=status` line "New version ready" with "Reload" (`sw-avviso.js`, loaded only on the message). On the next load, the old worker sees `registration.waiting`, sends it `sw-attiva` (`skipWaiting`) and takes the page from the network: the new version arrives one load later. The new one, now active, deletes the old caches. Incomplete cache: network first as always. The first install does not wait.
  The `nofill` files (`static/esempi/`) are not in the cache: with a deploy on the network the old worker takes them from the network without a check, so "never two versions" holds for the code and not for these example files.
- **Restarted worker**: the browser stops an idle worker and restarts it with `stale` forgotten; until that run of the worker has requested the manifest (`visto`), the first request for a file requests it before answering from the cache (at most 3 s, like a page: on a blocked network the cache then answers), so a page of the new version does not receive a file of the old one.
  With `?nav=cache` and a complete cache it does not wait: page and files belong to the same version. A "stale" worker holds no event open (`waitUntil` of the fill): the new one activates only when the old one has none.
- **Previous caches**: `activate` leaves the earlier `mzlab-app-*`; the new worker copies from them the files with the same SHA-256 (`heredado`) instead of downloading them again and deletes them when the fill is done, only if the manifest on the network is its own (`olvidar`).
- **Background fill**: 2.5 s after the worker starts (and at every `fetch` event, inside `waitUntil`, if the browser stopped it and the worker is not "stale") it downloads the manifest files not yet in the cache (6 at a time, excluding `nofill`: `static/esempi/` and files > 6 MB) and at the end sets the `.fill-done` mark; if a file fails there is no mark and the first request after a pause (30 s, doubled at every round up to 10 min) restarts and downloads only the missing ones
  (this is why `seal_sw` does not put `.nojekyll` in the manifest: GitHub Pages answers 404 for it, so the mark never arrived and the caches of earlier versions stayed); after a deploy the unchanged files come from the cache of the previous version. It does not block `install`.
- **`vendor/`** (Ketcher): cache first in `mzlab-big-*`, as before. Every response has COOP/COEP/CORP and `Cache-Control: no-cache` (`isolata`): without them the in-memory browser cache (`max-age=600` of GitHub Pages) would give the next page a file of the previous version without asking the worker.
  The copies are saved already with these headers (`guardar`) and a copy that has them goes to the page as the cache gives it: a new `Response` at every answer made the ~300 bodies of a load pass through the worker thread (warm `qqReady` ~100 ms later, `measurements-code-cache.md` S3). A copy saved by an old worker (without headers) is still wrapped until a deploy takes it again (`heredado`).
  No response uses the V8 code cache: Chromium keeps it only for a network response returned as is, never for a constructed `Response`, even if saved.
- **"Start from scratch"** (`reset.js`) deletes caches and registration (in parallel, each with its own timeout): the next page is downloaded from the network, the new worker restarts from an empty cache and fills it, and the page isolates itself with a single reload (`ripn`: Chrome puts back the old `mzlab.coiReload` guard when the worker is unregistered, so after a reset only the guard equal to the nonce counts; see `capabilities.md`).
- Tests: `tests/sw_cache_node.mjs` (simulated scope, also preload and `?nav=cache`), `tests/test_manifest_sito.py` (`seal_sw`), `tests_e2e/e2e_sw_versione.py` (three versions of the site served one after the other with the GitHub Pages headers: normal reload = new version, warm reload with no static requests, never files of two versions, "Start from scratch" = latest version; with `?nav=cache`: no page request, after a deploy the old version, then the notice, then the new one after "Reload"), `e2e_isolamento`. Measurement: `tests_e2e/misura_ricarica.py`.
