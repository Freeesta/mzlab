# Service worker (`mzlab/web/sw.js`)

Solo nel browser: l'app desktop serve `mzlab://` e non scarica mai `sw.js`.

- **Cache dell'app** `mzlab-app-<hash>`: il nome porta l'hash del sito pubblicato. `seal_sw` in `tools/build_site.py` scrive `static/sw-manifest.json` (`app`, `files`: percorso → SHA-256, `nofill`) e mette `app` in `const APPV` di `sw.js`; gira alla fine di `build_site.py` e di nuovo con `--build-json` (`.wasm` e pacchetti già al loro posto), quindi un cambio in qualunque file è una cache nuova. Il manifest del desktop (`manifest.json`) non contiene `sw-manifest.json`.
- **File dell'app: cache prima.** Un file nella cache è per costruzione la versione giusta, non si riconvalida. Un miss va alla rete (prima la cache HTTP, poi `no-cache` se lo SHA-256 non è quello del manifest), si salva SOLO se lo SHA-256 coincide; la pagina riceve il corpo controllato subito e il salvataggio segue in `waitUntil` (a cache fredda ~30 miss prima della prima pittura non aspettano le scritture della cache; `sw_cache_node.mjs`). Mai in cache: `api/`, `static/librerie/`, `manifest.json`, `build.json`, `sw-manifest.json`, file fuori dal manifest.
- **Pagine (navigazioni): rete prima**, timeout 3 s poi la copia in cache; a ogni navigazione il manifest si richiede di nuovo. Se descrive un'altra versione (`app` diverso) il worker è «stale»: dalla sua cache dà solo i file il cui SHA-256 è quello del manifest nuovo (un deploy cambia pochi file; mai una coppia JS/wasm mista), il resto dalla rete, non salva nulla e chiede `registration.update()`; il worker nuovo (`skipWaiting` + `clients.claim`) lo sostituisce.
- **Worker riavviato**: il browser ferma un worker inattivo e lo riavvia con `stale` dimenticato; finché quel giro del worker non ha chiesto il manifest (`visto`), la prima richiesta di un file lo chiede prima di rispondere dalla cache, così una pagina della versione nuova non riceve mai un file della vecchia. Un worker «stale» non tiene aperto nessun evento (`waitUntil` del riempimento): il nuovo si attiva solo quando il vecchio non ne ha.
- **Cache precedenti**: `activate` lascia le `mzlab-app-*` di prima; il worker nuovo ne copia i file con lo stesso SHA-256 (`heredado`) invece di riscaricarli e le cancella a riempimento finito, solo se il manifest in rete è il suo (`olvidar`).
- **Riempimento in background**: 2,5 s dopo l'avvio del worker (e a ogni evento `fetch`, dentro `waitUntil`, se il browser lo ha fermato e il worker non è «stale») scarica i file del manifest non ancora in cache (6 alla volta, esclusi `nofill`: `static/esempi/` e file > 6 MB) e alla fine mette il segno `.fill-done`; dopo un deploy i file invariati vengono dalla cache della versione prima. Non blocca `install`.
- **`vendor/`** (Ketcher): cache prima in `mzlab-big-*`, come prima. Ogni risposta ha COOP/COEP/CORP e `Cache-Control: no-cache` (`isolata`): senza, la cache in memoria del browser (`max-age=600` di GitHub Pages) darebbe alla pagina dopo un file della versione precedente senza chiedere al worker.
- **«Riparti da zero»** (`reset.js`) cancella cache e registrazione (in parallelo, ciascuna con il suo tempo massimo): la pagina dopo si scarica dalla rete, il nuovo worker riparte da una cache vuota e la riempie, e la pagina si isola da sola con un solo ricarico (`ripn`: Chrome rimette la guardia `mzlab.coiReload` vecchia quando il worker viene disiscritto, quindi dopo un reset conta solo la guardia uguale al nonce; vedi `capacita.md`).
- Prove: `tests/sw_cache_node.mjs` (scope simulato), `tests/test_manifest_sito.py` (`seal_sw`), `tests_e2e/e2e_sw_versione.py` (tre versioni del sito servite una dopo l'altra con le intestazioni di GitHub Pages: ricarico normale = versione nuova, ricarico a caldo senza richieste statiche, mai file di due versioni, «Riparti da zero» = versione più recente), `e2e_isolamento`. Misura: `tests_e2e/misura_ricarica.py`.
