# CI: quali test girano e come si dividono

Gli shard pytest di `test.yml`: cache `target`, esclusioni per diff (`doppi`, `aree`), build condivise (`prebuilt`), ordine e metà. Il resto dei workflow condizionali è in `ci-veloce.md`.

- La cache `target` la salvano solo gli shard 3.11, una per shard (chiave `pytest-wasm-<shard>-…-rel`, con l’hash di `tools/ci_cargo_mtime.py` e dello shim: cambiare lo shim rifà la cache); lo shard `solo311` esegue le build `--release` dei test lenti.
- `tools/ci_pytest_doppi.py <base>` (passo `doppi`) esclude `test_guardie_memoria`, `test_feat_wasm` e `test_flow_determinismo` se il diff attiva il filtro Rust di `rust.yml`, che li esegue già. Prova: `tests/test_ci_pytest_doppi.py`.
- `tools/ci_pytest_aree.py <base>` (passo `aree`, solo `pull_request`; push e merge_group eseguono tutto) esclude i test che chiamano cargo se il diff non li raggiunge: dipendono da `crates/`, `Cargo.*`, toolchain, vendor, dai file che le crate incorporano (`include_str!`) e dalle aree che il loro sorgente nomina (web, `TP_Mine`, `docs`, `tests_e2e`). Fuori da queste aree o con un file non-test di `tests/` esegue tutto; con `--build` `prebuilt` non costruisce se nessuno resta. Prova: `tests/test_ci_pytest_aree.py`.
- Build condivise: i job `prebuilt (native|wasm-a|wasm-b)` di `test.yml` costruiscono una volta `mzlab-cli`, gli esempi e i `.wasm` dei test (`tools/ci_prebuilt.py`, elenco `GROUPS`); ripristinano la cache `pytest-wasm-v3-rest-a-` (stessi percorsi del salvataggio dello shard, parte della versione; `MZLAB_CACHE_JOB=pytest-shard` per il registro dei mtime); gli shard li attendono (`ci_attendi_job.py`), li scaricano e impostano `MZLAB_PREBUILT`.
- `tests/cargo_util.py` (`build`, `cli`, `example`, `installed`) installa quel file invece di lanciare cargo; senza variabile, o per una build non elencata, cargo gira come sempre. `prebuilt` non è un controllo richiesto (se fallisce gli shard costruiscono da soli) e `browser` non lo usa; `test_ci_prebuilt` verifica che ogni build dei test sia in `GROUPS`.
- `tools/pytest_lenti.txt` (file e secondi medi, dal più lento; si rigenera con `python3 tools/ci_pytest_slow.py --scrivi` dalle ultime run 3.11 di `stat-ci`, media ≥ 5 s) dà l'ordine (`ci_pytest_ordine.py`: i lenti in testa) e le metà (`ci_pytest_meta.py`: ogni file lento alla metà più leggera; gli altri per hash; i file di `SPLIT_FILES`, `test_lettori_parita` con 8 build cargo, alternano i test fra le metà). Prove: `tests/test_ci_pytest_lenti.py`, `tests/test_pytest_meta.py`.
