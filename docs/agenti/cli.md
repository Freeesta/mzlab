# Riga di comando (`crates/mzlab-cli`)
Parte del motore Rust (`docs/agenti/rust.md`). Binario nativo `mzlab-cli` (non va mai nel sito né nel grafo WASM; il nome `mzlab` è del binario dell'app desktop). Piani e `prov/1`: `rust-flow.md`; descrittori `step/1`: `rust-step.md`; tela: `flow-grafica.md`.

## Comandi
- `mzlab-cli features FILE... [--out PATH] [--preset auto|pos|neg | --params FILE.json] [--help]`: esegue lo stesso motore della pagina sui file (più file = una serie, nell'ordine dato; indice, picchi e candidati deboli per file su un pool di thread: `par.rs`, `MZLAB_PHASES=1`: secondi per fase) e scrive la tabella delle feature allineata in CSV. La logica è in `src/lib.rs` (`execute`), senza regole proprie; `src/main.rs` la chiama soltanto.
- Ingressi: un `.mzML` passa dalla tabella delle scansioni (`upload::prepare` + `mzidx::build_mzml_spill`); ogni altro file singolo che l'app legge (`.raw`, mzXML, `.cdf`, ...) passa dal lettore del registro (`mzlab_lettori::apri`, `upload::indicizza_lettore`). Gli insiemi di più file (`.wiff` + `.wiff.scan`, cartelle `.D` o `.raw`) non sono accettati. Gli indici stanno in una cartella temporanea cancellata alla fine.
- Parametri: la stessa sorgente del pannello Pipeline. Il testo JSON (`--params FILE.json`; chiavi `polarity`, `mode`, `floor`, `min_height`, `min_points`, `ppm`, `rt_tol`, `fill`) va a `run::recipe_for`, che sceglie la ricetta adatta al primo file (alta risoluzione o profilo a risoluzione unitaria) come fa il sito. `--preset` è solo un nome per `{"polarity":1}` (pos), `{"polarity":-1}` (neg) o nessun testo (auto, predefinito); preset e file dei parametri insieme sono un errore.
- Passi: `run::detect` per file, `run::read_files`, `run::align` (allineamento e riempimento), poi `mzlab_feat_table_wasm::core::table_file(.., "full")`: il CSV «full» di mzmine che la pagina scarica (`export::csv_full`), campioni proposti dai nomi dei file (`campioni/1`), nessuna vista.
- Uscita: `--out` con un percorso `.csv` scrive lì, con una cartella scrive `features.csv`, senza `--out` va su stdout. I messaggi di avanzamento e gli errori vanno su stderr; codice 2 per un errore d'uso o di lettura.
- `mzlab-cli campioni variabili [--names FILE|-] [--pos N [--sep CHARS]] [--has a,b [--substring]]` e `mzlab-cli campioni nome-gruppo NOME...` (`campioni_cmd.rs`, prove in `campioni_cmd_tests.rs`): le rotte `campioni(op="variabili")` (nomivar/1) e `campioni(op="nome_gruppo")` sugli stessi nomi (uno per riga), stessi byte della pagina; `campioni.md`.
- `mzlab-cli peaks-edges TRACCIA.csv|- --at MIN [--ref MIN] [--mrm] [--set NOME=VALORE...]` (`peaks_edges_cmd.rs`, prova `peaks_edges_cmd_tests.rs`): i bordi del picco in bassa risoluzione di `peakq_lr::lr_edges`, la funzione che la pagina chiede con `QUALITA.edges`; `{"edges":[t0,t1]}` o `{"edges":null}` sotto `snMin`; i nomi di `--set` sono quelli della finestra «Parametri di rilevamento dei picchi» (`dati-integrazione.md`).
- `mzlab-cli llm tools [--out FILE]` (`llm.rs`, prove in `llm_tools_tests.rs`; catalogo in `mzlab-llm`): il catalogo `strumenti/1` generato da `flow::steps()` e da `executable`; `docs/agenti/llm.md`.
- `mzlab-cli llm replay REG.jsonl --conv CONV.json [--turn N] [--strict]` (`llm.rs`, prove in `llm_replay_tests.rs`, registrazioni sintetiche in `tests/data/llm/`): gli eventi normalizzati di un turno di una registrazione `llmreg/1`, una riga JSON per evento; il turno è il numero di messaggi `assistant` della conversazione; errori = codice 2.
- `mzlab-cli tutor eval CASI --blocchi F (--replay DIR | --solo-recupero | --provider ID --key-file F ...)` (`tutor.rs`, prove in `tutor_tests.rs`, dati in `tests/data/tutor/`; logica in `mzlab-tutor`): valuta il tutor sulla Teoria su registrazioni (CI) o, a mano, con una chiave; una riga JSON per caso e il riassunto, uscita 1 se un caso non passa; `docs/agenti/tutor.md`.
- `mzlab-cli llm context RUNDIR [--budget N] [--hide-names]` e `mzlab-cli llm eval CASES_DIR --replay DIR` (`llm_ctx.rs`, prove in `llm_eval_tests.rs`): il `contesto/1` di una cartella di corsa e il punteggio dei casi di valutazione sulle registrazioni; dettagli in `docs/agenti/llm.md`.
- `mzlab-cli msn-graph FILE.mzML [--formula ION] [...]` (`src/msn_graph.rs`): il grafo `msngrafo/1` di un'infusione MSn con le opzioni di `msngrafo::Opzioni` (`--help`); `--verita FILE --riassunto` stampa una riga di soli numeri contro un file di percorsi e formule attesi. `--strutture NODO` (con `--smiles`) aggiunge `strutture` (`msn-grafo.md` §2). `--figura svg,html[,png]` e `msn-graph figure IN.json`: `msn-figura.md`. Contratto in `msn-grafo.md` §3 e §6.
- `mzlab-cli msn-lib add LIB FILE.mzML --id ID [opzioni di msn-graph] | build MANIFEST.tsv [--dir D] [--out LIB] | export LIB [--pulito] [--tutti] | search LIB GRAPH [--delta N]` (`src/msn_lib.rs`, prove `msn_lib_tests.rs`): la libreria `msnlib/1` scritta da `msngrafo::aggiungi`, come la rotta `api/msnlib/aggiungi`; `build` legge colonne `id, formula_neutra, addotto_atteso, file` (opzionali `smiles, attivazione`), `export` scrive gli MS2 (o tutti i livelli) come MSP. Contratto in `msnlib.md`.
- `mzlab-cli validate FILE.mzML... [--json]` (`validate.rs`, logica in `mzlab_core::mzmlvalida`): struttura (elementi obbligatori, `count`, `defaultArrayLength`, m/z in ordine, `encodedLength`), vocabolario PSI-MS (accession, nome, unità ammesse, termini obbligatori di spettro, cromatogramma e array; tabella `crates/mzlab-core/data/psims-cv.json` da `tools/psims_tabella.py`) e, per `indexedmzML`, offset, `indexListOffset` e SHA-1 di `fileChecksum`. Lo stesso JSON esce dall'azione «Valida mzML» del sito (modulo `valida`) e dell'app (`lr_valida`).
  Uscita: una riga `error|warning PERCORSO-XML codice: messaggio` per problema su stdout (con più file ogni riga comincia con `FILE: `), il riassunto di ogni file su stderr, `--json` = un array con un oggetto per file; uscita 0 nessun errore, 1 errori, 2 uso o file illeggibile; avvisi (termine obsoleto, valore senza unità) non cambiano il codice. Si ferma dopo 1000 problemi.
- `mzlab-cli ion-pattern FORMULA ADDUCT [--out PATH]` (`ion_pattern_cmd.rs`, prove nello stesso file): il JSON di `api/ion_pattern`, lo schema isotopico a risoluzione unitaria di uno ione (`mzlab_core::ionpattern`); uscita 2 per formula, addotto o elemento sconosciuti.
- `mzlab-cli canali FILE [--canale ID [--rt T0[,T1]] [--n N]] [--out PATH]` (`canali_cmd.rs`, prove in `canali_tests.rs` con i file di `tools/dati_sintetici.py`): il `canali/1` del file (TIC, BPC, un canale per tipo di scan o precursore, `dd:<livello>` oltre 64 precursori, una per transizione SRM, `uv:twc`, `an:<i>`) uguale a `api/canali`; con `--canale` la traccia del canale UV/analogico (`--rt`: spettro UV di `uv:twc`) uguale a `api/chrom?kind=pda`, `api/uvxic`, `api/analog`, `api/uvspec`; SRM, SIC, UV e analogici solo per un mzML. Modello: `canali-dati.md`.
- `examples/mzml_confronta.rs A.mzML B.mzML [--per scan|indice] [--f32] [--numpress]` (stesso passaggio di `mzmlvalida::analizza`): accoppia gli spettri per numero di `scan=` (o per posizione) e i cromatogrammi per tipo, Q1 e Q3; stampa solo conteggi e scarti massimi di livello, polarità, RT (≤1e-6 min), precursori (m/z, carica), punti, m/z (0 ppm; `--f32` 0,05) e intensità (relativa ≤1e-6; `--numpress` 2e-4); uscita 1 se qualcosa supera la tolleranza o resta senza coppia.
- `mzlab-cli flow run PIANO.json [--in FILE|CARTELLA...] --out CARTELLA [--set ISTANZA.PARAMETRO=VALORE...] [--workers N] [--budget-mb N] [--dry-run] [--fresh] [--jsonl]` (`flow_run.rs`: argomenti, `--set`, ingressi, controllo; `flow_out.rs`: cartella e codice di uscita). `--jsonl`: eventi `flowlive/1` su stdout (`flow-live.md`). `--dry-run` controlla piano, `--set` e ingressi e stampa su stdout gli ingressi trovati e le istanze in ordine con i parametri canonici, senza scrivere nulla.
- **Memoria dell'allineamento**: `features.align` e `features.gapfill` usano `slabs::align_and_fill_stored` sotto un `MemBudget`: nativo `budget_auto` (RAM/4), `--budget-mb N` lo fissa (prove). Il riempimento gira un file per thread (`run::align_to_par`). Tre vie con gli stessi byte: `memory`, `slabs` (fette di m/z, anche nel modo famiglia), `refused` (`error.memoryBudget`). `prov/1` e `corsa/1` riportano per il passo `mem_mb` e `via` (`slabs::stima`); `prov.json` e `corsa.json` cambiano con `via`, i file dati no.
- `mzlab-cli normative build --cache DIR --out normative/ [--only ID...] [--update-pins] [--no-resolve] [--allow-large]` (`normative/`, solo nativo): costruisce le liste normative UE e USA dalle fonti ufficiali; uscite 0/1 (lista `stale`)/2 uso/3 pin/4 troppo grande/5 fonte/6 file, chiavi `err.normative.*`; dettagli in `docs/agenti/normative.md`.
- Un mzML con array MS-Numpress si apre ovunque la CLI chiede un file (`features`, `canali`, indice del Flow): `flow_pace::build_index_with` lo manda al lettore `mzml-numpress` del registro, come `convert`.
- `mzlab-cli convert INGRESSO... --out CARTELLA [--zlib N] [--numpress] [--peaks file|profile|mzlab] [--workers N] [--report FILE.json] [--fresh] [--set conv.NOME=VALORE...]` (`convert.rs`, `convert_report.rs`; prove in `convert_tests.rs` con `convert_fixtures.rs`): chiamante sottile dell'esecutore di `convert.mzml` (`flow_base::convert_job`, che legge `zlib_level`, `numpress` e `peaks`). Piano di un passo `conv` (un ingresso per file o campione), cache in `CARTELLA/.convert`, `NOME.mzML` in `CARTELLA`.
  `--peaks` sceglie i picchi scritti (valore sbagliato: uscita 2); un campione a profilo con `file` resta a profilo e il piano registra `warn.flow.profile`.
  Ingressi: un file, una cartella dei produttori (`.D`, `.d`, `.raw`) o una cartella scorsa in ordine di nome (solo le estensioni di `mzlab_lettori::estensioni()`, mai `--out`). Un insieme con più campioni dà `NOME-ID.mzML` per campione; a nomi uguali si tiene l'estensione dell'ingresso.
  I byte sono quelli di `flow run` con un piano `convert.mzml` e non dipendono da `--workers`; un file già convertito (stessi SHA-256 d'ingresso, parametri e programma) si salta, `--fresh` lo rifà. Avanzamento su stderr, una riga per file; stdout elenca gli mzML.
  `--report`: array con `{ingresso, uscita, sha256, spettri, secondi, saltato, conv/1}` o `{ingresso, errore, causa}`. Uscita 0 tutto bene, 1 qualche file in errore (gli altri sono scritti), 2 uso sbagliato o uscita sopra un ingresso, 4 ingresso mancante o cartella senza file da convertire.
- `mzlab-cli flow report RUNDIR [--out FILE]` (`flow_report.rs`): il `corsa/1` di una cartella di corsa (`prov.json` e i file accanto).
- `mzlab-cli steps [--json] [--id ID[@V]]` (`steps_cmd.rs`): i passi del registro `flow::steps()` del binario stesso. Senza `--json` una riga `id@versione  native|page  titolo` (`native` = `flow::executable`); con `--json` l'array `step/1` di `registry_json` con `"executable_native"` come ultima chiave di ogni passo; `--id` un solo passo (con `--json` un oggetto; senza `@V` la versione più alta); passo ignoto = uscita 2 con `err.flow.step.unknown`.
- `mzlab-cli flow check PIANO.json [--set ISTANZA.NOME=VALORE...] [--json]` (`flow_json.rs`): controlla il piano come `flow run` (`prepare`: confronti, `flow::check`, passi senza esecutore) senza cercare gli ingressi; uscita 0 valido, 3 problemi, 2 uso, 4 piano illeggibile. Con `--json` `flowcheck/1` `{valid, problems:[{instance, port, error_key, params}]}` su stdout.
- `--json` di `flow run` (anche con `--dry-run`): su stdout un solo documento, `flowdry/1` (ingressi trovati con byte e SHA-256, istanze in ordine con parametri canonici e `params_sha256`), `flowrun/1` (codice, cartella, `plan_sha256`, per istanza stato `ok|cached|error|skipped`, `ms`, uscite con porta, file, SHA-256 e byte, errore con chiave e parametri) oppure `errore/1`. Codici d'uscita, stderr, file di `--out` e `prov.json` non cambiano.
  `errore/1`: `code`, `error_key`, `params`, `message`, `hint`, `problems` se il piano non è valido; chiavi `err.cli.usage|set|file|input.missing|input.twice|out` oltre alle `err.flow.*` del motore. `--progress jsonl`: su stderr una riga JSON per lavoro `{job, of, instance, item (da 1, o null), status ok|cached|error, ms}` al posto di `[3/9] ...`. Schemi `docs/schemi/{flowcheck,flowdry,flowrun,errore}-1.json`; prove `flow_json_tests.rs`, `tests/test_cli_json.py`.
- `examples/flow.rs` (non è un comando): chiamante sottile di `mzlab_cli::flow::run_plan`: legge un file `mzflow/2`, lo controlla, lo esegue con N thread e scrive `prov.json` (SHA-256, ms, picco di heap per istanza); compila anche per `wasm32-wasip1` (`tools/wasi_run.mjs`). Lo stesso `run_plan` è la rotta `flow/run` dell'app desktop (`crates/mzlab-desktop/src/flow_run.rs`).
- Prova: `cargo test -p mzlab-cli` (`src/tests.rs`, nel crate: un binario di prova sarebbe una seconda compilazione del motore): tre mzML sintetici, il CSV del binario (ricetta predefinita, `--params`, `--preset neg`) è uguale carattere per carattere a quello della catena della pagina su indici costruiti in memoria; `--help` e gli errori d'uso. Nessun browser, nessun Python.
- Intestazioni: nessuna colonna si chiama «formula» da sola (formula neutra o dello ione); la prova di `src/tests.rs` lo controlla sul CSV.

## Copertura: registro dei passi ed esecutore nativo
- Registri: `mzlab_feat::steps::registry()` (13, `steps-1.json`), `attributio()` (10, `steps-attributio-1.json`), `mzlab_chem::step::tabui()` (9, tutta la famiglia, `steps-tabui-1.json`), passi del crate (`features.table`, `spectra.centroid`, `spectra.ms2`, `spectra.msn_graph`, `meta.compare`, `quant.calibrate`, tutti in `steps-cli-1.json`). `mzlab_cli::flow::steps()` li unisce tutti; la pagina Flow legge i quattro file.
- Eseguiti da `FileRunner` (`EXECUTORS` di `flow.rs`): `convert.mzml`, la BASE (`index.mzidx`, `features.detect`, `features.align`, `features.gapfill`: `flow_base.rs`), `features.estimate`, `features.table`, `table.drift`, `table.kmd`, `table.plausible`, `spectra.ms2` (DIA: `dia.md`), `spectra.msn_graph`, `spectra.lookup`, `spectra.match`, `formula.ms1`, `formula.ms2`, `annot.level` (regola di `livelli.js`), `tp.generate`, `tp.link`, `tp.filter`, `tp.position`, `tp.network` (`flow_network.rs`), `chrom.uv_peaks`, `meta.compare`, `quant.calibrate`, `export.inclusion`.
  Un passo senza esecutore è rifiutato prima di partire (`err.flow.step.native`, anche in `flow/run` del desktop).
- Passo per passo: `cli-passi.md` (una riga per ogni passo del registro con esecutore nativo).
- Parametri: ogni parametro dei passi esportati (più `features.table` e `meta.compare`, non esportati), anche degli algoritmi, si imposta con `--set`. `features.table` usa le chiavi del pannello Pipeline (`ppm`, `rt_tol`, che `apply_params` divide in due campi) e non ha `fill`.

## Regole della CLI (valgono per ogni comando e modulo nuovo)
- **Un solo registro**: `mzlab_cli::flow::steps()` è l'unione di TUTTE le famiglie di descrittori (core, Attributio, Tabui, passi del crate); i file `docs/schemi/steps-*-1.json` sono le sue esportazioni e la pagina legge le stesse. L'esecutore nativo è una sola tabella `id → funzione` in `flow.rs`; da essa si ricava l'elenco dei passi eseguibili (nessun secondo elenco scritto a mano).
- **Nessun parametro solo-interfaccia**: ogni proprietà di `params` del descrittore (anche quelle di un algoritmo, l'algoritmo e il preset) è un'opzione: `--set ISTANZA.PARAMETRO=VALORE`, `--set ISTANZA.algorithm=NOME`, `--set ISTANZA.preset=NOME`. ISTANZA è l'`id` dell'istanza nel piano; vale anche l'`id` del passo se il piano ne ha una sola istanza. Il valore si legge col tipo del descrittore (numero, intero, booleano, scelta, testo, coppia `a,b`) e passa da `flow::check`.
- **Modulo nuovo (lista di controllo)**: (1) descrittore `step/1` nella famiglia ed esportazione rigenerata; (2) esecutore in `FileRunner` che prende nomi e byte e restituisce il testo/byte del file (nessun `std::fs` fuori da `flow.rs`); (3) test di parità CLI = motore della pagina (byte uguali); (4) riga di aiuto se nasce un comando; (5) riga qui e nel file d'area. Un parametro letto dall'interfaccia ma assente dal descrittore è un errore.
  (6) `flow_rule_tests.rs` resta verde: ogni parametro (anche degli algoritmi) raggiunge i parametri canonici con `--set`, ogni passo `native: true` ha un esecutore o sta in `BUCHI`.
- **Messaggi**: tutto in inglese; avanzamento solo su stderr, scritto mentre la corsa procede, una riga per lavoro (`[3/9] features.table (feat) ... done in 12.4 s`; un passo `per_item` aggiunge `item 2`), poi `done: N steps; outputs in CARTELLA`; stdout resta per i dati. Un errore stampa `error: <chiave> <parametri>` e una riga `hint:` con il rimedio.
- **Codici di uscita**: 0 corsa completa; 1 corsa finita con istanze in errore (le altre uscite sono scritte, `prov.json` e `corsa.json` ci sono); 2 uso sbagliato (opzione, `--set` malformato); 3 piano non valido (`flow::check`, un problema per riga); 4 ingresso mancante, illeggibile o con SHA-256 diverso; una cartella `--out` non scrivibile è un errore d'uso (2).
- **Ingressi**: i nomi di `inputs` del piano si cercano fra i file dati con `--in` (per nome), poi nelle cartelle date con `--in`; senza `--in`, nella cartella del piano. I formati nativi passano da `mzlab_lettori::apri` (`Limiti::desktop()`); un insieme di più file (`.wiff` + `.wiff.scan`, cartelle `.D`/`.d`/`.raw`) è un ingresso di `convert.mzml` (`flow_set.rs`); `NOME@ID` nomina il campione `ID` di un insieme con più campioni, senza `@` vale il primo.
- **Uscite** (`--out CARTELLA`): un file per porta di uscita (`<istanza>.<ext>`, `<istanza>-<k>.<ext>` per un passo `per_item`), `plan.json` (il piano effettivo: forma canonica con i `--set` applicati, che rilanciato senza `--set` rifà la stessa corsa), `prov.json` (`prov/1`) e `corsa.json` (`corsa/1`). Le temporanee stanno in `--out` e si cancellano.
- **Riproducibilità**: stesso piano e stessi ingressi danno gli stessi byte di ogni file d'uscita con 1 o N `--workers`; in `prov.json` e `corsa.json` cambiano solo `ms`, `total_ms` e `heap_peak_bytes`. Il `prov/1` porta versione del crate, piattaforma, target e, se la compilazione li conosce (`option_env!`: `MZLAB_COMMIT` intero, `MZLAB_RUSTC`, `MZLAB_CARGO_LOCK_SHA256`), commit, `rustc` e SHA-256 di `Cargo.lock`, più `modules.mzlab-cli` = SHA-256 dell'eseguibile (`docs/agenti/rust-flow.md`).
- Prova della cache: `src/flow_cache_tests.rs`: seconda corsa tutta `cached` con gli stessi byte; un parametro di `align` ricalcola `align` e `gapfill`, non indice e `detect`; `--fresh` ricalcola tutto con i byte della prima corsa; un file d'uscita cambiato a mano si ricalcola; `run_plan_cached` della rotta desktop riprende la stessa cache.
- Prova: `src/flow_run_tests.rs` su tre mzML sintetici: la BASE dà la tabella della pagina (`gap.mzfeat` = `run::align` con riempimento, `ali.mzfeat` = senza), `plan.json` rilanciato con 2 worker e la rotta `run_plan` danno gli stessi file e lo stesso `prov/1` (tempi e heap a parte), `--set` per passo e per istanza, `--dry-run`, codici 2/3/4.
- **Identità della compilazione** (`flow::build_agent`, la stessa per CLI, desktop e `.wasm`): `commit` intero (`MZLAB_COMMIT`), `platform` e, se noti, `target` (`MZLAB_TARGET`), `rustc` (`MZLAB_RUSTC`), `cargo_lock_sha256` (`MZLAB_CARGO_LOCK_SHA256`), `modules` (nome → SHA-256; la CLI scrive `mzlab-cli` = il proprio eseguibile). Chiave assente = non scritta: un record senza chiavi nuove ha gli stessi byte.
  `tools/prepara_sito.py` imposta le variabili; il `.wasm` si costruisce SENZA commit (i suoi byte cambierebbero a ogni commit): il commit del sito sta in `version.js` e `static/build.json` (`build_site.py --build-json` dopo i `.wasm`).
- **Cache** (`flow_cache.rs`): in `--out/cache/index.json` (`mzflow-cache/1`) ogni lavoro è scritto sotto `flow::cache_key` (SHA-256 degli ingressi per porta, passo, algoritmo, `params_sha256`) più istanza, elemento e versione del programma (`MZLAB_COMMIT` compreso), con file di uscita, SHA-256, stime e la provenienza che i passi seguenti della BASE leggono (`Lineage`: indice del profilo e parametri scritti da ogni passo, così la ricetta si rifà).
- Ripresa: una corsa nella stessa cartella riprende un lavoro la cui chiave c'è e il cui file ha ancora quello SHA-256: niente calcolo, `cached: true` in `prov/1`, `... reused` su stderr, stato `cached` in `corsa/1`. `--fresh` ricalcola tutto e riscrive l'indice; i file delle voci vecchie che la corsa non usa sono cancellati. Fuori dalla cartella non si legge né scrive nulla.
- **Cluster**: nessuna rete, nessun file fuori da `--in`/`--out`, nessuna domanda interattiva; `--workers N` (predefinito 1) per le istanze di un livello e gli elementi `per_item`; un piano per nodo, una cartella `--out` per corsa; il codice di uscita basta allo scheduler; la build `wasm32-wasip1` dello stesso sorgente gira in un sandbox WASI. La divisione di un piano su più nodi non è fatta.
- **Comando copiabile** («Run on CLI»): testo di Rust dal piano canonico con i nomi veri dei file di Dati, mai costruito in JS. POSIX: `command -v mzlab-cli || cargo install --path crates/mzlab-cli` (niente binari precompilati), `MZLAB_IN='…'` (segnaposto `FOLDER_PLACEHOLDER`, riempito da `F.cliFill`, citato una volta), cartella `mzlab-run-<data-ora>`, piano in here-doc `<<'MZFLOW'`, `flow run`. Anche da `mzlab-cli flow command PIANO` e dalla rotta `api/flow/command`.
- **Riga corta e `--set`** (`mzlab_core::flow::line`): `mzlab-cli flow run plan.json --in <cartella> --out mzlab-out --set ISTANZA.NOME=VALORE …`, un `--set` per algoritmo, preset e parametro diverso dal default, nell'ordine del piano. `apply_sets` (algoritmi e preset prima) è il codice della CLI (`flow_apply.rs` rimanda lì), del sito e dell'app; errore `err.cli.set` con `set` e `message`.
- Rotta `api/flow/line` (app: `flow/line`): senza `line` dà la riga, con `line` il piano con i `--set` applicati; `err.cli.line` se non è un `flow run`.
- **Fuori perimetro senza «via»**: binari precompilati, rilasci, nuove dipendenze della CI. Il comando presuppone `mzlab-cli` nel PATH (`cargo install --path crates/mzlab-cli --profile cli`).
