# Desktop app: native mzFinder, Pipeline, Attributio and graph
Continuation of `rust-desktop.md`: `feat.rs`, `feat_finder.rs`, `feat/*` routes, Pipeline panel, import, Attributio, graph, mzFinder in the page.

- **Native mzFinder** (`src/feat.rs`, `src/feat_finder.rs`; test `tests/feat.rs`): the `feat/*` and `finder/*` routes of `rpc` (outside the engine block) call the same fns as the `.wasm` (`mzlab_feat_wasm::run`, `mzlab_feat::legacy`, `mzlab_feat_table_wasm::core`) on the `.mzidx` of the index folder (files registered with `lr_put`/`lr_index`): same bytes as the site (`.mzfeatf`, `.mzfeat`, `.mzfeat` with the checks) and same JSON as the Dig.
  Step results stay in `FeatState` (field `State.feat`): the page names the files and asks for the next step, it sends no bytes.
  Parameters in the body JSON: `feat/detect {name, recipe}` (first `detect_fits` with the computer's budget), `feat/estimate_detect {name, recipe, budget_mb}` (`{mb, via}` like the .wasm's `estimate_detect`), `feat/align {names, recipe}`, `feat/hypotheses {names, rules, structure, parent, parent_rt, recipe}`, `feat/evidence {minutes, parent_mz, parent_rt, files, parent, recipe}` (they reply `{bytes, sha256}`; `hypotheses` also registry, `tried`, `found`), `feat/table {kind: view|report|qc|samples|export|ms2|bytes, ...}`;
  `feat/preview {name, recipe}` (preview of a file: estimates with checks, histograms and three traces, like the `.wasm`'s `preview_file`);
  `feat/files` (names of the files with `.mzidx` in the index folder), `feat/version` (version of the `mzlab-feat` crate, the one the gate names), `feat/clear`;
  With `files` and `parent` in `feat/evidence` the parent peak on the aligned table is computed in the app, `legacy::parent_peak` like the site's `finder_parent`, and prevails over `parent_mz`/`parent_rt`.
  `dig {files, parent, registry, msn}` (`msn` = the standard's MSn file: `feat_msn.rs`, like the `.wasm` `finder_msn`, gives tree, calibration and localizations at summary, `detail` and trees), `transf_rows {text}` (table of the user's list, `legacy::transf::describe`), `msn_tree`, `lr_plan {files, parent}`,
  `lr_mrm {files, rt_tol}` (per-transition MRM table from the registered mzML, `lr::mrm::file_from_mzml` like the `.wasm`, no calibration line; the page puts it in `mrm` of the summary), `estimate {names, mz}` (XIC window, RT tolerance = max(2·FWHM, RT drift of the precursor) and dead time from the preview of the first file, profile `lr`), `lr_dig {files, parent, registry}` (LR Dig on the table of the last `feat/align`; `detail` and the trees answer on the last Dig, HR or LR),
  `detail {id}`, `inclusion_csv {id}`, `frag_tree`, `frag_tree_compare`, `formula_info`, `identity_graph`, `polarity_pairs`, `origin_evidence`. Errors of `legacy` texts: `error.finder` with `detail`.
  `tp_table {samples, rows}` (`tptab/1` on the table of the last HR Dig: `mzlab_ops::run::table::core::tp_table_json` like the `table` `.wasm`; `null` without an HR Dig) and `campioni {cop, input}` (operations of `campioni/2`: `finder-desktop.js` asks for them with `samplesOf` of `finder-tabella.js`, async).
- **Pipeline panel in the desktop** (`TP_Mine/files/feat-desktop-pool.js`; test: step "Pipeline panel pool" of `e2e_shim_finder.py`): with `window.MZLAB_DESKTOP` `32_pipeline.js` (`getPool`, `listIdx`) uses `createDesktopPool` in place of the pool of `.wasm` workers: same methods (`crateVersion`, `preview`, `detectAll`, `align`, `hypotheses`, `evidence`), but every step is a `feat/*` route; the `.mzfeatf` stay in the app and the table comes back in pieces with `feat/table {kind: bytes}`.
  `detectAll` keeps up to 4 `feat/detect` requests open; the app runs them in the indexer's pool (cores minus one, at most 4), so several files run together and one core is left to the window (test: `detect_of_several_files_at_once_gives_the_same_bytes` in `tests/feat.rs`).
- **Roles in the desktop Pipeline panel**: the file roles (`finder-ruoli.js`, async functions) ask the pool for `campioni/2` (`pool.campioni` → `finder/campioni`); step "Pipeline panel in the app" of the shim: roles, Run, QC, table, report.
- **Tables from other programs in the desktop** (`feat_import.rs`, route `feat/import`; test: step "tables of other programs" of the shim): `kind: build` (files `{name, sha256, text}` → JSON table with the readers of `mzlab_feat::import`, errors with their key) and `kind: check_structure` (many annotations in one request). With `MZLAB_DESKTOP` `25_untarget.js` (`readyNative`) uses `pool.importBuild`: `UNT.build` answers with a promise and `UNT.prime(table)`, called by `UNTM.run`, fills the cache that `checkStructure` reads from.
- **Attributio in the desktop** (`feat_attributio.rs`, route `feat/attributio/annotate`): `{root, kind: json|csv|xlsx, files: [{path, text}]}` → `{summary, text}`, the same `mzlab_feat::attributio::table` as the `attributio` `.wasm` (`docs/agenti/attributio-pannello.md`).
  The files are those of the index folder (no OPFS, no `wasm-feat/`). The views of `36_`-`38_` (QC, table, export, report, MS2) are `feat/table` (`pool.table`, `ms2File`, `rowTraces`; types `row` and `row_traces`) on the table kept by the app, named by its SHA-256 (another table gives `error.featState`) and are asynchronous (`await` on the session methods).
- **Structure graph in the desktop** (`feat_graph.rs`, route `feat/grafo`; test: step "structure graph" of the shim): `kind: analyse` (SMILES → `grafo/1`, for `structureOf` of `34_pipeline_run.js` via `pool.analyse`), `fragments` and `partial` (molfile → `frag/1`, `parz/1`, for `disegno-frammenti.js` `carica()` and `disegno-parziali.js`). Errors keep their key (`error.grafo.*`) as the `.wasm` throws them; with `MZLAB_DESKTOP` `wasm-feat/manifest.json` is not read.
- **mzFinder in the desktop page** (`TP_Mine/files/finder-desktop.js`; test `tests/e2e_shim_finder.py`): `20_tpmine.js` sends the worker `init.desktop` (= `window.MZLAB_DESKTOP`); with that flag `tpmine-worker.js` sends every call to `createDesktop(...).call`, which calls only the `feat/*` and `finder/*` routes (no Pyodide, no `wasm-feat/`, no computation in JS).
  Before classify and the Dig `ensure` registers the files by name like the Data tab (`lr_boot`, `lr_put` if the file's number is not already the registered one, `lr_index` if the index is missing); the bytes of a file that exists only in the page ("Choose files...") go to the app once (`lr/upload`, in chunks as `Uint8Array`, never `Blob`: WKWebView on Mac delivers the body of a POST with `Blob` empty; an empty chunk is rejected with `err.file.unknown`, the example files pass through here).
  The Dig is: `finder/plan`, `feat/detect` per file, `feat/align`, `feat/hypotheses`, `feat/evidence`, `finder/dig`; then `detail`, `inclusion_csv`, `frag_tree`, `frag_tree_compare`. The user's transformation list goes through `finder/transformations` before `feat/hypotheses`.
  An LR series (full scan, several EPI MS2 files and MRM) does `finder/lr_plan`, `feat/detect`, `feat/align`, `feat/hypotheses` (skipped if the precursor has only the m/z: empty registry), `finder/lr_dig`, `finder/lr_mrm`; detail with MS2/transitions/specificity, `frag_tree` and the ISF verdict come from `lr::*`. The standard's MSn file leaves the series (`finder-desktop.js`) and goes to `finder/dig` by name. "Estimate from data" calls `finder/estimate`. Test: `crates/mzlab-desktop/tests/e2e_shim_finder.py`.
