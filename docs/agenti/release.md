# Release (tag `vX.Y.Z`)

- **Single version**: `Cargo.toml` (`[workspace.package]`), `crates/mzlab-desktop/tauri.conf.json` and `CITATION.cff` carry the same `X.Y.Z` (`.zenodo.json` only if it has the `version` field). `python3 tools/versione.py` checks it; `tests/test_versione.py` runs it in the mandatory pytest job, so a half-written version does not enter `main`. `--tag vX.Y.Z` compares with the tag; `--nota vX.Y.Z` prints the `## [X.Y.Z]` section of `CHANGELOG.md` (error if missing or empty).
- **Release gate**: `python3 tools/gate_release.py` starts on its own with `tools/versione.py --tag` (step `versione` of `release.yml`), with no way to skip it and outside normal CI; it prints OK/FAIL with `file:line` and remedy. Test: `tests/test_cancello_rilascio.py`.
  Checks: every `step/1` step has a row in `cli.md`; every `docs/agenti/*.md` is cited in `docs/agenti/INDICE.md`; `llms.txt` and `for-agents.md` cite only existing `mzlab-cli` subcommands; every crate has a non-empty `README.md`; code map (`tools/indice.py --controlla`, `graphify-out` if present, max 150 commits) up to date; `docs/rilascio/CHECKLIST-v<X.Y.Z>.md` (copy of `CHECKLIST-TEMPLATE.md`) with all boxes ticked.
- **`CHANGELOG.md`**: Keep a Changelog format, English only (sections Added / Changed / Fixed: the text of a version becomes the release notes); new entries go in "Unreleased" and move to the version section at release time.
- **`.github/workflows/release.yml`** (two starts: tag `v*` from the terminal, or `workflow_dispatch` by hand with the version typed twice; without a version = dry run, no release). The `controllo` job decides: on the tag with an already existing release it does nothing (it is the round that starts when the published draft creates its tag); from `workflow_dispatch` it refuses if the version is not `X.Y.Z`, if the confirmation differs, if it is not `main` or if the tag or release already exist:
  `versione` (version and notes check) → `sito` (the same steps as `pages.yml`, site zip + `tools/sbom.py`) in parallel with
  `desktop` (calls `desktop.yml`: universal macOS `.dmg`, Windows `.exe`, Linux AppImage and `.deb`, unsigned) and `sbom` (calls `sbom.yml`: CycloneDX of every crate) → `bozza` (environment `release`): gives the files the uniform names of `tools/note_release.py` (`mzLab-X.Y.Z-Windows.exe`, `-Mac.dmg`, `-Linux.AppImage`, `-Linux.deb`, `-sito.zip`, `-sicurezza-SBOM.zip` with all the `.cdx.json`), writes `SHA256SUMS` and creates a **draft release** with the notes in English: Windows / Mac / Linux table with direct links, then the changelog section.
- **File names**: the app's new-version notice reads only `tag_name`, so the asset names are free; changing them is done only in `tools/note_release.py` (`nomi()`) and in the "Name the files" step of `release.yml`. Nothing is published on its own.
- The command of the "Installer" step of `desktop.yml` must end with `-- --profile desktop` (profile `desktop` of `Cargo.toml`, `opt-level = 3`; see `docs/agenti/rust-desktop.md`); the `.wasm` stay on the `release` profile.
- The analysis CLI `mzlab-cli` is built with `cargo build --profile cli -p mzlab-cli` (profile `cli` of `Cargo.toml`, `opt-level = 3`, outputs identical to the `release` profile, which stays the `.wasm`'s); any binary in the release uses that profile.
- Measurement of the `cli` profile (36 indexed mzML, detect→align→gapfill plan, `tools/compare_profiles.py`): `release` 10.3 s with 1 worker and 4.3 s with 4; `cli` 7.4 s and 3.2 s (−28 %); binary 8.1 MB against 10.3 MB; cold build of `cli` 6 min (4 CPUs). With `lto = "thin"` and `codegen-units = 16` the speed is the same, the build 3 min and the binary 13.0 MB: not adopted.
- If the build steps in `pages.yml` change, they change in the `sito` job of `release.yml` too.
- **`tools/sbom.py`**: CycloneDX 1.5 of the site's JS and WASM components (Ketcher, OpenChemLib); versions are read from `mzlab/web/vendor/README.md` and `tools/build_site.py`.
- **Federico's steps** (the code does not do them):
  1) once, in Settings → Environments create the `release` environment and, if wanted, add yourself as required reviewer
  2) write the changelog section, raise the version in the three files, merge into `main`
  3) without a terminal: on GitHub, **Actions** tab → **release** workflow → **Run workflow**, branch `main`, in "version" type `1.0.0` (without `v`), in "confirm" retype `1.0.0`, **Run workflow** (if the two lines differ the workflow stops immediately and does nothing); with a terminal: `git tag v1.0.0 && git push origin v1.0.0`
  4) wait for all jobs to be green (about 30 minutes), then **Releases**: you find the **draft** "mzLab v1.0.0" with the files, `SHA256SUMS` and the changelog notes; check them and press **Publish release**: at that moment the tag `v1.0.0` is born on the `main` commit that was at the head at start, and Zenodo (if activated as in `docs/zenodo.md`) archives by itself and creates the DOI
  5) Software Heritage: at <https://archive.softwareheritage.org/save/> "Save code now" with the repository address (one click, needed once and after each release if you want the SWHID updated)
  6) fill in `doi` and `date-released` in `CITATION.cff` as in `docs/zenodo.md`.
- Out of scope of the release workflow: Windows (SignPath) and macOS signing, an own domain, `update.rs` pointing to another origin.

## Plan B: host the site elsewhere
The site is a static folder; there is no active mirror. **Build** `site/`: run `pages.yml` (`workflow_dispatch` or push to a test branch) and download its artifact, or repeat its `run:` steps by hand in the same order (`build_site.py`, `wasm_opt.sh`, `build_feat_wasm.sh`, `librerie_pacchetti.py`, `genera_sospetti.py`; Python ≥ 3.11, the toolchain of `rust-toolchain.toml`, network).
**Check**: no file above 25 MiB (`find site -size +25M`, Cloudflare Pages limit), no console errors from `python3 -m http.server -d site` with the service worker registered, `.wasm` served as `application/wasm`.
**Publish**: Cloudflare Pages "Direct Upload" (`npx wrangler pages deploy site --project-name mzlab`) or another static host over HTTPS that serves the files as they are.
**Moving to another address**: update `README.md`, `CITATION.cff`, `.zenodo.json`; the desktop app checks for updates only from `https://freeesta.github.io/mzlab/` (`crates/mzlab-desktop/src/update.rs`), so a version that accepts both addresses is needed first; the data saved in the browser stay tied to the address they were written under. Announce with a pinned issue and on the course page.

## Publishing the libraries
No crate or npm package is published; every outward action (crates.io, npm, reserved names, DOI) needs the Coordinator's "go".
- Candidates, in order: 1) the numpress codec separated from `mzlab-core` (`src/numpress.rs`, no dependencies, external truth in the MS-Numpress specification vectors); 2) `mzlab-lib` (`.mzlib` format, library readers, scores; no internal dependencies); 3) `mzlab-lettori` with the reading part of `mzlab-core`, to be separated first; 4) npm `mzlab-lettori-wasm`, only after 3, with the `.wasm` caps unchanged.
- Not candidates: `mzlab-feat` (contracts still moving), `mzlab-desktop`, `mzlab-cli`, the page's `*-wasm` crates; `vendor/opentfraw` is not republished, the changes (`vendor/opentfraw/MODIFICHE-MZLAB.md`) are offered to the original project.
- Licenses: MIT inherited with `license.workspace = true`; the `deny` job (`deny.toml`) checks the dependencies on every PR; with "MIT OR Apache-2.0" MIT is chosen; whoever redistributes `opentfraw` carries the Apache-2.0 license and the NOTICE of the changes; no GPL code copied.
- A public library requires: English facade with semver (`0.x` while it changes), rustdoc on every public item and README with an example that compiles, declared MSRV, tests with external truth without the private repository, `cargo package --list` without `mzlab-dati` data or forbidden surnames, per-crate CHANGELOG and `cargo semver-checks` before every release; free names on crates.io and npm to be verified.
- No crate carries `publish = false`, so an accidental `cargo publish` would go through; if it is added, it is removed only from the chosen crate.

## Repository security hygiene

- `dependabot.yml` (cargo, pip, github-actions: weekly, one group per ecosystem, at most 3 open PRs, never merged on their own; `wasm-bindgen`, `js-sys`, `web-sys` without major/minor jumps, `tauri*` without major) and `codeql.yml` (JavaScript and Rust, weekly and manual only, not mandatory) add no jobs to the PRs.
- Settings that only the owner turns on by hand (no file can set them), in Settings → Code security: Dependabot alerts, Dependabot security updates, push protection, Private vulnerability reporting; in Settings → General: Allow auto-merge. Secret scanning for public repositories is free and automatic (docs.github.com, "About secret scanning"); for the other switches the documentation does not declare a default activation, so they must be checked.
- No CodeQL "default setup": the `codeql.yml` flow replaces it (the default setup would also run on PRs).
- **Linux CLI**: the `cli-linux` job of `release.yml` (release and `workflow_dispatch` only, never the PR CI) builds a static musl `mzlab-cli` (profile `cli`) for x86_64 and aarch64, each on a runner of its own architecture, tests it (`--version`, `flow steps --json`) and attaches it as `-cli-Linux-x86_64` / `-cli-Linux-aarch64`; see `cli-agenti.md`.
