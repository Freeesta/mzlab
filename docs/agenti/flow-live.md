# Flow "live": the state scheduler (`mzlab_core::flow::sched`)

Used by `flow::execute` (`run_sched.rs`), the live run of the CLI and the app, and the site (`flow-live.js`).

## Requirements that hold
- Work happens while the graph grows: a job starts as soon as inputs and parameters are ready, per file (file 1 advances while 5 is converting), and the plan stays editable during the run; an edit touches only the downstream jobs, reuses the cache by `plan_key` and cancels only the obsolete jobs.
- Same bytes for same inputs in whatever order the jobs finish; same model on the site, the app and the CLI; limited memory (admission by estimated `mb`, never a "Use more memory" window in the middle of an edit); the interface appears before the scheduler.
- No new `.wasm` and no new ceiling for the scheduler; tests count events and states, never fixed pauses.

## What it does
A pure scheduler (no threads, files, clock, network) that, given an `mzflow/2` plan and the step registry, knows which jobs exist, in what state they are and which are ready, and reacts to a changing plan. The executor (thread or Worker) asks for work with `next`, reports `started`, `progress`, `finished`, `cached`, reads the events with `events_since`. Files:
`flow/sched.rs` (state machine, `update`, `next`), `sched_graph.rs` (jobs, dependencies, `plan_key`), `sched_view.rs` (states, cards, event log), `sched_events.rs` (`State`, `NodeView`, JSON text of the events), tests in `sched_tests.rs` and `sched_cases.rs`.

## Jobs and dependencies
- `JobId = (instance, item)`; `item` is the NAME of the plan input that drives the job, never an index. A `per_item` step has one job per element of the first `many` port it reads (like `jobs()` of `run.rs`); a non-`per_item` step has one job (`item = None`).
- If that port reads the `many` output of another `per_item` step, `(B, f)` depends only on `(A, f)`. A non-`per_item` step that reads a `many` port, or a port that does not drive, depends on ALL the upstream jobs (barrier).
- If the driving port reads the output of a step that is not `per_item` (number of elements unknown in advance) or of an invalid step, the step has ONE job with `item = None`: the shape of the jobs changes when the upstream becomes valid. Job names are therefore stable only as long as the upstream is.
- Elements are ordered like the port's references; the priority of `next` uses the position of the input in `plan.inputs`.

## plan_key
SHA-256 (`budget::sha256_hex`) of the `sched/1` text: `step@version`, `algorithm@version`, `Resolved::run_sha256()` (without the `noresult`; with what the plan writes if the step estimates), program version given to `Sched::new`, the element name (two files with the same fingerprint, e.g. "loading", do not share the key), then for each port in the order DECLARED by the step (not the one written in the file) the fingerprint of every file read (`sha256` of the plan, otherwise the text of `identities`/`set_identity`) and the `plan_key`s of the upstream jobs with the name of the output port.
Neither the name nor the position of the element enter the key: the file is identified by content. Same plan written with different JSON keys or step order = same keys; going back to an already tried value = the same key.
- **First-index recipe** (decision D2): `features.detect`, `features.align`, `features.gapfill` have one more edge toward the job that produces the index of the FIRST input of the plan from which the data descend (port `index`, or the HR source recipe for align). Adding a file at the end changes nothing; adding it at the HEAD changes the key of all detections (and of the downstream steps), not of the conversions nor of the indexes. This is intended: the HR recipe starts from the first index (`run::recipe_of_layers`).
- The key does not depend on the outcome of the upstream jobs, so it is known before running; today's key (`cache_key`, SHA of the outputs) remains as a check of the file taken from the cache.

## States
`waiting` (inputs not ready) · `ready` · `running{frac}` · `done` · `reused` (from the cache) · `stale` (there is an output of an old key; the job is redone as soon as its inputs are `done`/`reused`) · `cancelled` · `error{key,params}` · `refused` (`error.featMemory`) · `blocked{by}` (`plan.problem`, `platform.computer`, or the permission given to `block`; a new key removes the `block` block) · `skipped` (an ancestor is in error, refused, skipped or cancelled) · `paused` (view only: `ready` while the scheduler is paused).
- States that stay until the key changes: `running`, `done`, `reused`, `error`, `refused`, `cancelled`; `retry(id)` requeues the last three. The others are derived at every change from the jobs they depend on.
- `finished(id, Err(e))`: `error.featMemory` → `refused`, `err.flow.cancelled` → `cancelled`, anything else → `error`.

## Updating the plan
`update(&Plan) -> Vec<Command>` (only `Cancel(JobId)`): recomputes the jobs and the keys, then for each job with the same `JobId`: same key = stays as it is (even `running`); different key = if it was running, `Cancel` and the job does not restart until the executor reports (`finished` answers `Discarded{key}`: the result is true for the old key, the caller puts it in the cache); if it had an output it becomes `stale`, otherwise `waiting`/`ready`. Vanished jobs: `Cancel` if running, event `cancelled`, they disappear from the view.
The problems of `flow::check` block (`blocked`) the jobs of the instance concerned, the rest continues. A cycle gives the `plan` event and leaves the jobs as they were.
- Going back to an already tried parameter: the caller calls `cached(id)` when the `plan_key` is in the cache and the job goes to `reused` without running.

## Choosing the job
`next(limits{slots, mem_mb}, estimate) -> Vec<JobSpec>` starts NOTHING: two `next` in a row give the same jobs until `started` is called. Order: first the elements already started (with a `running`/`done`/`reused` job), by decreasing depth; then the order of the plan inputs; then the order of the steps in the file. A job that does not fit in `slots` or `mem_mb` (estimate in MB given by the caller) or that shares an exclusive resource (`set_resources`, e.g.
`dataset:<path>`) with one running or already chosen is skipped, it does not block the following ones. When paused `next` is empty. A job with a cancelled run not yet reported does not start.

## Cards (aggregate per node)
`nodes()` gives a `NodeView` per plan instance: worst state (`error > refused > blocked > skipped > running > stale > paused > ready > cancelled > waiting > reused > done`; all `reused` = `reused`, mixed = `done`), `frac` = average (`done`/`reused` = 1, running without a fraction = indeterminate → `None`), `parte/di` = finished/total jobs, `ms` = sum of the `done` jobs (time is measured by the caller; no remaining time).

## `flowlive/1` events
`events_since(seq)` = JSON array of the events with greater `seq`; `seq` grows by 1 from 1, `rev` = number of `update`s so far (0 at creation). A `job` event at every change of state, key or time of a job, a `node` event at every change of the card, a `plan` event for an unschedulable plan. The log keeps the last 8192. Schema: `docs/schemi/flowlive-1.json`; test `tests/test_flowlive_schema.py` on the events recorded in a case. Written with `json::Out`, without serde.

## Shared cases
`crates/mzlab-core/tests/data/sched_cases.json`: steps (as data), plan, calls and the answer of each (`expect`); `sched_cases.rs` replays them. Regenerate the answers with `MZLAB_UPDATE_SCHED_CASES=1 cargo test -p mzlab-core --lib flow::sched` and reread the diff (the answer is the contract). They serve the `.wasm` parity.

## `flow::execute` on top of the scheduler
`run.rs::execute` creates `Sched`, asks `next` (one job at a time, unlimited memory), `started`, runs with `Runner::run` on `workers` threads (pool with `Condvar`; on wasm in sequence), reports `finished` and keeps the results by `JobId`. The inputs of a job are read from the results of the upstream jobs (the driving port takes only the element of that job).
At the end the record is written as before, level by level (`levels`), with `settle`: same `prov/1` for any finishing order. A `many` output of a per-element job has the key `instance.port[input-name]` (`[name#k]` if one job gives more than one).
`Job::item` stays the position (view, `Lineage`); `item_name` is the plan input, `item_root` the root of the file name. The per-element file is called `instance-<root>.ext`: root = input name without extension, unsafe characters turned into `_`, plus 8 digits of the SHA-256 of the whole name if two inputs have the same root. The CLI cache key does not contain the element position.
Tests: `flow/run_tests.rs` (10 seeds × 1 and 4 threads), `crates/mzlab-feat/tests/flow.rs`, `flow_cache_tests.rs`.

## Progress inside jobs (`mzlab_core::pace`)
- `Pace::new(sink).at(done, total)` forwards `(done, total)` at most once per whole percent, never backwards; the last call is `(total, total)` (an empty job gives `(0, 0)` once). The bytes produced do not depend on the callback.
- Who uses it: `flow_centroid::job_with` (scans written by `mzml_to_centroids_with`), `flow_pace::build_index_with` (scans decoded by the reader, `Scans`, or bytes read of an mzML, `Counted`; `build_index_of` is the case without callback), `flow_base::write_mzml_with` (scans written by `Conversione::scrivi`), `mzlab_feat::trace::detect_with` (peaks examined, per block). Tests: `flow_centroid_tests.rs`, `flow_pace_tests.rs`, `lr_fullscan.rs`.
- In the browser the worker of `TP_Mine/files/feat-worker.js` sends `{id, progress:[done,total]}` and the pool forwards it to `opts.onStep({phase, name, done, total})`; the `feat` `.wasm` calls back the 6th argument of `detect_file_to` (`progress(done, total)`, `Pace`; `analyse_with`, `analyse_file_with`, `detect_to_with` carry the callback) and the pool forwards it as `{job, frac}` to the scheduler (`progress`).
- `FileRunner` passes to `job_with`, `build_index_with`, `detect_with` and `write_mzml_with` the callback of `Gate::pace` (empty outside a live run): `convert_job`, `index_job`, `detect_job` and the centroid use it, `msn_graph` does not. `align_job` passes to `run::align_to_par_progress` the callback of `Gate::pace` (`slabs::align_and_fill_progress`: one unit per slab, per weak-level file and per filled file; the total is announced before the first); the in-memory alignment counts one unit plus the stages after.
- The site client is `flow/lazy/flow-live.js` + `flow-live-jobs.js` (`docs/agenti/flow-web.md`): detection and alignment go through the `feat-worker.js` pool, MSn goes through the `msn` executor (below), `cancel(JobId)` is `pool.cancelJob`.
- Whole reads of `.mzfeat` on the site (`wholeRead` of `flow-live-jobs.js`: `table.filter`, `export.table_csv`, `export.mztab`, `tp.link`, `tp.dig_lr` and the steps after `tp.link` from `flow-web-tp.js`): before reading, `fs.size` of the pool (op `fs.stat`) gives the bytes and 16 MB + 2 × the bytes are needed (copy of the worker and of the .wasm). Beyond the safe budget the job waits for `permission.memory` if it enters `alto` (`holdRead`, asked once at Run), otherwise it is `error.memoryBudget` phase `readTable` with the numbers; nothing is read beforehand. Test: `e2e_flow_web_export.py`.
- Known limit: the `table` module receives the whole table (no offset-read API from OPFS); `tableOf` (`features.group`, `table.stats`, `table.drift`) reads it without `wholeRead` because those steps pass their budget to the .wasm. To revisit when a real `.mzfeat` reaches it.

## Live run on the computer (`crates/mzlab-cli/src/flow_live.rs`)
- `LiveRun::start(text, flow::steps(), inputs-folder, job, workers)` runs on the same `Sched` and the same `flow::work` loop as `execute` (`Hooks`: `live`, `reuse`, `leave`, `begin`, `end`); the threads are `default_workers()` (cores minus one, at most 4; 0 = answers only).
- `set_identity` takes effect only at the following `update`, even with an unchanged plan: `send` of `flow-live.js` calls `update` when a fingerprint changes (an index going from "loading" to ready).
- `update(text)` changes the plan: jobs with the same `plan_key` continue, those with another key and running see their flag raised and end with `err.flow.cancelled` at the next chunk (no half-written file: the writers remove the output), then run again; it answers with the same text as `api/flow/sched/update`.
- `act`/`ask` are `sched_act`/`sched_ask` (same bytes as the site), `cancel_all` pauses and raises all the flags, `events_since` and `event_lines` give the `flowlive/1` events, `finish` gives the `Run` of `record` (same `prov/1` as `flow run`).
- Reuse: every finished job stays in `kept` under its key with date and size of its files; a key that comes back (even of a discarded job) is `reused` if the files are still the same, otherwise the job cache (`flow_cache`) takes it back. Files have the label's name: a run with another parameter rewrites them.
- `start`/`update` receive `claim` (predicate of the jobs the threads do not take), then `release` / `lend(id, Lend::{Running(frac), Done(file), Failed})`: jobs that someone else runs (the desktop conversion queue); the threads do not take them (`leave`).
- `mzlab-cli flow run --events` (not with `--json`/`--dry-run`: code 2) prints one `flowlive/1` line per event while running; folder and `prov/1` are those of `flow run`. Desktop: routes `flow/live/<op>` (`crates/mzlab-desktop/src/flow_live.rs`), see `rust-desktop.md`. Tests: `cargo test -p mzlab-cli --lib flow_live`, `cargo test -p mzlab-desktop --lib flow_live`.

## Tabs and status bar (`flow/lazy/flow-live-{view,card,bar,desktop}.js`)
- **State in a single view**: `F.liveView` keeps the last `flowlive/1` event of every node and job (from `flow-live.js` and `flow-live-desktop.js`; an older `rev` falls) and gives every tab the state word: "Waiting..." (blue, "hold" mark; also `blocked` for `input.missing`), "k of n files · NN %", "working", "done in X s", "Up to date (nothing changed)", "Settings changed: press Run", "This step failed", "Needs the desktop app", "Allow more memory: Run now", "Fix the plan first", "skipped", "paused", "cancelled": a short line (max 28 characters, the card has fixed height).
- **Special words**: `look` also gives `title`, the whole sentence (tooltip and `aria-label`; for errors the text of `F.message`). The "Centroid spectra" tab at `done`/`reused` says instead `F.liveView.centroidWords` (on the card "7 files ready", "2 of 3 files ready", "Reading 7 files..."; in the `title` "7 files ready (already centroided)", "... (centroided earlier)", "... (1 centroided earlier, 1 already centroided)").
- **No computation in JS**: fractions, counts and times arrive in the events; never a remaining time. A tab made of several steps shows the node in the worst state (same order as `nodes()`).
- **Status line** (`F.liveCard`, born in `flow-canvas.js`): mark + word + `role="progressbar"` bar (`aria-valuenow` only if the fraction is known, otherwise indeterminate stripes). The mark has a shape per state (color is added), "Settings changed" has a dashed border, errors a solid border; colors are CSS variables, with `prefers-reduced-motion` and `data-a11y-reduce` every animation stops. The tab has `data-live=<state>` and the `aria-label` ends with the word. It redraws once per frame on the `flow:live-view` event, without moving the focus.
- **"Files" table** (`F.liveCard.files`, at the bottom of the step panel): one row per job with a file (file, state, share, time, memory `≈ N MB` from the web runner estimate, "–" elsewhere); hidden until there are rows.
- **Bar** (`F.liveBar`): "Auto-run" (`#flx-live-on`, on by default, `localStorage` `mzlab.flow.live`; off = the plan is not followed and nothing starts), "Pause"/"Resume" (appears only with active jobs; `aria-pressed`; running jobs finish), "Run now" only if a node is `blocked` for `permission.memory`. `#flx-live` announces only the state changes of the nodes, at most one every 2 s, and never covers a warning with a button. 40 px targets with a coarse pointer.
- **App** (`F.desktopLive`): "This computer" uses `flow/live/*` instead of `flow/run` + `flow/progress`: Run starts the session (`start`), reads `events` every 300 ms (1.5 s at rest), sends `update` at every change while Live is on, waits until nothing is left to do (`nodes`) and asks `finish` for the `prov/1`. A file the app does not hold is excluded and reported. There is no "Run now".
- Tests: `e2e_flow_live.py` (words and bar during the run, "Settings changed", "Files" table from the keyboard, axe), `e2e_flow.py` (app with fake `flow/live/*` routes: `flow_desktop_fake.js`), `e2e_flow_avvio.py` (no live module in the first draw: they are in the LATE list of `flow-tool.js`).

## Per-file centroiding (`spectra.centroid` in the base plan)
- **Plan**: `F.BASE[0]` (group "Import data") is `spectra.centroid` then `index.mzidx`; tab "Centroid spectra" (`F.NAMES`). `F.addCentroid` (`flow-fix.js`) puts it before the index and connects the index to its output; the plan check never inserts a step silently.
- **Plan without the node**: if Data has files in profile mode (`ST.files[].spectrum_mode`) and the plan has no `spectra.centroid`, "Issues" (`F.profileIssues`) offers "Centroid the profile files" or "Run on profile anyway" (writes `profile: "as_is"` in the plan: `exportPlan`/`importText` carry it, so it enters `plan_sha256` of `prov/1`). Until one is chosen, the detections of those files are `blocked` with `by: input.profile` (`x.waitingProfile`, unblocked by `settleIndex`).
- **On the site** (`flow-live-jobs.js` `centroid`): file already centroided → `cached` job (tab word: "already centroided"); profile file with its `<name>.cen.mzidx` in OPFS (`listIdx` reports it in `cen`) → `cached`; file read as a vendor file → `rb.nativeCentroidIndex` (existing route `lr_index_cen`, no computation in JS); a profile mzML without `.cen` stays `blocked` for `platform.computer` (the app or the CLI centroids it).
- **Detection**: the detection of a profile file reads the `.cen.mzidx` (`x.source`), never the profile index; the file's mode enters the scheduler identity (`index:mode`).
- **Tab and table**: the tab says "k of n files centroided, m already centroided" (`F.live.centroidNote`); the "Files" table has the "Mode" column (`F.live.modeOf`).
- **Record**: `Outcome.file` → `Activity.files` → `prov/1` key `files` (per file name: `via` = `centroided` | `passthrough`, with `fwhm` and `threshold` used and `fwhm_basis` = `measured` | `fallback` | `given`) and `run-report/1` `steps[].files`; `via` at activity level stays the memory mode. The job cache (`flow_cache.rs`) keeps `file_info`. Tests: `cargo test -p mzlab-cli --lib flow_centroid` (mixed series), `e2e_flow_live.py` (section C).

## MSn steps in the mixed plan (site)
- Even a plan of only MSn steps runs in the scheduler (Run retries the MSn jobs in error). `spectra.msn_graph`, `msn.library_export`, `msn.table_export` and `spectra.match` (`tree`) are scheduler jobs with a single job per step (`item = None`): the `msn` executor of `flow-live-jobs.js` calls `F.webMsn.one` (`F.webMsn.run` is the same code without the scheduler, test reference); the fraction counts only real stages (library read 0.2, engine answered 0.8), never an estimate on the infusion open in Data (`F.webMsn.infusion`).
- **MSn results cache** (`flow-live-jobs.js`): the text of every MSn job is in OPFS `mzlab/flow/msn/<key>.json` (`{name, text}`), key = SHA-256 of the `plan_key` (step, parameters, program version, open infusion, upstream jobs) plus, for `spectra.match`, the text of `msnlib.json` (the user's library is not in the plan). Key found = `cached` job (tab "reused"), no request to the engine; infusion closed = never from the cache. `index.json` keeps the last 32 keys, the oldest are deleted. Test: `e2e_flow_msn.py`.
- The `plan_key` follows that file: `build` of `flow-live.js` connects the `source` port of the MSn steps to the infusion, not to the first index of the series. The text stays in OPFS (`mzlab/flow/<id>.*`) and `live.run` gives it in `files` like the MSn runner; a finished job is not redone until the key changes, after a restart it is redone (no cache in OPFS). `spectra.match` with another algorithm stays `blocked` for `platform.computer`.
- If the infusion is not open in Data the job ends in `error` with `err.flow.msn.open`; there is no fraction, the tab says "working".

## Traps
- `finished` for a cancelled or vanished job answers `Discarded{key}`: it must be cached, not used. A result for an unknown `JobId` gives `Unknown`.
- `set_identity` and `set_resources` hold from the next `update` or `next`; resources stay tied to the `JobId`.
- The registry is copied in `Sched::new` (no borrow); steps with an absent version or unresolvable parameters have a `blocked` job with `plan.problem`.

## In the site `.wasm`
- The scheduler runs in the `rotte` module (`mzlab-rotte-wasm`, loaded on first request; not in the `hr` modules: the `limit_hr` margin cannot hold it, and no ceiling is raised), in one object per session (`thread_local`) behind the function `flow_sched(op, body)` (`crates/mzlab-rotte-wasm/src/lib.rs`, `mzlab_core::flow::sched_route`). The engine worker (`rust-worker.js`, op `lr_flow_sched`) serves it at the route `api/flow/sched/<op>` (`statRoute` in `lr-map.js`); an error is `{error_key, params}`.
- Operations (JSON text in and out; a job is `{"instance","item"}`): `new` (`{plan, registry, version, identities}`), `drop`, `update`, `next` (`{slots, mem_mb, mb:{"instance|entry":estimate}, mb_default}`), `started`, `progress`, `finished` (`{job, result:{ms}|{error_key,params}}`: `"accepted"`, `"discarded:<key>"` or `"unknown"`), `cached`, `block`/`unblock`, `retry`, `pause`/`resume`, `jobs` (state of every job; one in `error`/`refused` also carries `error_key` and `params`), `nodes`, `events` (`{since}`), `rev`, `set_identity`, `set_resources`.
- The registry is not compiled into the engine: it arrives as the JSON of the `step/1` steps from the page's plan (`F.registry`) and is reread by `mzlab_core::step::registry_from_value` (ports, parameters, algorithms, presets, where a step runs; the texts for people stay empty). The engine is the same one that already serves `api/flow/command`: the page does not wait for it.
- **Record of a failed run**: `F.live.run` writes `prov/1` and `run-report/1` even when a job of the base chain ends in `error`/`refused`, before refusing the run: `F.webProv.record` accepts the finished jobs (`done`, `reused`, `error`, `refused`, `blocked`, `skipped`), sends the failed job with `error_key` and `params` from `jobs` and skips those not run; `record_prov` reads errors with parameters (in the given order), `warnings` and `file` of the reports like `execute` (`run_web_tests.rs`, `flow_record_tests.rs`: alignment of mixed-polarity files equal to `flow run`).
- Parity: `tests/test_flow_sched_wasm.py` builds the engine for Node and `tests/flow_sched_nodo.js` runs the cases of `sched_cases.json` (SKIP without cargo, wasm-bindgen or node); the native tests of `sched_route` and of the registry reread are in `flow/sched_route_tests.rs`.
- Engine measurement (wasm-opt -Oz): 1 610 624 B before, 1 678 813 B with the scheduler and the registry reader, against the ceiling 1 703 936 (remainder 25 123 B).
- **Reuse before Run** (app): `flow/reuse {plan, files?}` → `{reused, compute}` in steps, from the cache keys alone of `mzlab-flow/out` (`mzlab_cli::flow::probe_plan`, `crates/mzlab-cli/src/flow_out.rs`: a job with no key in the cache fails with `err.flow.probe.miss`, the steps after a miss count as to compute, the index is not rewritten); `flow-desktop.js` asks it 600 ms after every edit and at the end of the run.
- **User lists** (app, `flow/lazy/flow-liste.js`): a parameter with `x-liste` (`liste/1`) is edited in a table in the inspector (add and remove rows, "Import CSV", "Export JSON", SHA-256 of the list), without windows; every edit goes through `flow/liste {kind, rows|csv}` → `{rows, csv, sha256, json}` or `{errors}` (`mzlab_feat::lists::route`) and only a valid list enters the plan (its CSV, so the plan text and the cache key change). On the web the text field remains. Test: `e2e_flow_liste.py` (route simulated in `flow_desktop_fake.js`).
