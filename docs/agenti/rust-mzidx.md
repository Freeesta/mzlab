# Rust engine: `.mzidx` builder and pool

Sections of `rust.md` (the other engine topics live there).

## `.mzidx` builder (`mzlab-core::mzidx`)
- `build(&ScanTable, pass, &mut dyn Output, budget)` (`build_mzml`, `build_mzml_to_vec`) writes the format of `docs/agenti/mzidx.md` byte for byte like Python's `mzidx.build`. `ScanTable` is what the caller already knows (level, polarity, RT and TIC of each scan, the JSON rows of the table, `source` and `run` in JSON, `hr1`): Rust decodes only the peaks, with the callback parsers `mzml::parse`/`raw::parse` (never `read`); `Spectrum.wide` keeps the file's 64-bit intensities, so the `f8` arrays are identical to Python's.
- Memory: the first pass keeps the peaks while they fit in `budget / 4` (default 64 MB); beyond that, with a scratch file it writes them there (file decoded once), without one it drops them and the file is re-read once per "round" of 1-unit m/z buckets that fits in `budget / 2` (stable sort by bucket, writes at offsets). With the scratch a round holds at most `ROUND_MAX` (32 MB): larger rounds are not faster (`measurements-rust.md`). A failed `try_reserve` gives `error.memoryBudget`, never a panic. `Output` = write at offset (file, `Cursor<Vec<u8>>`, browser callback).
- Bucket too dense: a single bucket fits in a round as long as its sections cost at most `budget * 2`; beyond that, `error.memoryBudget` with phase `indexPeaks` (`stima_mb` = the bucket, `budget_mb` = that limit). The first pass checks it every 256 scans with a lower bound (12 B per peak for MS1, 24 for the other levels) and refuses as soon as the lower bound exceeds the limit: the rest of the file is not read (mzML: `late::Fermabile`), kept or written to the scratch. Test: `tests/mzidx_dense.rs` (early refusal, same bytes at 24-512 MB with and without scratch).
- Tests: `tests/mzidx_parity.rs` (examples and synthetics of `tools/mzidx_reference.py` against Python's file, large and small budget; skipped without python3/numpy, `MZLAB_GOLDEN_STRICT=1` fails). Time and memory: `cargo run --release --example mzidx -- FILE.mzML [OUT] [BUDGET_MB]`.
- Profile spectra from the `.mzidx` (`profspec.rs`, `idxwalk.rs`): `scan_points` marks the requested scans in a dense table (`u32::MAX` = not requested, on equal position the last wins); `each_peak_for` reads `pos` in blocks of 16 384 peaks and, for m/z and intensity, only the stretch between the first and the last peak of a requested scan (a block with none is not read). The `point_step` fallback walks the m/z array alone (`each_mz`) with last m/z, minimum gap and count per scan. Bit-for-bit tests: `tests/profile_sparse.rs`.
- Measurement (synthetic LR, 40 MB, 2000 scans, 1.98M peaks, release, N=21, median [min-max]): first `/api/spectrum` 28.8 [28.3-35.5] → 11.9 [11.8-13.1] ms; with the 20 central scans sparse (fallback) 111 [93-122] → 15.9 [13.1-19.3] ms and peak heap 32.5 → 1.45 MiB (counting allocator, one thread); call with the step already known unchanged (6-8 ms), because here every block contains peaks of the requested scans.
- **Rows of a reader without text** (`Rows::lettore`, `scantable/inert.rs`): the row is built from the scan, also with the producer's TIC (`SpectrumExtra::tic`, every `.wiff` scan) and the base peak (`precursori`); the TIC is the one `spectrum` re-reads from the text of `spectrum_head` (`{}` of an f64 gives back the same bits, every NaN becomes `f64::NAN`). Precursors, `scan_params`, `cv_params` and accessions in id, filter or userParam go through the text. Test: `crates/mzlab-core/tests/scantable_reader_extra.rs`; `prepare_lettore` with TIC, 25 000 scans: 400 → 205 ms.

## Worker pool for the `.mzidx` (site)
- **The pool is the only builder** (`createPool` in `rust-worker.js`, operation `lr_index`): no Python fallback. Correctness is proven (arrays identical to Python: byte-for-byte parity in `mzlab-core`, `e2e_lr` and `e2e_mzidx`); speed does not block (Federico's rule): 20 LR files −38 %, 15 HR files −16 % time and +31 % peak memory (`measurements.md`).
- `mzlab-wasm::build_mzidx(size, read, write, livelli, polarità, rt, tic, righe, source, run, hr1, budget_mb)`: same `.wasm` as the engine (`BlockReader` on `File.slice`, write at offset with a callback); errors in JSON with a key (`error.memoryBudget` if `try_reserve` fails).
- `mzlab-wasm/src/natives.rs` (+ `natives_engine.rs`: `Natives`, `Engine::native_*`): the producer's files read as they are (`native-reading.md`). `native_samples(nomi, dimensioni, read)` (samples of a set; `read(member, offset, length)`), `build_mzidx_native(nomi, dimensioni, read, c, nome, centroidi, write, budget_mb, fase)` (`.mzidx` v2 of one sample; `fase(n)` reports 1 fingerprint, 2 scans, 3 chromatograms), `native_to_mzml(..., c, centroidi, sink, progress)` ("Download .mzML").
  `Engine::native_attach(slot, ds, ...)` makes the routes of that slot read the reader and the `guscio` (`Src`; at most 4 open readers, 32 MB of shells), `native_metodo(slot)` gives `method/1`.
  The `.wasm` is built WITH `simd128` (one binary, no fallback; minimum browsers in `wasm-potential.md` §8; a browser without SIMD128 shows `error.noSimd`, `simd128` check in `capacita.js`); `.cargo/config.toml` gives the memory flags and `+simd128`.
- `idx-worker.js`: short-lived worker, ONE file; it writes the file `<nome>.mzidx.part` in OPFS (`createSyncAccessHandle`) and ends; the pool closes it (the WASM memory goes back to the system). Messages only, no `SharedArrayBuffer`.
- `idxpool.js` (`createPool`, tested by `tests/test_idxpool.py` with a fake Worker): N workers = min(`hardwareConcurrency` − 1, 4), at least 1, at most 2 on iPad/phone (`poolSize`); files start in queue order (the upload order); a dead worker is replaced and its file goes back to the head of the queue once, the second time it fails (`reason: "crash"`, the upload answers `err.engine.index`).
- Budget of a builder (`builderBudget`): its share of the engine budget with the pool's workers, `engine budget / (workers + 1)`, between 32 (iPad/phone) or 64 MB and 512 MB; the native side (desktop, CLI outside Flow) uses `budget_auto::index_budget` (share of `native_auto_mb` with `min(cores − 1, 4)` builders, between 64 MB and 1 GB). It only raises the densest bucket allowed; the bytes do not change.
- Pool memory (`errorKind`): `error.memoryBudget` without `fase` (reservation failed) halves workers and budget until the pool holds still, retries once and shows a single note `error.poolLowered` (budget log in Diagnostics, reason `indexPool`); with `fase` (builder estimate) the file fails at once with its numbers in its row (`error.memoryBudgetFase.indexPeaks` names the limit and the desktop app), with no note, no re-read and no reduced pool.
- Not memory: a fixed limit (`error.fixedLimit`), a stopped helper (`error.workStopped`) or a failed read (`err.file.read`) make the file fail at once (`errorKind` = `error`), with no reduced pool.
  A worker that does not start (module or `.wasm` not loaded) gets a second try on a new worker; on the second failure the pool is off for `offMs` (5 s, `unavailable()`) and files fail with a keyed error, then the next job tries again (never off for the whole life of the page).
- In the CLI (`flow_pace::build_index_with`) the mzML is read only once for the SHA-256: `flow_set::digest` (provenance of the inputs) remembers it by path, size and modification time (`known_sha`) and `prepare_with` receives it with the `probe` (`upload::probe`, first and last 64 KB only); if the file changed or was not measured, `prepare` re-reads everything. Measurement (36 mzML, 1 worker, step `index.mzidx`): 4.1-4.5 s → 3.0-3.2 s; the `.mzidx` files stay identical.
- Scan table of an mzML without an index (`scantable::read_walked`): 1 MiB blocks; a spectrum that leaves the block restarts the block from its beginning, so the file is read only once (`tests_walk.rs`: 20 MB read against 43 before); tags are searched in 32-byte blocks (`first_byte`, vectorized also in wasm) and the blocks read are reused without zeroing them (`Source::give`). Measurement in `measurements-speed.md` (PERF-HOTPATHS-1); mzML files with an index use `read_listed`.
- Damaged index (`idxcheck`): on opening every array of every section must end inside the file and every key must name a section (`check`); when reading the arrays (`Index::arrays`) every `scan_id` must be in the scan table (`scan_ids`, skipped by `open_lean`, which does not read it), and `idxwalk` refuses a `pos` outside `n_scans`. Otherwise `error.badIndex`, never a panic. Tests: `crates/mzlab-core/tests/idx_corrupt.rs`.
- Per-section sums: every metadata section has the optional key `crc32` (CRC-32 IEEE of the bytes of each of the 10 arrays, order of `NAMES`, 0 for an empty array), written by `mzidx/crc.rs` (`Summed` sums the bytes as they arrive in order; an array written out of order leaves the section without the key) and by the Python builder with the same bytes. An index without the key opens and reads without a check; a missing name or a non-numeric value is `error.badIndex` on opening, a number that is not a CRC-32 is one on reading.
- Sum check (`idxcheck::sum`): applies to arrays read whole: `rt`, `scan_ids`, `sumint`, `bp_mz`, `bp_inten` (`Index::arrays`), `fence` (`fence_blocks`) and, in the Python reader, also `tic`; `mz`, `inten`, `pos` read in blocks are not checked.
- Sums in the Rust reader: the CRC is bit by bit (no table, no flate2) and the sums live in `Index::crcs` (10 `f64` per section, NaN if absent), not in `Section`: the feature modules stay under the size and memory caps. Tests: `crates/mzlab-core/tests/idx_crc.rs`, `tests/test_mzidx_crc.py`.
- Cost of the f32 (`<f4`, MS1 only of an HR file): every stored m/z is within half an f32 ulp of the file's value, i.e. 2^-24 relative = 0.0596 ppm at most (measured 0.059 ppm); the `<f8` sections keep it exact (below 0.001 ppm). For HR screening it is a rounding below one ppm of the candidates, not a loss of peaks. Test: `crates/mzlab-core/tests/idx_mz_precision.rs`.
- Reuse of an index already built (`idxsource`): where it is reused for an mzML (desktop start `lr_boot`, warmed files of the site `claim` in `rust-scalda.js`) `Index::built_from` compares size and `probe` of the file with `source`, and a file replaced with the same name, size and date has its index rebuilt; vendor samples (`natsame`, `nat_same`) and the live run of the CLI compare name, size and date. Tests: `crates/mzlab-core/tests/idx_source.rs`, step "same size and date" of `tests_e2e/e2e_riscalda.py`.
