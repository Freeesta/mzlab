# Motore Rust: costruttore e pool del `.mzidx`

Sezioni di `rust.md` (le altre cose del motore stanno lì).

## Costruttore del `.mzidx` (`mzlab-core::mzidx`)
- `build(&ScanTable, pass, &mut dyn Output, budget)` (`build_mzml`, `build_raw`, `build_mzml_to_vec`) scrive il formato di `docs/agenti/mzidx.md` byte per byte come `mzidx.build` di Python. `ScanTable` è ciò che sa già chi chiama (livello, polarità, RT e TIC di ogni scansione, righe JSON della tabella, `source` e `run` in JSON, `hr1`): in Rust si decodificano solo i picchi, con `mzml::parse`/`raw::parse` a callback (mai `read`); `Spectrum.wide` tiene le intensità a 64 bit del file, così gli array `f8` sono identici a Python.
- Memoria: se tutti i picchi stanno in metà `budget` (predefinito 64 MB) restano dalla prima passata e il file si decodifica una volta; altrimenti la prima passata conta i picchi dei 10000 secchi di 1 unità di m/z e il file si rilegge una volta per «giro» di secchi che sta nel budget (ordinamento stabile per secchio, scrittura a offset). `try_reserve` fallito → `error.memoryBudget`, mai panico. `Output` = scrittura a offset (file, `Cursor<Vec<u8>>`, callback del browser).
- Prove: `tests/mzidx_parity.rs` (esempi e sintetici di `tools/mzidx_riferimento.py` contro il file di Python, budget grande e piccolo; salta senza python3/numpy, `MZLAB_GOLDEN_STRICT=1` fallisce). Tempo e memoria: `cargo run --release --example mzidx -- FILE.mzML [OUT] [BUDGET_MB]`.

## Pool di worker per il `.mzidx` (sito)
- **Il pool è l'unico costruttore** (`createPool` in `rust-worker.js`, operazione `lr_index`): niente ripiego Python. La correttezza è provata (array identici a Python: parità byte per byte in `mzlab-core`, `e2e_lr` e `e2e_mzidx`); la velocità non blocca (regola di Federico): 20 file LR −38 %, 15 file HR −16 % di tempo e +31 % di memoria massima (`misure.md`).
- `mzlab-wasm::build_mzidx(size, read, write, livelli, polarità, rt, tic, righe, source, run, hr1, budget_mb)`: stesso `.wasm` del motore (`BlockReader` su `File.slice`, scrittura a offset con una callback); errori in JSON con chiave (`error.memoryBudget` se `try_reserve` fallisce).
- `mzlab-wasm/src/nativi.rs` (+ `nativi_motore.rs`: `Nativi`, `Engine::native_*`): i file del produttore letti come sono (`lettura-nativa.md`). `native_samples(nomi, dimensioni, read)` (campioni di un insieme; `read(membro, offset, lunghezza)`), `build_mzidx_native(nomi, dimensioni, read, c, nome, centroidi, write, budget_mb, fase)` (`.mzidx` v2 di un campione; `fase(n)` segnala 1 impronta, 2 scansioni, 3 cromatogrammi), `native_to_mzml(..., c, centroidi, sink, progress)` («Scarica .mzML»).
  `Engine::native_attach(slot, ds, ...)` fa leggere alle rotte di quello slot il lettore e il `guscio` (`Src`; al più 4 lettori aperti, 32 MB di gusci), `native_metodo(slot)` dà `metodo/1`.
  Il `.wasm` si costruisce SENZA `simd128` (un solo binario per tutti i browser, nessun ripiego: la misura non mostra differenze, 9,1 s con contro 9,3 s senza su 20 file LR); `.cargo/config.toml` dà solo i flag della memoria.
- `idx-worker.js`: worker a vita breve, UN file; scrive in OPFS (`createSyncAccessHandle`) il file `<nome>.mzidx.part` e finisce; il pool lo chiude (la memoria WASM torna al sistema). Solo messaggi, nessun `SharedArrayBuffer`.
- `idxpool.js` (`createPool`, provato da `tests/test_idxpool.py` con un Worker finto): N worker = min(`hardwareConcurrency` − 1, 4), almeno 1, al massimo 2 su iPad/telefono (`poolSize`); i file partono nell'ordine della coda (quello dell'upload); un worker morto è sostituito e il suo file torna in testa alla coda una volta, la seconda volta fallisce (`reason: "crash"`, l'upload risponde `err.engine.index`); `error.memoryBudget` dimezza i worker e il budget (64 MB, 32 su iPad), ritenta una volta e mostra la nota `error.memoryBudget`;
  `.wasm` assente o non caricabile = pool spento per la sessione (`unavailable()`), l'upload fallisce con un errore con chiave.
