# mzFinder .wasm modules: merged modules and ceilings
A module's record is the `misura` field of its `tools/moduli/<nome>.toml` plus the before → after line in the PR body (`wasm-tetti-misure.md`); this file has modules, ceilings and build rules.
A .wasm ceiling (bytes after `wasm-opt -O3`) lives in ONE place: the module's `tools/moduli/<nome>.toml` file (field `tetto`, read only by `tools/moduli.py`; the build scripts, `tests_e2e/lib.wasm_cap` and `tools/ci_wasm_dimensioni.py` also read it from there, and the `wasm_opt.sh` lines of the workflows call `moduli.py --tetto`).
"Under the ceiling" = strictly under: a module equal to its ceiling fails, both in `tools/wasm_opt.sh` (`-ge`) and in `tools/moduli.py` (`misura >= tetto`); `--controlla --base` also prints a `NEW`/`REMOVED` line for an added or removed module (not a FAIL: the owner decides).
The rule: a ceiling rises by at most 10 % per new function and never in a workflow or a script; `python3 tools/moduli.py --controlla --base origin/main` lists every changed ceiling and fails beyond 1.10 times the base value.
`wasm-opt` is binaryen version_133 (`tools/wasm_opt.sh`, three SHA-256 values pinned in the script).
- **Missing wasm-opt**: without binaryen 133 or `wasm-opt@1.4.0` from npm, `tools/wasm_opt.sh` errors (`MZLAB_WASM_OPT_STRICT=1`, `env:` of `pages.yml` and its copy `tools/lab/qqq-pages.yml`, `sito-rust.yml`, `release.yml`) and gives a single warning in local builds and in `notte.yml`. The binaryen tarball is in `actions/cache` (key `binaryen-version_133-<os>`) in the jobs that build the `.wasm` files; the script reuses it only if the SHA-256 is the pinned one, and a different SHA after the download remains an error (`tests/test_wasm_opt_chiuso.py`).
- **HR group**: a single `wasm-feat/hr/` module (crate `mzlab-feat-wasm` with the features `detect,proofs,finder,finder_edge,finder_msn,flow_ms2`) instead of five; the manifest entries `feat`, `proofs`, `finder`, `finder_edge` and `finder_msn` point to the same file and the workers (`feat-worker.js`, `tpmine-worker.js`) instantiate it only once. `untargeted` and `interp` stay separate. `hr` does not carry the Flow planner: the recipe and lineage of a job are written by `rotte` (`worker-flow-web.js`), `flow_job_meta` reads the text (−110 KB).
- **`wasm-opt` steps of `hr`**: `hr` uses `@estesi` (`--converge` and `--const-hoisting` on top of `@motore`, `tools/moduli/hr.toml`): 1 711 946 → 1 691 715 B (−20 231 B, gzip +1.0 KB), identical outputs (SHA-256) and hot-path timings within noise.
- **Timing measurement of `hr`**: `python3 tools/bench_hr.py [--extra "<steps or @set>"]` builds `hr` once, applies `@motore` alone and with the extra steps, alternates the two builds (ABBA, median and spread of `detect`, `preview`, `align`, `proofs` in Node on a synthetic series) and compares the SHA-256 of the outputs; it exits with 1 if a median is slower than the limit (3 %) or if an output changes. `--merge-similar-functions` (−14 KB) was discarded: +3.5…+7.3 % on the paths.

- **`wasm-opt` steps**: `tools/wasm_opt.sh` applies `-O3` (ONE variable, `livello`, for every module; `MZLAB_WASM_OPT_LEVEL` is only for `tools/banco_wasm.py` for the `-Oz` baseline: variants `site`, `site_o3`) and, with `@estesi`, the readers list (`build_lettori_wasm.sh`); with `@motore` (`--low-memory-unused --reorder-functions --strip-producers`) that of engine and libraries (workflows and `tools/build_feat_wasm.sh`). `--converge` and `--const-hoisting` are not in the engine.
- **`--low-memory-unused`** is valid because rustc links with `--stack-first`: data starts at 1 MiB (`tests/test_lettori_wasm.py`).
- **No relaxed SIMD**: never (CPU-dependent results, site = app byte for byte): forbidden by `tests/test_guardie_regole.py`.
- **Reader JSON texts**: `mzlab-lettori-wasm` writes its JSON texts with `mzlab_core::json::Out` (`json_text.rs`), without `serde_json` (only in the tests, which compare it with the old output on boundary values); the chromatogram with points (`cromatogramma`) is written by `mzlab_lettori::json::chromatogram_json`, the same as the app (`natregistro`).
- **Sorting**: every new `sort*` of `mzlab-lib`, `mzlab-feat` and `mzlab-feat-wasm` uses `SortC` (`sortc_by`, `sortc_by_key`, `sortc`; `tests/test_guardie_regole.py` rejects std `slice::sort*` outside `untargeted/` and `legacy/`) (`sortc_by`, `sortc_by_key`, `sortc`); std `slice::sort*` costs 2-10 KB of `.wasm` per instance and stays only where `mzlab-core` marks it (hot path, or order with NaN that `sortc` does not preserve).
- **Index sorting by f64 key**: `specpeaks::order_by_f64` (`#[inline(never)]`, std stable `slice::sort_by` with `total_cmp`, ascending or descending) is the only copy in the engine, used by `merge_unit`, `pad_zeros`, `subtract_hr`, `rt_groups` and `sticks`.
- **One copy of the generic cold code**: the engine's `Mzml` has a single reader (`Src`, also in `mzml_metodo`), the header of the written mzML is `mzmlwrite::head_text` (not generic over `Write`), `/api/spectra` of a profile is generic only in the scan reading (`profile_picks`, `Picks::json`), `in_spans` takes a `&mut dyn FnMut`, `Error::with` moves the common part into `with_text` (`#[inline(never)]`).
- **Generic hot code**: `mzml::parse_loop`, `Index::walk`, `decode_block`, `mzidx::Sec<f32|f64>`, `binned_cells` and `Accorpa` stay one instance per type (per XML event, block or cell). Instances are counted from the names section (`tools/twiggy_wasm.sh`) before and after `wasm-opt -O3 -g`; the real gain is measured only with the build (`tools/wasm_opt.sh`): `wasm-opt` already merges many copies and the removed copies also change the inlining of the callers.
- **Std sorting in hot paths**: where sorting is per point or per peak (`mzidx.rs`, `mzidx_order.rs`, `mapgrid.rs`, `maptiles.rs`, `specpeaks.rs`, `specdiff.rs`, `rawreader/extra.rs`) std `slice::sort*` stays with `#[allow(clippy::disallowed_methods)]`: at `opt-level = "z"` it is ~2× faster than `sortc` (2.5 M elements: 249 vs 542 ms). Elsewhere `sortc`, which does not panic on a comparison that is not a total order and saves ~2.5 KB of `.wasm` per call site.
