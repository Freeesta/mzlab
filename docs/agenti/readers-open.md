# "aperti" module: open formats (mzML with numpress, gzip mzML and mzXML, mzXML)

Family `aperti` (`crates/mzlab-lettori/src/open/`, feature `aperti`, cap in `tools/build_lettori_wasm.sh` (copied in `tests/test_lettori_wasm.py`), `.wasm` in `wasm-lettori/aperti/`). Reader contract and on-demand loading: `readers-module.md`, `extending.md`.

## mzML with MS-Numpress (`open/mzml_numpress.rs`)
- `numpress.rs` (`mzlab-core`, only with `estesi`, outside the engine): decodes `Np::{Linear, Pic, Slof}` (MS:1002312/13/14, and the zlib forms 1002746/47/48 via `of_accession`); `decode(np, byte, atteso)` limits the values to `atteso` (8 M if 0) and gives `err.file.numpress`; `decode_text` adds base64 and bounded zlib (`error.memoryBudget` beyond `max_bytes`); `plain_base64` writes plain f64; the encoders `encode_linear/pic/slof` serve the tests.
- Slof takes `exp` and `ln` from `libm` (encoding, decoding and fixed point): the `.wasm` already has them from there, a native build would take them from the system library, which differs in the last bit (about one `exp` in ten), and the 64-bit intensities of a slof mzML would differ between site and app. Test: `slof_gives_the_bits_of_libm_on_every_face` (`numpress/tests.rs`).
- Final half byte (linear and pic): an odd number of half bytes ends with 0x0, as the reference C++ writes and expects (an 0x8 would be reread as one more value). On reading a lone 0x0 is padding; a lone 0x8 is the last value, a zero, except when the declared length is already reached (padding of the files mzLab used to write with 0x8).
- Tests of the final half byte: reference bytes in `numpress/tests.rs` (`REFERENCE`, the CI gate); optional check outside the CI: `python3 -m pytest tools/numpress_pyopenms.py` rereads with pyopenms every array of `convert --compression smallest` of every family.
- The engine rejects numpress with `err.file.numpress`: all six accessions of `numpress::ACCESSIONS` (with and without zlib), in the engine's spectra and chromatograms (`mzml/build.rs`) and in the chromatograms read from the index (`mzmlhead::decode`); read as plain floats the zlib forms gave false values or an infinity (test `crates/mzlab-core/tests/numpress_engine.rs`). The module rewrites the arrays of ONE spectrum/chromatogram as plain f64 (`open/np_rewrite.rs`: `riscrivi`) and gives them to `mzml::parse` / `Mzml::chromatogram`.
- `ENTRY` `id "mzml-numpress"`, `.mzml`: `riconosci` wants `<mzML` and one of the six accessions before the end of the first `</spectrum>` (reads 64 KB, then doubles up to 16 MB: the m/z array can be plain and long while only the intensities are numpress; `Fiducia::Si`). `apri` makes a single pass over the offsets (`scantable::read`), checks `start < end ≤ size` and `Limiti::ok_entries`; `scansione(c, k)` reads only the bytes of `k`.
- `cromatogrammi`/`cromatogramma`: like `mzmlhead.rs`, on the rewritten bytes of the chromatogram; the type is that of `source::kind` (a SIM ion `SIM SIC …` or `SIC …` is `Sic`, as for `mzml::read`; test `a_sim_ion_has_the_kind_of_the_engine`). The tag scanner, the spectrum parameters and the reading of the original header are in `open/mzml_header.rs`.
- Cut copy (the file does not end with `</indexedmzML>` or `</mzML>`): whole scans are read, cut ones are counted by `missing`; if the cut took away the file's TIC, `cromatogrammi` lists a `TIC` made from the `totIonCurrent` of each whole scan, in file order (unit "number of detector counts"), and `cromatogramma("TIC")` gives it; a whole file keeps only its own chromatograms. Test: `crates/mzlab-lettori/tests/open_numpress_cuts.rs` (every cut length).
- `testata_mzml` = original header (instrument, serial, components, sources with SHA-1, software, date; the SHA-1 of the whole file is computed only if the original names no source) with mzLab as converter; `metodo` repeats the `mzLab method/1` document if the file carries it, otherwise `{}`.
- Page: `LETTORI_FAM.aperti` (`lettori-famiglie.js`) and `LETTORI_MOD.variante` (`lettori-modulo.js`: reads 64 KB and doubles up to 16 MB, like `riconosci`) recognise the numpress mzML; `numpressToNat` (`shell.js`, `NATIVO.numpress`) opens them as a native sample of a single member and the engine indexes them from the module's reader (`famigliaEsterna` gives "aperti"), without rewriting the mzML; "Download .mzML" converts it at that moment (`nativeToMzml`). Desktop and CLI already read it natively.
- Tests: `crates/mzlab-lettori/tests/open_numpress.rs` (synthetic files; builders in `tests/common/`), `open_numpress_hostile.rs` (hostile cases and real data if `MZLAB_DATI` is set), units in `numpress/tests.rs`, `tests_e2e/e2e_lettori_modulo.py` (numpress mzML and zlib twin).
- Known limits: the spectrum cvParams that the rewrite does not know become userParam "ACC name" in the rewritten mzML; `dataProcessing`, `referenceableParamGroup` and `scanSettings` do not pass (`raw-not-extracted.md`).

## gzip mzML (`open/mzml_gz.rs`)
- `ENTRY` `id "mzml-gz"`, `.mzml.gz`: `riconosci` wants the gzip magic bytes and `<mzML`/`<indexedmzML` in the first 4 KB decompressed (`Fiducia::Si`). `apri` decompresses EVERYTHING in memory (`gunzip::Membri`, fixed cap `Limiti::byte`, `error.fixedLimit` beyond; broken gzip `err.file.zlib`; a truncated gzip with some bytes already inflated opens with the spectra it has and `Lettore::missing` counts the others) and passes the file to `mzml_numpress::apri`, which also reads plain arrays.
- Gzip broken at the head: a `.mzml.gz` shorter than the magic bytes or that inflates nothing is `Fiducia::Forse` and `apri` rejects it with `err.file.zlib`, like the site's inflate (`rust-carica.js`); `tests/gz_borders.rs` compares the keys of app and site.
- `ENTRY_MZXML` `id "mzxml-gz"`, `.mzxml.gz` (only feature `tutte`: app and CLI, not the site's module, which has no margin under the cap): same decompression, then `mzxml` reads it.
- On the site (`gz-flusso.js`, `shell.js` `gzToEngine`) the gzip is inflated as a stream in the engine's worker: `Gunzip` of the `.wasm` (`mzlab_core::gunzip`, a write-mode `GzDecoder` per member, 1 MiB pieces read and 64 KiB at a time) writes to OPFS with `archivio.js` `putStream`, never holding the whole file. A `.mzML.gz` becomes `files/<name>.mzML.gz.part`, then `files/<name>.mzML` (`putGz`, `lr_put` with `gz`), and goes on like a loaded mzML; the space asked for is the gzip's ISIZE (`gzRoom`).
- Members and padding (`mzlab_core::gunzip`, same on site and app): several gzip members in a row are one stream; zero bytes after a whole member (file padded to a block) close the stream, as in GNU gzip; a non-zero byte after those zeros is `err.file.zlib` (`gunzip::tests`, `tests/gz_borders.rs`).
- A `.mzXML.gz` on the site is inflated into `conv/gz~<page>~<case>.mzXML` (`lr_gunzip`, `gunzipTo`), which the module reads as `.mzXML`; the temporary file is removed when the conversion is done. At startup (`lr_boot`) the free `.gz.part` and the `gz~` of pages whose lock `mzlab-gzses:<page>` is free disappear. "Cancel" stops the stream at the next piece and removes the partial file.
- Without streaming (`?gz=memoria`, OPFS without sync handles) or with MS-Numpress arrays in the inflated head (`GZFLUSSO.numpress`) the `.mzML.gz` goes to the module, inflated in memory; above 50 MB compressed the row says `load.note.gzMemory`. A `.mzXML.gz` without streaming is rejected with `err.file.gzStream`. Chromium's `DecompressionStream` stops at the first member of a multi-member gzip: that is why the inflate is in Rust.
- Tests: `crates/mzlab-lettori/tests/open_gz.rs`, `mzml_variants_tests.rs` (CLI), `crates/mzlab-desktop/tests/gz_mzml.rs` (site mzML = original byte for byte; TIC, BPC, XIC, spectra and scans of the site = app), `tests/carica_worker_node.mjs` (`putGz`, `gunzipTo`, `gzRoom`), `tests_e2e/e2e_gz_flusso.py`.

## mzXML (`open/mzxml.rs`)
- `ENTRY` `id "mzxml"`, `.mzxml`: `riconosci` wants `<mzXML` in the first 4 KB (`Fiducia::Si`). The reader decodes by itself (no rewrite into mzML): `mzxml_index.rs` (offsets), `mzxml_scan.rs` (one scan), `mzxml_header.rs` (header, `method/1`, `Header`). The engine does not read it: `LETTORI_FAM.aperti.soloModulo` contains `.mzxml`, so the page always sends it to the module.
- Scans: `mzxml_indice::righe` makes a pass in 1 MB blocks that finds every `<scan ` (`Limiti::profondita_ok` on nesting, `ok_entries` on the count); the `<index>` at the end of the file is not used (the headers of all scans are read anyway). A scan = the bytes from one `<scan ` to the next (the nested MS2 of mzXML 2 begin after the end of the MS1).
- Ruined copy: a scan with a NUL byte (never in XML: zeroed block) or, in a file without `</msRun>`, cut before `</peaks>`/`</scan>` stays out of the index. `Lettore::missing` = max(declared − read, discarded), declared = max(`scanCount` of `<msRun>`, `<offset>` of the `<index>` after the run): site ("N missing" row) and CLI (`warn.file.truncated`) say it as for mzML.
- Scan: `num` (id `scan=N`), `msLevel`, `polarity` (+/−), `retentionTime` (ISO duration `PT…S`, in minutes), `totIonCurrent`, `basePeakMz`, `filterLine`, `scanType` (SRM/MRM/CRM prepended to the filter if the line does not say it, so `SrmFromScans` finds the transitions), `centroided` (otherwise that of `dataProcessing`), last `precursorMz`. Peaks: `precision` 32/64, big-endian, `m/z-int`, zlib or not, base64.
- Peak limits: the declared length (`peaksCount`, for `Limiti::ok_entries`) is the cap of the values (`error.memoryBudget` beyond) and of the inflated zlib (`error.fixedLimit` beyond, also with `peaksCount="0"`); without `peaksCount` the zlib inflates at most up to `budget::undeclared_inflate` (32 times the compressed bytes, at least 1 MB); a truly broken zlib stays `err.file.zlib`; other precisions, orders or compressions give `err.file.xml`, broken base64 `err.file.base64`.
- The TIC of the index is `totIonCurrent`; if it is missing for some scans, `indice` and the `TIC`/`BPC` chromatograms (MS1, or all scans if there are none) compute it from the peaks. `intestazione(k)` gives every attribute of `<scan>`, `<precursorMz>`, `<peaks>` and every `<nameValue>`; `extra_mzml` carries SIM, window (`startMz`/`endMz`), collision energy and precursor attributes as userParam "mzXML …".
- `metodo(c)`: `origin` (format `mzxml`, name, SHA-1, bytes), `instrument` (manufacturer, model, software), `operator.utente`, `ms.source.tipo` (`msIonisation`); `fields` = every attribute of every header element (`mzxml:<path>`, in file order), `identity` for the operator and for file names that are paths. `testata_mzml`: model, components (source, analyser, detector), software, source file (`parentFile`) with SHA-1 (this file if missing), `mzLab method/1` in the `<run>`.
- Tests: `crates/mzlab-lettori/tests/open_mzxml.rs` (32/64 bit × zlib × with and without `<index>` × nested, TIC/BPC, SRM, method), `open_mzxml_hostile.rs` (false index offsets, huge `peaksCount`, inflating zlib, broken base64, nesting, truncated files; the three real mzXML of `dati/formati/aperti/mzXML/` open with the expected scans and sorted peaks, and against the mzML next to them if present, with `MZLAB_DATI`), `tests_e2e/e2e_lettori_modulo.py` (an mzXML opens in the Data view).
- **Input only**: mzXML is read and converted to mzML; mzLab does not write mzXML and will not have a writer (the only encoder is the tests' one, `crates/mzlab-lettori/tests/common/mzxml.rs`).
- Not verified (no reference mzML next to the real files): m/z, intensity, RT, precursor and polarity against msconvert's mzML.
