# mzFinder in the browser: `crates/mzlab-feat-wasm` and `TP_Mine/files/feat-worker.js`

The WASM bridge of the L1-L9 pipeline of `mzlab-feat` (formats and levels: `mzfeat.md`).

## The crate
- Offset outputs (contract in `memory.md`): `detect_file_to(read, size, name, recipe, write, progress?)`, `align_series_to(files, read, sizes, recipe, write, budget_mb, spill?, weak?, progress?)`, `build_evidence_to(table_read, table_size, hypotheses, minutes, parent_mz, parent_rt, recipe, write, budget_mb)` write with `write(offset, bytes)` and return JSON `{bytes, sha256}`; with a small `budget_mb` `align` works in slabs and the proofs stream (same bytes), or the error is `error.memoryBudget`.
- `align_series_to` and `align_series` go through `series_js::series_into` (one copy of the alignment in the module): the series recipe reads each scan table once (`series_recipe`), gap filling reopens each index with `Index::open_lean` (header and meta, table neither read nor analysed).
- `cache.rs`: `file_key(read, size, name, recipe)` (`file_key_untargeted` in the `untargeted` `.wasm`) returns `"<sha256>.<Recipe::file_hash>"` from the head of the `.mzidx` after `recipe_for` (empty without sha256; only detection changes it); `check_stored(bytes, key)` returns the source name in the meta if sha256 and fingerprint match (`error.badMzfeatf`, `error.newerFormat`; the `u…` fingerprint of untargeted is not in the meta).
- The versions that return the bytes are for small series and tests. The `native --budget-mb N` example and `tests/feat_wasm_node.js --budget-mb N` use the offset outputs.
- `mzlab-feat-wasm` (cdylib + rlib) exposes with wasm-bindgen: `detect_file(read, size, name, recipe)` → `.mzfeatf` bytes; `align_series(files, read, sizes, recipe)` → `.mzfeat` bytes; `run_hypotheses(files, read, sizes, rules, structure, parent, parent_rt, recipe)` → `Hypotheses` object (`registry_json`, `tried`, `found`); `build_evidence(table, hypo, minutes, parent_mz, parent_rt, recipe)` → `.mzfeat` with the `evid` section; `preview_file(read, size, recipe)` → preview JSON (below); `version()` and `crate_version()` (version of `mzlab-feat`, the one `cancello.json` names).
- `read(k, offset, len)` is a JS function that returns a `Uint8Array` (in the worker: synchronous OPFS handle); `NaN` = no value for `parent_rt` and the minutes. `recipe` is JSON `{"polarity":1|-1|null,"mode":"ion"|"family"}` plus the six numbers of the panel, all optional: `floor`, `min_height`, `min_points`, `ppm` (alignment and fill), `rt_tol` (alignment and fill), `fill` (false = no L6; the recipe text changes only if false). Errors: JSON `{error_key, params}` (`error.badRecipe` and the keys of `mzlab-feat`).
- The series indexes (`open_one`, `open_all`; `open_one` also for `qc.mass_accuracy`, one file at a time) call `read` through `blocks_js::Blocks` (`mzlab_core::blocks::BlockCache`, 3 blocks of 256 KB growing up to 1 MB along in-order reads): each call to JS and to the OPFS handle costs about 0.2 ms almost fixed and the engine asks for a few KB at a time (detection, weak candidates, filling); the bytes read are the same.
- Blocks are born at the first miss and die with the index; indexes opened together (`open_all`: series recipe, hypotheses, Dig, TP) keep a single 64 KiB block each, with no read-ahead (`blocks_js::shape`; the proofs peak after the hypotheses stays in the guard of `tests/test_guardie_memoria.py`); alignment and filling open one file at a time.
- `.wasm` split by features: `detect` (L1-L5), `proofs` (L6-L9), `finder` (470 KB, with `mzlab-feat/chem`: `classify`, `formula_info`, `transformations` and the HR Dig with its tree, `src/finder.rs` on top of `mzlab_feat::legacy`, folder `wasm-feat/finder/`) and `finder_edge` (220 KB: `identity_graph`, `polarity_pairs`, `origin_evidence`, `src/finder_edge.rs`, loaded by the worker only at the first of these routes).
- `finder_msn` (320 KB, MSn tree, library and product localization, `src/msn.rs`, folder `wasm-feat/finder-msn/`, `finder_msn` entry of the manifest), loaded only with an MSn file in the series.
- On the site the five HR `.wasm` (`detect`, `proofs`, `finder`, `finder_edge`, `finder_msn`) are ONE merged module, `wasm-feat/hr/`: the five manifest entries name it and the workers instantiate it once; group cap in `docs/agenti/wasm-caps.md`. `tools/build_feat_wasm.sh` writes `wasm-feat/manifest.json` with the SHA-256 values.
- `memmap2`, `zstd-sys`, `libz-sys`, `cc` do not appear in the WASM graph (check in `rust.yml`).
- Graph `.wasm`, on request: `crates/mzlab-feat-grafo-wasm` (manifest `grafo`) exposes `analyse(smiles)` → `grafo/1` `{formula, atoms, groups, fragments, cuts}` (or `{error_key, params}`), `positions(smiles, transform, peaks_json, tol, ppm, positive)` → `posiz/1` JSON (`positions.md`), `positions_prior(..., reatt_json)` (with `prior`), `version()` (`mzfeat-grafo/10`); the page loads it when the user gives the SMILES of the parent, and passes `fragments` to `run_hypotheses` and `groups` to the rule preconditions.
  For the Drawing (`drawing.md`): `labels(request)` → `label/1`, `cut(request)` → `cut/1`, `mech(request)` → `mechanism/1`, `sel(request)` → `selection/1`, `link(request)` → `link/1` (`drawing-menu.md`).
- Dig progress: `finder_progress(kind, phase, done, total)` (`finder`) and `finder_lr_progress(phase, done, total)` (`finder-lr`) → JSON `{phase, label, done, total, frac}` from `mzlab_feat::legacy::progress` (phase weights and tests in the module); `"null"` for an unknown phase; for `align` with `total` > 1 the label is a percentage ("Aligning the series: 40 %").
- For the Drawing the same `.wasm` exposes `fragments(molfile, a, b)` → `frag/1` JSON (the two sides of the bond between atoms `a`,`b`, or of every bond outside the rings) and `partial(molfile, delta)` → `parz/1` JSON (partial structure with the Δ, `level` 3; see `drawing.md`).
- `chem` is a feature of `mzlab-feat` (default); `mzlab-feat-wasm` turns it off (`default-features = false`), so the proofs `.wasm` stays byte-for-byte identical; whoever adds a `.wasm` that depends on `mzlab-feat` and does not use `chem` does the same. Test: `tests/test_feat_grafo_wasm.py`.
- `legacy` (the Dig, the LR Dig, the rules) is also default; it sits on top of `finder_base` (fragmentation and MSn trees, MS2, identities, series), which also comes with `interp`. Bridges that do not ask for it take `mzlab-feat` with `default-features = false` (`mzlab-chem`, graph, table, `mzlab-ops`): among the `.wasm` only `hr` and `finder-lr` compile it. The inclusion list row is in `finder_base/inclusion.rs`. Check: `cargo tree -e features,no-dev -p <bridge> -i mzlab-feat`.
- `mzlab-core/src/sortc.rs` (re-exported as `mzlab_feat::sortc`): compact stable sorts for all code that goes into a `.wasm` (the std `slice::sort*` weigh 4-5 KB per type): `by`/`by_key`/`ord` for `Copy` data, `any_by`/`any_by_key` for the rest. In `.wasm` code do not use std `sort*` or `collect()` into `BTreeMap`/`BTreeSet` (it brings its own sort): `insert` in a loop.
- `src/run.rs` holds the generic pipeline over `ReadAt`, shared with the native example `examples/native.rs` (reference: prints `name sha256` of each file). Gap: the family edges are not in the `.mzfeatf`, `build_evidence` passes them empty.

## The HR Dig in Rust: `mzlab_feat::legacy` (`finder` `.wasm`)
- `legacy::dig(files_json, parent_json, serie_evid, registro, open)` reads the `.mzfeat` series with `evid/1` (columns = sample, blank and control files of `files_json`, in that order) and the `hypotheses/2` registry; the candidates are the identities with `totale` > 0, sorted by points (up to 500 rows), as in gate G1. Parent row: that of the `tp/1` view if the table has a non-empty one, otherwise the largest summed area within 5 ppm of the [M+H]+.
- For each candidate: formula, ppm and derivation from the hypothesis, `delta` from the parent, kinetics (`legacy/kinetics.rs`), consensus MS2 from the DDA scans inside the peak of each file (`finder_base/ms2.rs`) and three-component similarity with the parent MS2 (`finder_base/similarity.rs`).
- `score` = `totale`; `components` = points of each proof type divided by the maximum it gives (`weights`, from the points table); level 4 = formula of a hypothesis with the mass proof, 3 = also the MS2 proof, 5 = the rest; `tree`, `calibration`, `region`, `margin` and `localization` are added by the worker with an MSn file (below), otherwise `null`; the level does not use `n_groups` of the localization.
- `legacy/out.rs` writes the JSON of `api.run` (`summary`, `engine: "rust"`), of `api.detail` (negative id for a hidden product) and the inclusion list. `rt_map` writes `rt_align`; `Cand::confirmation()`/`pred()` bring the prediction to 1 with ≥2 shifted fragments (no level 3); `network.rs` writes `mass_network` with the rules of `FinderDig.set_rules` (`network_pred.rs`: two-step predecessors or with correlated MS2); `hidden.rs` (rows, `ion` mode) and `hidden_fam.rs` (parent fragments with no row, `family` mode, XIC from the `.mzidx`) add negative-id products.
- `finder_base/fragtree.rs` = `fragtree._two_level` (with `FormulaSpace`, `molgraph.substructures` up to 4 cuts and `mask_smiles` in `fragtree/mol.rs`): `of_dig` (`legacy/fragtree_dig.rs`: reads the Dig) gives the tree of the DDA MS2 of the parent (`FinderDig.frag_tree`); without an MSn file or a parent MS2 the note of `fragtree.hr`; `frag_tree_compare` gives the empty answer (without an MSn file there is no `localization`).
- `finder_base/identity.rs` (+ `identity/{pairs,values,hyp}.rs`, edge proofs in `finder_base/edge.rs` + `edge/stats.rs`, `iimn` tables in f64): `identity_graph` (mzMine groups and edges, computed edges, neutral-mass hypotheses per component) and `polarity_pairs`; `finder_base/edge/report.rs` = `report_evidence`: `origin_evidence` (`{report, pol}` → proofs of the report "where does this ion come from?" of `origine.js`, without label).
- **Routing** (`TP_Mine/files/tpmine-worker.js`): every call goes to a Rust module; files received with `put` stay in `held` (source of the `.mzidx` that `finder-idx.js` builds if OPFS does not have it); `default_transformations` is the text saved in `tests/golden/finder_transf_default.txt`, copied into the worker (`tests/test_tpmine_worker.py`); a call the engine cannot serve answers with an error.
- `run` goes to Rust if the files are HR (plus at most the MSn file of the standard), all with `.mzidx`, with any transformation list; the MSn file leaves the list given to the Dig: `finder_plan` (LC files, minutes, formula, `grafo/1` of the SMILES) → pool of `feat-worker.js` (`detectAll`, with the `.mzfeatf` kept in memory by name, size and date of the `.mzidx`; `align`; `hypotheses` with `structure`; `evidence`) → `finder_dig`; then `detail`, `inclusion_csv`, `frag_tree`, `frag_tree_compare` from that `FinderDig`; `msn_tree` gives `null`.
- The parent adduct (`[M+H]+`, `[M+Na]+`, `[M+NH4]+`, `[M-H]-`, `[M+HCOO]-`) decides ion formula and m/z (`series::parent`); with a negative adduct the worker passes the recipe `{"polarity":-1}` to detection, alignment, hypotheses and proofs.
- The "RT (min)" field of the parent (`parent.rt`, empty = automatic) picks the parent row closest in RT and passes `parentRt`/`parentMz` to hypotheses and proofs; empty, the row is the one with the largest area in the time-0 files (otherwise in all).
- Before the proofs the worker asks `finder_parent` (parent row in the aligned table: `legacy::parent_peak`) and passes m/z and RT to `evidence`: so the products view (`tp/1`) and the kinetics read against the parent. The Dig leaves out the rows that the ISF gate of the view marks `ST_ISF` (in-source fragments of the parent or of a product), lists them in `isf_hidden` and writes it in the warnings.
- A site without `wasm-feat/` answers "mzFinder engine not built". Test: the Flow e2e tests that use the engine.

## The MSn tree in Rust: `mzlab_feat::finder_base::msn` (`finder_msn` `.wasm`)
- `msn::scans_of(index)` reads the MSn scans of the `.mzidx` (a scan shared by several sections once only); `msn::build_tree(scans, ion, smiles, calibrate)` (nodes, parents and consensus from `mzlab_core::msntree_build`, subformula formulas of the precursor, calibration `msn/space.rs::fit`, atom sets `msn/atoms.rs`); SMILES missing, unreadable or too large = tree without structure (`subs` `None`), no error.
- `msn/library.rs::build(tree, dda)` (node precursors and peaks ≥ 1 % of the DDA MS2 of the parent); `msn/localize.rs` (`classify_fragments`, `site_log_likelihood`, `localize`, `default_groups`, `describe`; group names "anello" and "catena").
- `msn/json.rs`: `summary` (`MsnTree.summary`), `tree_summary` (`_tree_summary`), `calibration`, `library`, `localization` (`detail.localization`); `msn/json/frag.rs`: `frag_tree` = `fragtree._hr_msn`, `compare` = `fragtree.compare_hr`. Parity ≤ 1e-9 in `tests/legacy_parity.rs` (`msn` cases of the golden; the order of sites at equal log-likelihood is free).
- `src/msn.rs`: `finder_msn(read, size, parent_json)` → `FinderMsn` (`build_tree` with the [M+H]+ ion of the parent, calibration `auto`, library if the structure is there) with `msn_tree`, `calibration`, `set_parent_ms2(mz, rel)` (rebuilds the library with the DDA MS2), `localize(id, neutral formula, mz, rel, tp_mz)` (ion = neutral + H; `null` without structure or with an element the parent does not have; kept by `id`), `frag_tree`, `frag_tree_compare(id)`.
- **Worker**: with a file of type `msn` the worker loads `finder_msn` after `finder_dig`; in the `summary` it puts `tree`, `calibration` and, for rows with MS2 and formula, `region` and `margin` (2 decimals); `detail` receives `localization` and `ms2.evidence`; `frag_tree` and `frag_tree_compare` come from the MSn tree, `msn_tree` from `FinderMsn`. The first parent MS2 seen in a `detail` rebuilds the library.
- Not ported: the library masses as in-source fragments (`isf_masses`, `isf_coincident`) and the library in the IIMN families (`iimn.family`): the Rust Dig does not have these parts. `isf_hidden` is ported (`legacy/hidden.rs`: ratio of the areas; the apex shift against the parent is not tested).
- Test: `crates/mzlab-feat` tests (a synthetic MSn file from `msn_synth.py`: tree, calibration, `frag_tree`, `frag_tree_compare` and the localization of synthetic products).

## The table `.wasm`: `crates/mzlab-feat-table-wasm`
- Views, report and exports of the table, loaded by the page only when a table is shown or exported (the pipeline engine does not carry it). Built by `tools/build_feat_wasm.sh` into `wasm-feat/table/`, with the `table` entry in `manifest.json` (SHA-256), same weight limit as the others.
- Functions: `table_view(read, size, campioni_json, spec)` → `{digest, rows (id), factors, counts}`; `table_report(..., table_sha256)` → `report/2`; `table_qc(read, size, campioni_json, spec)` → `qc/2`; `table_samples({files:[{name,sha256}]})` → `samples/1` proposed from the names; `tp_table(read, size, campioni_json, righe_json)` → `tptab/1` (the variant with `gruppi` for ≥ 2 conditions is only in the desktop: see `mzfeat-tp.md`; the `table` `.wasm` weighs 219 750 B after `wasm-opt -Oz`)
  - `export_table(..., polarita, kind)` with `kind` `full`, `full_mzmine`, `quant`, `csv_semicolon` (feature sheet as text with `;`), `mztab` (mzTab-M 2.0, `export_mztab.rs`) or `xlsx_rows` (the same sheet as JSON rows `{hojas:[{nombre, filas}]}` that the page packs into xlsx)
  - `table_row(read, size, samples, id)` → `row/2`; `table_row_traces(..., id, index_read, index_sizes, ppm)` → `row_traces/2` (`row.rs`).
  - `export_ms2(..., polarita, kind, index_read, index_sizes)` with `kind` `mgf` or `sirius`; `version()`, `crate_version()`. `spec` is the JSON `{"normalize":..., "filter":[...]}` (empty = whole table, areas as measured); `read(0, offset, len)` reads the `.mzfeat`, `index_read(k, offset, len)` the `.mzidx`. Errors as in the others (`{error_key, params}`).
- The steps are in `src/core.rs` over any `ReadAt`; the `table` example writes them natively and `tests/test_feat_table_wasm.py` (with `tests/feat_table_node.js`) compares the bytes with the `.wasm`.

## The native crate `mzlab-ops` (`crates/mzlab-ops`)
- Pure Rust, without `wasm-bindgen`/`js-sys`: what orchestrates the engines for a transport lives here.
- The bridges (`*-wasm`) keep the JS glue and re-run the moved modules under the old paths: no JS export changes.
- Fixed layout: `src/lib.rs` declares `run`, `op`, `vfs` (the last two are filled by other chats).
- `run/table/` (`core`, `filterspec`, `pol`, `rows_mgf`; feature `table`) comes from `mzlab-feat-table-wasm`.
- `run/feat/` comes from this crate: `run` (with `run::meta`), `run_evid`, `run_tp` (with `dig`), `estimate`, `interp` [`table`], `run_estimate` and `family` and `cache` [`detect`], `state` [`proofs`], `untargeted` [`untargeted`].
- The features (`table`, `detect`, `proofs`, `untargeted`) have the same names as the bridge, which turns them on with its own; `mzlab-feat` has no default features, so a `.wasm` does not receive `chem` that it did not have.
- CLI and desktop depend only on `mzlab-ops` (not on `mzlab-feat-wasm`) and import from `mzlab_ops::run::{table,feat}`; the JS exports of the mixed modules are in the `*_js.rs` files of the bridge (`run_meta_js`, `cache_js`, `family_js`, `estimate_js`, `interp_js`, `run_tp_js`, `run_dig_js`).

## The worker (`TP_Mine/files/feat-worker.js`)
- One file, two roles.
- Page side `createFeatPool({workerUrl, wasm:{feat,proofs}, size, notify, onProgress})`: `detectAll(files, recipe)`, `align(stored, paths, recipe)`, `hypotheses({...})` and `evidence({...})` (L7 and L8-L9 in two workers that close at the end of the work; the hypotheses state passes as bytes of `Hypotheses.state()` / `load_hypotheses`, `crates/mzlab-ops/src/run/feat/state.rs`), `proofs({...})` (the two in a row), `budgetMb` (working memory of a step, 0 = 192 MB), `fs.write/read/exists/remove` (archive worker, writes `nome.part` then `move()`), `cancel()`, `resume()`.
- Supervision (like `idxpool.js`): a worker that dies (killed or `.wasm` trap) is recreated, the work restarts once with `notify("tpmine.feat.restarted")`; at the second death the work is refused with `error.featWorker`. With `sha256` in the manifest the downloaded `.wasm` is verified (`error.featWasmHash`).
- The `.mzidx` files are read from OPFS (`mzlab/idx/<nome>.mzidx`) with synchronous handles opened per operation; a handle of a just-dead worker is awaited for up to 2 s.
- i18n keys of the messages (`tpmine.*` in `TP_Mine/js/40_tabui_testi.js`, `error.*` in `mzlab/web/lang/en/errors-a-m.js`; read by `32_pipeline.js` with `I18N.t`): `tpmine.feat.restarted`, `tpmine.feat.cancelled`, `tpmine.feat.degraded`, `error.featMemory`, `error.featState`, `error.featWorker`, `error.featWasmHash`, `error.featNoHypotheses`, `error.featFailed`, `error.badRecipe`; `tools/controlla_i18n.py` also counts `TP_Mine/js` and `TP_Mine/files` as use.

## L1-L9 in the browser (`TP_Mine/files/feat-run.js`)
- `runFeatPipeline(pool, {files, recipe, parent, save, onPhase})` runs the phases in order: `detect` (L1-L3 of each file, one job per file in parallel), `align` (L4-L6 in one worker), `hypotheses` (L7) and `proofs` (L8-L9), in two workers, only with a parent, `save` (`.mzfeatf` and `.mzfeat` in `mzlab/feat/` from the archive worker, each as soon as its phase is done).
- `detect` goes through the cache `mzlab/feat/cache/<key>.mzfeatf` (also with `save=false`; `pool.op` for `file_key`/`check_stored`): the entry with the same name in the meta is read, the other files are detected and written; an entry of a newer format is neither used nor touched; `pool.fs.trim` keeps the folder within 512 MB; `clearDetectCache(pool)` = "Clear cache" of the panel. `timings` "detect": `cached` = files from the cache.
- If memory refuses hypotheses or proofs (`error.featMemory`) the run returns the table without proofs (`degraded` = phase) and warns with `tpmine.feat.degraded`; if it refuses detect or align it throws the error with `params.files`, with the phases already saved. It returns `{stored, table, evid, tried, found, registry, timings, degraded}`; `timings` has one row per phase (ms, per-file times, linear memory peak of the `.wasm` in MB).
- The `.wasm` APIs have the granularity of the phases above; the desktop `feat/*` routes do not exist.
- Measurement (4 CPUs, 4 workers; 13 Orbitrap `.mzidx` of ~82 MB, 147 hypotheses): detect 18.3 s, align 6.2 s, proofs 13.6 s, total 39.4 s, `.mzfeat` with `evid` equal to the native one; peak per worker: detect 100 MB, align 158 MB, proofs 204 MB.
- `tests_e2e/e2e_feat_run.py` prints the timing table; with `MZLAB_FEAT_MZIDX=<folder>` and `MZLAB_FEAT_PARENT=FORMULA:MZ:RT` it uses real files (persistent profile) and checks total < 60 s and detect ≤ 128 MB; `e2e_feat_cache.py` tests the cache.
- `tests_e2e/e2e_feat_na.py` (series cropped in RT by `tools/feat_ritagliata.py`, also with `rt_range`): the `CELL_NA` cells are there and `.wasm` and native give the same bytes.

## Tests
- `tests/test_feat_wasm.py` (+ `tests/feat_wasm_node.js`): `.mzfeatf`, `.mzfeat` and `evid` of the WASM have the same SHA-256 as the native on the synthetic `piccolo` series.
- `crates/mzlab-feat-wasm/tests/degenerate_detection.rs`: estimate, `detect` and `detect_weak` on degenerate HR indexes (no peak, one scan, intensities all zero or negative, a repeated m/z, one compound, different counts per scan) give bytes, equal in two rounds and with the spare cores busy (`spare::busy`); NaN/inf in the intensities are refused at load with `err.file.nonFinite`, never a panic.
- `tests_e2e/feat_site.py` builds the `.wasm` and the server for the two e2e.
- `tests_e2e/e2e_feat_worker.py`: builds the `.wasm`, pool on OPFS, killed worker and trap, archive without `.part`, sizes.

## "Pipeline" panel (`TP_Mine/js/32_pipeline.js` = `window.PIPE`, opened from "Pipeline..." in the `#unt` window)
- Panel details (form `PIPEFORM`, `params.rs`, gate, `PIPER`/`PIPEV`, recipe `PIPEREC`, steps 5-8, `family_record`, weak tier, `target/join.rs`, close isomers): `docs/agenti/mzfeat-wasm-panel.md`.
