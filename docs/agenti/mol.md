# The `mol/1` record (`crates/mzlab-mol`)

Chemical structure as data: one molecule (one component) with atoms, bonds in Kekulé form, stereo elements with a state, advanced-stereo groups and optional layers. Reasons and prohibitions: "Why and what not to do" at the bottom; transformations: `docs/studi/STRUTTURA_DATO_TRASFORMAZIONI.md`. The crate depends only on `serde`, `serde_json`, `sha2`; on the site the `.wasm` `molkit` links it; `mzlab-feat` uses it with the features `record` (off in every `.wasm`), `check` and `sub` (substructure search; on in `molkit`). Existing outputs and formats do not change.

## JSON schema
Compact, fixed field order (that of the types in `model.rs`), empty fields omitted; same molecule and same atom order = same bytes.
- `format`: always `"mol/1"`. `atoms[i]`: `{el, iso, chg, rad, h}` (symbol H-Og; isotope 0 = natural; `h` = implicit H, an H with an isotope is an atom). `bonds`: `{a, b, o}` with `a < b`, `o` in 1,2,3 (Kekulé, aromaticity is not written), no duplicates.
- `stereo`: `{t:"tetra", c, refs, implicitH, par, status}` or `{t:"db", a, b, refs, cfg, status}`; `status` is `defined` or `unknown`. No element = the centre is not stereogenic; `unknown` = it is one but the configuration is not known (`{"t":"tetra","c":6,"status":"unknown"}`, without `refs`/`par`/`cfg`).
- `tetra` defined: `refs` = neighbours of the centre in ascending order (3 or 4); `par` `cw`/`ccw` = the sense in which the other `refs` appear when viewed from the first; with 3 `refs` the implicit fourth place (H if `h` = 1, `implicitH` true; lone pair if `h` = 0, `implicitH` false) comes last. It is the RDKit `CHI_TETRAHEDRAL_CW/CCW` convention on the order of the `refs`.
- `db` defined: `refs[0]` neighbour of `a`, `refs[1]` neighbour of `b` (not the bond itself), `cfg` `cis`/`trans` between the two (never E/Z: CIP labels are computed). The `a`-`b` bond is double.
- `groups`: `{kind: abs|and|or, atoms}` (`and` racemate, `or` relative), atoms ascending, only defined `tetra` centres, each in one group only.
- Optional layers, outside the hash: `coords {dim 2|3, xy (rows of dim numbers), from}`, `id {can, inchikey, skeleton}` (placeholder), `props [{name, from, can, v}]` (one value per atom), `regions [{atoms, delta, kind zone|multicenter|whole, support}]`.
- One record per component: salts (two components in the same record) pass validation, but the identity for MS is that of the parent.

## Public functions (`src/`)
- `Mol::new(atoms, bonds, stereo, groups)`: a record with the core only, in the given order (the canonical order: `canonical()`).
- `Mol::from_json(text)`: reads and validates; `MolError::Json` if it is not JSON of the right shape, `MolError::Invalid` if it breaks a rule.
- `Mol::validate()`: indices in range, symbols, orders 1-3, `a < b`, refs really neighbours, state consistent with the fields present, groups on defined centres, layer lengths.
- `Mol::to_json()`: compact, deterministic JSON of the whole record.
- `Mol::core_json()`: JSON of `{atoms, bonds, stereo, groups}`, the bytes that enter the hash.
- `Mol::core_hash()` / `core_hash_hex()`: SHA-256 of `core_json()`; coordinates, id, properties, regions do not change it; it follows the given atom order.
- `Mol::renumbered(new_of_old)`: the same molecule with atom `i` at index `new_of_old[i]` (a permutation); rewrites bonds, `refs`, `par`, `cfg`, groups and per-atom layers, sorts the elements as in the golden data, leaves `id` as it is.
- `Mol::from_smiles(text)`: SMILES with an optional CXSMILES tail (`|&1:2|`); atoms in text order, aromaticity in Kekulé form (`MolError::Smiles` if impossible), H and radicals derived from valences (bracket: the written `H`), `@`/`@@`/`/`/`\` into `defined` elements, groups `a:`, `&n:`, `on:` (other extensions are skipped); an explicit `[H]` stays an atom.
- `Mol::to_smiles()` / `to_smiles_with_order()`: SMILES with all atoms in square brackets and Kekulé bonds, `@`/`@@`, `/`/`\` and the group tail; the second also gives the record index of each written atom. `unknown` elements are not written (a SMILES cannot say it), radicals are not written (the reader derives them).
- `Mol::from_molfile(text)`: V2000 or V3000 molfile (the first record of an SDF); atoms in file order, type 4 bonds in Kekulé form (if the file does not say which aromatic N carries the H it tries one or two candidates), H and radicals from valences (valence field or `M  RAD` if present), any element allowed (H only for B C N O P S F Cl Br I, 0 for the others), explicit `[H]` stay atoms, `coords` layer kept (unless all are at the origin). `MolError::Molfile` if it cannot be read.
- `Mol::to_molfile(title)` (`src/molfile_write.rs`): V2000, V3000 beyond 999 atoms or bonds or with stereo groups (lines ≤80 with `-`); H with the valence field where the reader's rule would give something else, one wedge per `defined` centre chosen with the reader's parity (`molfile_stereo::parity`), wavy for `unknown`, "either" on `unknown` double bonds; without `coords` everything at the origin.
  `from_molfile(to_molfile(m))` = `m` (`tests/molfile_write.rs`, 92 golden molfiles, coordinates to 4 decimals in V2000). `Mol::pieces()` (`src/pieces.rs`): one record per connected piece; `fixed(v, n)`: whole decimals.
- `sdf/1` (`mzlab-feat` `chem/sdf.rs`; Draw "Export the canvas" `#ex-mol`, `#ex-sdf`, `#ex-ion` (behind `#ex-sdfopt`) in `disegno-esporta.js`; molkit `sdf`, app `feat/grafo` kind `sdf`, `mzlab-cli mol export`: same bytes, `tests/test_molkit_sdf.py`): `.mol` the whole canvas in one record; `.sdf` one record per connected structure with `MZLAB_FORMULA`, `MZLAB_EXACT_MASS`, `MZLAB_ION`/`MZLAB_MZ` (chosen adduct for neutrals, "drawn" for a drawn ion) and `MZLAB_HASH` (`mol1:`). Open formats only.
- `Mol::drawing_from_molfile(text)` → `Drawing` (`src/drawing.rs`, for the drawing check): same reader, but non-element symbols and query bonds (type 5+, written as 1) are kept (`query_atoms`, `query_bonds`), an impossible Kekulé leaves the aromatic bonds single (`kekule: false`), wedges come back with their bond (`wedges`, also on a multiple bond) and `sites` are the stereo sites with query atoms read as Xe.
  `allowed_valences(el, chg)`/`has_valence_rules(el)` expose the valence table (H: 1, H± 0). `from_molfile` rejects queries as before.
- Molfile stereo: a tetrahedral centre is `defined` only if a wedge starts from the atom (2D; parity from the signed volume of the neighbours, 3 neighbours = H or lone pair), a wavy wedge is `unknown`; a double bond is `defined` from the geometry of the substituents (not in rings ≤7 nor aromatic), with the "either" sign (V2000 field 3, V3000 CFG=2) `unknown`; groups from `MDLV30/STERAC` (`and`), `STEREL` (`or`), `STEABS` (`abs`), only on `defined` centres.
- `Mol::canonical_order()` / `canonical()` / `can()`: our own canonical order (neither RDKit's nor InChI's): classes by refinement on the constitution, then a search with individualisation among the tied atoms that keeps the smallest core JSON, so stereo is the last invariant; the automorphisms found prune the search (cap 20 000 leaves). Two writings of the same molecule give the same record byte for byte. `can()` = `mol1:` + hash of the canonical core (`CAN_VERSION`; if the algorithm changes, the version changes).
- `Mol::stereo_sites()` → `Vec<Site>` (`Tetra(c)`, `Db(a,b)`), ignoring the written stereo: a chemically suitable atom or bond (C/Si/Ge/Sn with 4 places, N+/P+/B-, P/As, S/Se sulfoxide and sulfonium, N in a 3-membered or bridgehead ring, C=C, C=N, N=N double bonds with a ring ≥ 8) and different substituents;
- Flip test of `stereo_sites`: if the substituents differ only by stereo elsewhere (cis/trans on a ring, pseudoasymmetric centres) the flip test decides: its value is changed, with the other sites assigned (all combinations up to 5, then 64 fixed random ones), and the canonicals are compared. Twins (same class) in separate branches with no other sites make the swap an automorphism and the site does not exist.
- `Mol::with_stereo_sites()`: the written element stays, a site without an element becomes `unknown`, every other element drops (and its members from the groups): it is the molfile's "missing stereo = unknown" for molfiles without wedges.
- `Mol::aromatic_bonds()` / `aromatic_atoms()`: aromaticity perceived from the Kekulé form (never written in the record): Hückel 4n+2 on rings of 5-7 atoms (the shortest per bond; electrons: 1 per double bond in the ring system, 2 per lone pair of N/O/S/Se/P/As or C-, 0 for empty C+/B and for C with an exocyclic double bond to O/S/N/Se, no other exocyclic double bond) and on pairs of rings sharing a bond (azulene, imidazo[1,2-a]pyridine); the shared bond of a pair is aromatic only if a ring alone is. Our own rule, not another toolkit's model.
- `hex(bytes)`: lowercase hexadecimal. `MolError`: error with `Display` (`Json`, `Invalid`, `Smiles`, `Molfile`).

## Tests (`tests/record.rs`, `tests/data/golden.json`)
- Golden data from RDKit: `python3 tools/struttura_dato/confronto.py --golden crates/mzlab-mol/tests/data/golden.json` (needs `pip install rdkit`, only to regenerate them; the Rust test does not require it). For the 20 molecules of the study: record with atoms in written order and in RDKit canonical order, CXSMILES, InChIKey, SHA-256 of the core computed in Python.
- The test rereads each record, rewrites it (same JSON), compares the hash with Python's (20/20 × 2 orders). Traps tested: unknown stereo ≠ no stereo (different hashes), S ≠ R ≠ unknown ≠ racemate, layers outside the core do not change the hash, broken records rejected.
- SMILES reader (`tests/smiles.rs`): the 20 molecules and 80 more cases (aromatics, radicals, charges, isotopes, `@` in every position, `/` `\` also in rings, groups `a`/`&`/`o`) compared with RDKit: same atoms, same bonds (in aromatic systems the Kekulé choice may differ: sums per atom are compared), same `defined` stereo elements, same groups.
- `composti.csv`: the 625 rows (atoms, number of bonds and defined stereo equal to RDKit, digits per row in the golden data); 286 rows with stereo elements and 111 with at least one unspecified, counted from the golden data.
- Intended limit: the reader does not decide whether an atom without a sign could be stereogenic (`with_stereo_sites` does), so it never creates `unknown` elements; it keeps an `@` even on a non-stereogenic centre, which RDKit cleans.
- Writer: every record of the golden data (without `unknown` elements) and the 625 rows are rewritten, reread and coincide with the record renumbered in text order; rewriting the result gives the same text. `renumbered` with RDKit's canonical permutation gives RDKit's canonical record (`tests/record.rs`). Trap: explicit `[H]` stay atoms (4 `refs`, `implicitH` false), so the hash differs from that of the same molecule with implicit H.
- Molfile reader (`tests/molfile.rs`, `tests/data/golden_molfile.json`, generated by `confronto.py --golden-molfile`): 92 molecules in V2000/V3000 with wedges, with type 4 bonds and without wedges, compared with RDKit (atoms, bonds modulo Kekulé, `defined` elements, V3000 groups); the sign of the wedge parity is fixed by this data. A molfile without wedges gives no `defined` centre (RDKit marks it `unknown`: `with_stereo_sites` does it).
- Limit: the NH tautomers of an aromatic system without a valence field are not recoverable (the number of H is compared). Double bond with the "either" sign → `unknown`; without a sign the configuration comes from the drawn coordinates (like RDKit).
- OpenChemLib trap: with an explicit `[H]` OpenChemLib removes the atom and reorders the others (e.g. `C[C@]([H])(O)CC`), so its labels do not match the written order; the reader instead keeps the received order (`ocl_ordine.mjs --json` gives the golden data).
- Stereogenicity (`tests/stereo.rs`, `tests/data/golden_stereo.json` from `confronto.py --golden-stereo`): the sites of 717 SMILES (20 + 72 + 625 rows of composti.csv) coincide with RDKit's `FindPotentialStereo` except 3 exceptions listed in the test: the azide N=N+=N- (linear, no cis/trans) and two trialkyl phosphates with three equal arms (they have only two arm types, so two always coincide: the phosphorus is not stereogenic).
- An imino N-H is a site but stays `unknown` (no neighbour to name in a defined element). The sites of the 92 molfiles coincide with RDKit's `defined`/`unknown` states (also without wedges).
- Aromaticity (`tests/stereo.rs`): the aromatic bonds of the 717 SMILES coincide with RDKit's (golden data `golden_stereo.json`, third column) and 9 textbook rings (benzene, quinone, cyclooctatetraene, tropylium, azulene, pyrrole, pyridone, cyclopentadienyl) have the expected count.
- Canonical order (`tests/stereo.rs`): for each SMILES and for its version with the sites, three random permutations give the same canonical JSON and the same `can`; enantiomers, E/Z, defined/unknown and cis/trans on a ring have different `can`.
- Size rules: file ≤ 500 lines, functions ≤ 80 (`tools/controlla.py`).
- View for the engines (`crates/mzlab-feat/src/chem/graph_record.rs`, feature `record` of `mzlab-feat`): `grafo::Mol::from_record(&rec, aromatic)` builds the mzFinder graph from the record: atoms and H of the record, bonds ordered by pair; with `aromatic` the rings perceived by `aromatic_bonds()` take the flag and order 1,5, without it they stay Kekulé. Isotopes and radicals do not enter; like `parse` it rejects elements without a normal valence and more than 200 atoms, accepts detached pieces.
- Test `tests/grafo_record.rs` (`--features record`, line in `rust.yml`): same graph as `parse` and `from_molfile` on study cases, extras, composti.csv and molfiles (set of bonds). The old V2000 reader does not know radicals and adds the charge's H shift to that of the valence: the record is right and the test allows the difference on the H of charged or radical atoms only.
- Consumers on the record (feature `record`, in no `.wasm`): `posiz/1` (`positions_record_json`, `docs/agenti/positions.md`) and `frag/1`/`parz/1` (`frammenti::fragments_record_json`, `partial_record_json`: cuts ordered by atom pair, perceived aromaticity; test `tests/frammenti_record.rs` on the V2000 molfiles of the golden data). `interp/1` (`docs/agenti/interp.md`) and `mol3d_from_record` (`docs/agenti/reactivity.md`).
- Descriptors (`src/descr.rs`, `crippen.rs`, `crippen_tab.rs`; Wildman-Crippen 1999 tables written by hand): `Mol::crippen_logp()`/`crippen_mr()` (types on the graph, implicit and explicit H), `tpsa()` (Ertl, N and O only), `hbd()` (N/O with H), `hba()` (O and N with a lone pair, our definition), `rotatable_bonds()` (RDKit "strict" rule), `molecular_weight()` (None if a weight is missing), `descriptors()` = all.
- Test `tests/descr.rs`: 45 molecules against RDKit values (logP, MR, TPSA, rotors, MW); the 625 rows of `TP_Mine/data/composti.csv` coincide with no differences. Crippen logP is not the measured one (caffeine −1.03 versus −0.07).
- Transformations `trasf/1` (`src/transform.rs`, `transform_chain.rs`, `delta.rs`; study `docs/studi/STRUTTURA_DATO_TRASFORMAZIONI.md`): `Transformation` = parent → product with the atom map on the canonical indices of the two `mol/1`, identified by the core hash and never copied. `from_json`/`to_json` (fields in the order of the study, `level` and `stereo_rule` optional), `validate()` without molecules, `validate_against(parent, product)` with the hashes, sizes, elements (equal except at the centre) and the stereo rule.
- Certain product: `product` + complete `map` (one `[parent atom, product atom or null]` per atom, in order) + `added` + `centre`, without `sites` or `region`. Uncertain product (the change only): no `product`, `map`, `added`, `centre`; `sites` (distinct atoms, p in (0, 1]) and a `region` that includes them. A `product` is never given to an uncertain TP.
- Stereo: `touched_stereo(parent)` gives the parent's elements on the `centre`; the product does not have them `defined` unless `stereo_rule` is `retention` or `inversion` (test in `tests/transform.rs`). `product_atom`/`parent_atom` follow an atom along the map; `compose(next)` composes two certain steps (map, `added`, `centre`, delta; a lost atom stays lost; the evidence from the first step's parent and the second step's product remains); `canonical(parent, product)` rewrites everything on the canonical order and on the hashes of the renumbered records.
- `delta` (`mzlab_mol::delta`): `+O`, `-H2+O`, `-Cl+OH` as signed element counts; `add` sums two deltas and writes them in a single form (gains then losses, Hill order). No consumer uses `trasf/1` yet (interp, Draw and posiz/1 move to the record after the `grafo::Mol` view); the crate stays out of every `.wasm`.

## Substructure (`src/query.rs`, `substruct.rs`; `substructure/1` in `mzlab-feat` `chem/substructure.rs`)
- `SubQuery`: record + one test per atom (`AtomTest`: element; list `L`/`M  ALS`, V3000 `[C,N]`; negated list `T`, `NOT[...]`; `A`, `AH`/`*`, `Q`, `QH`, `X`, `XH`) and per bond (`BondTest`: same class, types 4-8 = aromatic, single/double, single/aromatic, double/aromatic, any).
- `SubQuery::from_text`: molfile (text with `M  END`, V2000 or V3000) or SMILES; query atoms enter the reader with a placeholder element (the first of the list, else C), query bonds as single. Rejected, never ignored: ring/substituent counts, unsaturation, bond topology, R groups (`MolError::Query`). `read_target`: molfile or SMILES (the `mol/1` JSON does not enter, so a `.wasm` with the matcher will not carry the JSON reader).
- `SubQuery::matches(target, SubOptions{stereo, max_matches, max_steps})`: VF2-style subgraph monomorphism (connected order of the query atoms, candidates among the neighbours of an already matched atom, degree and bond checks before descending); one row per distinct set of target atoms, in the order of the query atoms. Aromaticity perceived on both (`aromatic_bonds`): a Kekulé query bond does not match an aromatic ring; an atom does not check aromaticity (N also matches n). Charge, isotope, radicals: if non-zero in the query they must coincide.
- Hydrogens: the implicit H of the query do not count; an explicit H of the query (non-isotopic, on a heavy atom) asks for at least that many H (implicit plus explicit) on the partner and has no column. Stereo only on request, on complete matches: a `defined` centre or double bond of the query wants the same `defined` element and the same sense in the target; `and`/`or` groups do not enter.
- `max_steps` cap (2 000 000 assignments tried) per target: beyond it, a clear error instead of an endless search on symmetric cases.
- `substructure/1` (`search_json`): request `{query, targets, stereo, max}` (at most 1000 matches), response `{format, atoms, stereo, hits: [{i, n, maps}], errors: [{i, error}]}`; only the targets that contain the query, an unreadable target goes to `errors`. Errors `error.sub.request`, `error.sub.query` (`detail`). A hit is a suspect to verify, never an identification.
  Same bytes from the site (`substructure` of `molkit`), the app (`feat/grafo`, `kind: "sub"`) and `mzlab-cli mol search --sub QUERY TARGET... [--set stereo=0|1] [--set max=N]` (argument = file if it exists, else text).
- `substructure_db/1`: `db` (text of a list) in place of `targets`. SDF if a line is `M  END` (records split at `$$$$`, name = title line or `> <name>` field, id = `> <id>` field), table if the first line has a `smiles` column (`molecules::table`, the molecules CSV reader without checks: the catalogue; rows without SMILES in `skipped`), else a SMILES list (SMILES, space, name; empty lines and `#` skipped).
  Response `{format, atoms, stereo, source, total, skipped, hits: [{i, name, id, structure, n, maps}], errors: [{i, name, error}]}`; empty list `error.sub.db`, over 200 000 entries `error.sub.dbSize`.
  `mzlab-cli mol search --sub QUERY --db LIST|-`. Parity on the fixture `tests/dati/sub_db.json` (`test_molkit_wasm.py`, `mol_search_tests.rs`, `substructure.rs` of the app).
- Flow step `structure.moiety` (`chem/moiety.rs`, `moiety_text`): the rows of a candidates CSV with the SMILES column `column` that contain `query` (or, `keep` = `lacking`, do not), last column `moiety_matches`, delimiter and cells as in the input (quotes if needed); rows without a readable structure excluded; no column: `error.sub.column`. In the `.wasm` `molkit` (`flow_moiety`) and in `flow run` (`cli-passi.md`); fixture `tests/dati/moiety.json`.
- Tests: `crates/mzlab-mol/tests/substruct.rs` against RDKit (`crates/mzlab-mol/tests/data/golden_sub.json`, 611 pairs of 47 synthetic queries, with and without stereo, from `tools/sottostruttura_riferimento.py`; queries with explicit H = `MergeQueryHs`); every molecule finds itself and its connected fragments; features rejected; step cap; 100 atoms against 10 under 50 ms (release). Parity: `crates/mzlab-desktop/tests/substructure.rs` (app = function), `mol_search_tests.rs`.
- Known difference from RDKit: a simple RDKit atom does not match an atom in fewer rings; here the ring is not counted (no pair of the golden data touches it).
- **CIP (`cip/1`)**: "Stereodescriptors" card of Draw (`#cip-card` after `#chk-card`, `disegno-cip.js`, test `e2e_disegno_cip`), off by default; fixed note: mass spectrometry does not distinguish these stereoisomers. When on, it sends the molfile and follows edits (700 ms); rows "C2: R", "C4=C5: E" (r/s pseudoasymmetric); `#cip-status` (`role=status`, also `skip`).
  Engine `chem/cip.rs` + `chem/cip_rank.rs` (feature `check`): digraph, rules 1a, 1b (ring closures), 2, 3, 4a, 4b, 5, auxiliaries, mean Z for mancude; missing: 4c and 4b/5 on double bonds.
  RDKit golden (382 molecules) in `crates/mzlab-feat/tests/data/golden_cip.json` from `tools/cip_riferimento.py`, test `crates/mzlab-feat/tests/cip.rs`. `molkit` `cip`, `feat/grafo` `kind: "cip"`, `mol cip`; parity on `tests/dati/cip_disegno.json`.
- **Evidence colours (`highlight/1`)**: `chem/hilite.rs` (feature `check` and `sub`) carries onto the drawing's molfile the layers `moiety` (substructure, every match), `sites` and `cuts` (numbered on the evidence's SMILES, carried with the first match of that SMILES); in LR it keeps only the `selected` atoms; `skip` noMatch, lr, tooBig (over 400 atoms). `molkit` `hilite`, `feat/grafo` `kind: "hilite"`, `mol hilite`; parity on `tests/dati/hilite_disegno.json` (`crates/mzlab-feat/tests/hilite.rs`). Interface in `drawing.md`.

## Why and what not to do
- **Why**: SMILES is an exchange format, never an identifier (different toolkits write different SMILES for the same molecule; "unknown stereo" and "no stereocentre" are written the same). Identity is the standard InChIKey plus our canonical, because the InChIKey does not distinguish a racemate from a pure compound. Per-atom properties attach to the record's canonical indices. The traps are tested by `crates/mzlab-mol/tests/record.rs` (RDKit golden data from `tools/struttura_dato/confronto.py`; `tools/struttura_dato/ocl_ordine.mjs` checks the atom order of OpenChemLib).
- **What not to do**: SMILES as a dictionary key, file or cache; per-atom properties on the indices of the written SMILES or of Ketcher's molfile; stereo inferred from coordinates; "no sign" treated as "stereo absent" (when in doubt `unknown`); aromaticity as data (Kekulé in the record); our own canonical tautomer or InChI; RDKit, Open Babel, OpenChemLib or InChI inside the capped `.wasm` (they are test arbiters in `tools/`); a single structure for an uncertain TP (parent + region, level 3); changing `posiz/1`, `frag/1`, `interp/1` in one go.
