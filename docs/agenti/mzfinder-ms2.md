# mzFinder low resolution: MS2 matching rule and targets

Engine and `ms2_links/1` contract: `docs/agenti/mzfinder-lr.md`; matching rules: `docs/studi/TABUI_MS2_LR.md` §4-§5. This file holds the engine side only (association rule, MS2 targets); the Tabui page that showed them was deleted, the engine, CLI and Flow keep using it.

## MS2 → feature association rule and "Fragment ions found"

Code in the Rust engine (`crates/mzlab-feat/src/legacy/lr/`): `ms2assoc.rs` (pure rule), `ms2link/feature.rs` + `rules.rs` (use in the matches), `ms2target.rs` ("MS2 target" rows), `ms2rep.rs` (representative scan for the detail), `ms2frag.rs` (fragment ions, losses, sentence). Tests: `crates/mzlab-feat/tests/lr_ms2assoc.rs` (exact-value tables), `crates/mzlab-finder-lr-wasm/tests/lr_ms2link/assoc.rs` and `target.rs`. Texts in English only, no `lang/` keys.
- **Rule**: an MS2 belongs to a feature only if (a) the centre of the precursor is at most `max(half the isolation window, 10 ppm)` from the READ m/z in the table (`Entry.observed`, never the calculated m/z nor the one corrected with the offset) and (b) the scan time lies between the start and the end of the feature's peak (not just near the apex).
- **Tolerance** (`ms2assoc::tolerance`): half the isolation window written in the file (`Scan.iso`, median of the experiment's scans, `Exp.half`); if the file does not state it, the table tolerance `PREC_TOL` = 0.5 Da. Every match reports `tol` and `tol_window` (true = from the file), and the reason (`why`) writes it in words.
- **Feature peak** (`feature::bounds`): start and end of the cell of the file with the same sampling time as the MS2, otherwise the median of start and end of the row's detected cells (a wide peak in another file does not widen it), otherwise reference RT ± `rt_tol_min`; shifted by the MS2 file's drift.
- **Match scans**: the part of the TRACE peak that falls inside the feature peak (`Link.lo/hi`, `n_in`); if they do not overlap, no match. The fragment pool (`ms2::pool`) uses only these scans.
- **Deviations shown** for each match: Δm/z in Da (`dmz`) and in ppm (`dppm`), ΔRT (`drt`), `tol`, `tol_window`, `n_in`.
- **Representative** (`ms2assoc::associate`, `ms2rep.rs`): among the scans inside the peak (of all the row's matches) the most intense; the intensity is that of the precursor (`pint`) if the scan has it, otherwise the scan's TIC (`intensity_src`); on a tie the one closest to the apex; the others are counted (`others`).
- **"MS2 target" rows** (`ms2target::near`): the table feature with read m/z within the tolerance of the precursor and a peak (start to end, in at least one file) that contains the apex of the trace peak, maximum area; outside tolerance the peak stays `no_feature`.
- **Detail** (`detail.ms2_rep`, `detail.ms2_text`): `ms2_rep` = `{file, rt, precursor, ce, intensity, intensity_src, dmz, dppm, drt, tol, tol_window, n_in, others, mz[], int[], found[]}` (whole spectrum of the representative scan and ions found with `loss` and `loss_formula`); without scans in the peak `ms2_rep` is null and `ms2_text` = "No MS² in the feature peak". The "With MS²" filter and the MS2 column count the matches of this rule (`rows[].ms2`).
- **Sentence** (`ms2frag::text`): "Fragment ions found: m/z X (intensity I, loss −ΔPm/z = −N.NNNN, −formula) ; …", ions more than 1.5 Da below the precursor, in decreasing intensity order, at most 10, from a relative threshold (`settings.frag_min_rel`, 5 % by default); without a formula "unassigned".
- **Loss as formula**: with the fragment ion's formula, the exact difference from the row's [M+H]+ (or the parent's if the row has no formula); otherwise the nearest loss within 0.3 Da (`LOSS_TOL_LR`) among the usual ones (H2O, NH3, CO, HF, HCl, SO2, C2H4, C3H6, C4H8, …) made only of elements of the molecule and in their number. At unit resolution it is a suggestion, not an identification.

## Tabui LR MS2 targets

The student acquires an MS2 on an ion because they saw it in the full scan: if the LR Dig does not list it, the MS2 must not stay orphaned. Code: `crates/mzlab-feat/src/legacy/lr/ms2target.rs`, called by `ms2link::ms2_link`; study: `docs/studi/TABUI_MS2_LR.md` §6; matches: `docs/agenti/mzfinder-lr.md`.

### Rules
- `ms2_link` removes the `ms2_target` rows of a previous call, matches the experiments (first pass), then for every trace peak `no_row` / `no_row_at_rt` (not `front`, not `parent_rt`, not `user`) looks in the aligned table (`LrDig.table`) for the row with read m/z within the tolerance of P (half the file's isolation window, otherwise `PREC_TOL`; never the offset)
  The row must have a peak (start to end, in one file) that contains the trace apex minus the drift, after `rt_min`, and maximum area among the series' files (`ms2target::near`; rule in the section "MS2 → feature association rule"). If the row is already an `Entry` nothing is created; if there is none: the peak stays among the unmatched with reason `no_feature`.
- One row per table row (two peaks, or two CE, on the same row give a single row). Ids from 200001 in table row order; `unexpected: true`, `ms2_target: true`, name "MS2 target m/z {P:.1} @ {RT:.2} min". Cells, criteria and score like the unexpected ones (`evaluate`, isotope check and kinetic generation with `finish_one`), WITHOUT the criteria filter and `max_unexpected`: the label may be `debole`, which is honest and visible.
- Then the second matching pass, with the new rows: the peak becomes `auto` and the `why` ends with "row made from this MS2" (only for the experiment that gave rise to the row). A target marked isotope (`isotope_of`) stays compatible (`ms2link/rules.rs::compatible`): the student chose it, the criterion "not an isotope peak" shows the doubt.
- If the ISF had already been computed by the page (`d.isf` not empty) it is recomputed with the new rows. `relink` starts over: a "not this ion" correction (`row: null`) on that peak prevents the row; removing it, the row comes back with the same id.
- Summary: `rows[].ms2_target: true` (the key exists only when true, the golden contract does not change), `kind: "unexpected"`; `live()` does not change (candidates only).

### Cases from the real files (private truth)
- An ion that the truth gives as an isotope of a row (`expect: "isotope"`) has the `isotope` link and no row of its own. The data test (`lr_ms2link_data.rs`) requires, for a truth target (`expect: "target"`), an `auto`, `ambiguous` or `user` link of the peak at the apex (±0.1 min) to any row with a reference RT within 0.1 min of the full apex; `isotope` holds only for `expect: "isotope"`; for `no_signal` no link to the Dig row at that time.
- The reason the Dig does not list strong ions (synthetic, tested in `lr_ms2link/target.rs`): an ion within `tol_da` of a hypothesis' m/z belongs to that hypothesis for `rows::assign` and is never an unexpected (`rows::unexpected` discards every row within `tol_da` of a known m/z, even at another time); it enters as an isomer only if it has ≥ 10 % of the strongest's area and is among the first 4 (`rows::candidates`). A small ion at the same m/z as a hypothesis but at another time therefore vanishes from the Dig table. No change to the Dig: fixing it needs the Coordinator's yes.

### Diagnosis on real data (done by the owner locally; numbers only in the private repository)
```
MZLAB_DATI=<percorso> cargo run --release -p mzlab-finder-lr-wasm --example finder_lr -- OUT FILES.json PARENT.json RULES.json --diag --ms2 N MZML...
```
(`FILES.json` and `PARENT.json`: the example's input files; `RULES.json` = `TP_Mine/data/regole_tp_3.json`). `--diag` prints, for every trace peak without a row BEFORE the targets, the table rows within 0.5 Da and 0.5 min of the apex (m/z, RT, score, cells, criteria) and the Dig step that loses them: nearby hypothesis (isomers), criteria, absence from the table (detection). Write the outcome in `scratchpad/consegne/TABUI_MS2_LR_DATI.md` of the private repository.
