# User lists (`liste/1`, `crates/mzlab-feat/src/lists/`)
Neighbouring areas: `mzfinder-ingresso.md` (the mzFinder transformation list), `rust-flow.md` (`prov/1`).

- Two kinds: `transformations` (name, formula change, maximum repeats 1-10 or the rules' default, comment), `adducts` (name, formula change, charge ±1…3). Suspects are not a list: a `nome;formula;mass;comment` file is imported as a molecule collection (`molecules.md`: short columns `formula`, `mass`, `comment`, collection named after the file; a row with only the mass becomes a mass-only entry, one with neither formula nor mass is refused with its own error). Schema `docs/schemi/liste-1.json`.
- Kind `transitions` (the transition table of `chrom.transitions`): `liste::route` hands it to `transitions::route`, which keeps the row order and answers `rows`, `csv`, `json` (`transitions/1`) and `sha256`; columns and errors in `transitions.md`.
- `from_csv(kind, text)`: separator `;` (or tab or comma if the header has no `;`), empty rows and `#` rows skipped, fields in double quotes; the header gives the columns (`name`, `delta`, `max_repeat`, `charge`, `comment`, in any order). Each wrong row gives a `RowError` (row, `error.liste.*`, text) and the list is refused if there is one; `errors_json` writes them.
- `to_json`/`from_json`: canonical JSON (keys in alphabetical order, elements sorted by name and change), same bytes for any row order and for the CSV → JSON → list → JSON round trip; `Liste::digest()` is the SHA-256 that goes into `prov/1`.
- The mzFinder list (`nome;cambiamento[;commento]` per row) is the header-less form of the same CSV: `from_legacy_text` and `Liste::transformation_rows` pass it through here before `legacy::transf::merge`, with the same rows and the same errors; `ripetizioni_max` becomes `passi_max` of the new rule (2 if missing), so the default list gives the same rules as before. Tests: `tests/lists.rs`, `tests/legacy_transf.rs`.
- Browser side (`mzlab/web/liste.js`): saved lists live in the `liste_utente` store of `mzlab_lab`, with one connection per operation closed when the transaction ends (`idbRun`), so the "Full reset" is not left blocked (test `e2e_reset`).
