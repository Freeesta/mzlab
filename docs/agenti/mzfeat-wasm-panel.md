# mzFinder "Pipeline" panel (`TP_Mine/js/32_pipeline.js`)
Continuation of `mzfeat-wasm.md`: form, parameter estimation, gate, run and view, recipe, steps 5-8, weak tier, targeted join, close isomers.

- Texts are in English like the rest of mzFinder. The pool is created on first open: `static/wasm-feat/manifest.json` (written by `tools/build_feat_wasm.sh`) and `feat-worker.js` from a Blob; the `.mzidx` files are those in OPFS `mzlab/idx/` (without the `.cen.mzidx`, the second centroid index of the same sample used by mzFinder). `pool.crateVersion()` and `pool.preview(file, recipe)` (JSON of `params::preview_json`).
- Six numbers: ppm tolerance (5), noise threshold (2e4), minimum height (2e5), minimum points (5), alignment RT tolerance (0.1 min), fill; under "More" polarity and rows (family/ion). Threshold and tolerance are proposed from the preview and stay editable: as long as the threshold is the estimated one it is not put in the recipe (`floor` absent = the engine estimates it), as soon as it is touched it is "chosen".
- **Form** (`32_pipeline_form.js` = `PIPEFORM`): the fields come from the `step/1` descriptors (`docs/schemi/steps-1.json`, copied by `build_site.py` into `static/mzfinder/`, read from `QTOOLS.ctx.files`); `MAP` says which parameter of which step feeds which input (fixed `#pipe-*` ids). "Reset" per field, "Auto" for `x-estimate`; polarity and rows under "More". Tests: `test_pipeline_form.py`, `e2e_pipeline.py`.
- `crates/mzlab-feat/src/params.rs` (tested in the module tests, on synthetic histograms; example `preview`): threshold = 3σ above the peak of the first bulge of the log10 intensity histogram (σ from the right side at half height, with a parabola for the peak; at most 4 Mpeaks read in chunks of 64 K; the bin of each intensity is found between the bin edges computed once (`histbin.rs`, the same formula with the `libm` log10 near an edge), without a logarithm per peak; no threshold if the bulge is missing).
- Tolerance = 3 robust σ (1.4826 MAD) of the m/z error of the points of the 80 highest traces (1-20 ppm), width = median FWHM of the same. The preview runs L1 with the chosen threshold: number of features, height histogram, 3 XICs (5 %, 50 %, 90 % height quantiles) with the edges; each chart is an SVG with `TDATI` (key T, button "Data"). The proofs (histogram, chosen point, σ and number of points) are in `PIPE.state.proofs`.
- **Gate** (`data/cancello.json`, `cancello/2` (`/1` is read too), written by G1; `tools/build_site.py` copies it into `static/mzfinder/`): `PIPE.gateState(json, crate)` is only internal data: `validated` (`vista_candidati: true` and `crate_version` equal to `crate_version()` of the `.wasm`), `validatedTable` (same rule on `vista_tabella`; a `/1` follows `vista_candidati`) and `why`; `ok` and `table` are always true. No user text and no closed view: table, candidates and QC are always shown.
- **Run and view** (`34_pipeline_run.js` = `PIPER`, `33_pipeline_view.js` = `PIPEV`): section "Run on all the files" (formula, m/z, RT and optional SMILES of the parent: its `grafo/1`, from the `grafo` `.wasm`, goes to the hypotheses as `structure` and the SMILES into the `genitore.smiles` record; roles and timings: `samples.md`). Without the gate the run does not pass the parent and the list shows the table rows (no `[data-cand]` in the DOM); with the gate open it lists the identities by points (on a tie "against" is always in red with ✕, never offset).
- Columns Contributions, 1/N and Cells (D/T/F/A): the "Discarded" filter lists the identities with no proof in favour, with their code (`EV_*`, or `EV_NO_PROOF` client side).
- **List and detail**: the list is virtualized (`role=grid`, keyboard Arrows/PageUp/PageDown/Home/End/Enter); the detail has proofs, cells and XIC/MS2 from the file open in Data (routes `api/xic` and `api/spectrum`), each chart with its table (`TDATI`); "Send to the feature tables" passes the table to `UNTUI.adopt` (program "mzlab"). `feat/*` routes of the desktop app: there are none.
- **Recipe** (`35_pipeline_recipe.js` = `PIPEREC`; schema `docs/schemi/feature_pipeline-2.json`; `workflow.js` registers the `feature_pipeline` operation and checks its record with `checkFeatureOp`): each run writes into the `NB.ops` registry (and so into the `.mzflow`) the parameters (exact recipe text), the proofs, crate version, SHA-256 of the inputs and of the table, version and SHA-256 of `regole_tp/1` and `livelli/1`, suspects index (`null` if missing), hypothesis registry, `giri: 1`.
- **"Feature table" tab, steps 5-6** (`36_feature_qc.js`, `37_feature_table.js`): QC, filter bar, virtual table and expanded row in `mzfeat-table-view.md`.
- **"Feature table" tab, step 8** (`38_feature_export.js` = `PIPEX`, under the table): seven buttons (mzmine CSV = `full_mzmine`, CSV with the estimated cells = `full`, Excel = `xlsx_rows` sheet zipped by `dlx`, `;` CSV with BOM, FBMN zip = `quant` + `mgf`, SIRIUS `.ms`, printable HTML report) for the rows of the view chosen in "Table".
  - Texts and numbers come from the table `.wasm` (`session.file`, `session.report` = `report/1`); the `.mgf`/`.ms` files go through the pool (`pool.ms2File`, `ms2file` operation of `feat-worker.js`), which reads the `.mzidx` in OPFS. The JS lays out the report, zips and downloads. The session has `row(id)` (`riga/1`) and `traces(id, ppm)` (`riga_tracce/1`: `pool.rowTraces`, `rowtraces` operation of the worker; `PIPEQC.open` receives `pool`).
  - Keys read: `PIPEQC.CONTRACT.report`/`cells`/`reportView` (`tests/test_pipeline_contract.py`).
  - No number is computed in the JS: `PIPEQC.CONTRACT` lists the keys read and `tests/test_pipeline_contract.py` looks for them in the real output of the `table` example.
- "Re-apply the recipe" reruns the last valid operation of the registry (also that of an opened `.mzflow`) with the verbatim recipe and says whether the `.mzfeat` is identical (same SHA-256) or what differs (files, engine, table).
- A `.mzflow` with an unknown operation opens with a warning. Tests: `tests/test_pipeline_recipe.py`, `tests/test_pipeline_view.py`.
- Test: `tests_e2e/e2e_pipeline.py` (site + `.wasm`; `MZLAB_PIPE_SITE` reuses a site, `MZLAB_PIPE_MZIDX` a real file, `MZLAB_PIPE_SHOTS` the screenshots).
- Weak tier (`series::weak_tier`, `Recipe::weak_files` 5, `WEAK_RATIO` 0.3): in `align_and_fill` each file is reread with `detect.min_height * 0.3`; the peaks kept are the good, non-isotopic ones not already in the file's table, aligned on their own (in the strong table dense noise would act as a bridge). `Aligned::retain_recurring` keeps the rows absent in the first file and detected in a single uninterrupted series of at least `weak_files` files; `append_unheld` appends those that no strong row already holds.
- `target/join.rs` (`TargetResult::missing_rows`, `add_missing_to`, `JoinParams`): in `run.rs::evidence()` the rows of the targeted pass with no detected peak (and with coincidence ≤ 0.05) enter the table with `append_unheld`, so a product expected by a hypothesis but below threshold has a row.
- Close isomers: `resolve::ResolveParams::min_sep` 0.04 min separates the maxima within a file; `AlignParams::split_gap` (the recipe uses `SPLIT_GAP` 0.03, `None` elsewhere: parity with Python does not change) cuts, in `align::split_duplicates`, a group with two features of the same file where there is an RT jump above `split_gap` and at least `MIN_SPLIT_FILES` (9) files have a feature on both sides; several possible cuts or groups larger than 2 times the files stay merged (noise chain).

## `family_record`: the family of a file on request

- **What it does**: `family_record(read, size, name, recipe)` (crate `mzlab-feat-wasm`, module `family.rs`, feature `detect`, so in the HR `.wasm`; Rust step `family::record`) redoes L1-L3 of ONE `.mzidx` file with the same steps as `analyse_file` and returns the `famiglia/1` record (`mzlab_feat::famrecord::record`): the edge proofs, which neither `.mzfeatf` nor `.mzfeat` store, are born here and are not kept.
- **Arguments**: `read(k, offset, length) -> Uint8Array` and `size` as `detect_file` (file 0 only); `name` ends up in the `file` field of the record; `recipe` is the `detect_file` JSON (`{"polarity": 1|-1|null, "mode": ...}`, plus `floor`, `min_height`, ...) and goes through the same `recipe_for`: same recipe as the page = same families as the table.
- **Output**: a JSON string `{schema:"famiglia/1", file, families:[{family, size, members:[{row, mz, rt, role, parent...}], arcs:[{lo, up, delta_mz, delta_rt, r, kind, admitted_by, readings:[{kind, name, step, ppm}], proofs:[{kind, value, threshold, points, sign}]}]}]}`. Only numbers and words, no verdict; `row` is the row of the `.mzfeatf` of the same file.
- **Errors**: JSON string `{error_key, params}` like the other exports: `error.badRecipe` (invalid recipe), `error.badIndex`/`error.io` (read), `error.memoryBudget` with `{fase:"family_record", stima_mb, budget_mb}` if the estimated text (600 B per row + 900 B per arc) does not fit the `.wasm` budget (192 MB, no parameter).
- **Determinism and test**: same bytes with the same inputs; `crates/mzlab-feat-wasm/tests/family_record.rs` (synthetic series `degdma`, skipped without python3/numpy) compares the record with that of the native example `families.rs`, the second run and the refusal at zero budget.
- **Size**: the HR `.wasm` after `wasm-opt -Oz` goes from 1 131 442 to 1 136 182 B (+4 740) under the `limit_hr` cap 1 212 416.
