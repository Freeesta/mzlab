# Recipes for whole campaigns (`mzlab-cli`, tested chains)
Each recipe is a tested chain: every call exits 0, the call count is asserted and every command, step and `--set` named here is checked against the binary (`crates/mzlab-cli/src/workflow_kinetic_tests.rs`). Before writing any script: `mzlab-cli commands --find TASK WORDS --json`, the task table of `for-agents.md`, `mzlab-cli flow steps --compact`. Never call one command once per file, ion or target when a row of that table does it in one call.

## Kinetic LR campaign (unit resolution, ESI+, one or more conditions)
Template: `docs/recipes/kinetic-lr.mzflow.json` (plan), `kinetic-lr.targets.csv` (targets), `kinetic-lr.parent.json` (parent). It names the files of the synthetic test series (`Blank_01`, a shared `t0`, `Fe_t5|15|30`, `Cu_t5|15|30`); for your series replace `inputs` and `idx.in.source` with your mzML names, the targets with yours and the parent formula or SMILES. Plan: `index.mzidx@1` → `features.detect@2` → `features.align@1` → `features.gapfill@1` → `tp.dig_lr@1`, `quant.targets@1` on the same indexes, `export.table_csv@1` of the LR table.

Nine calls from vendor files to the kinetics per condition (tested on mzXML; a folder of `.wiff`, `.raw` or `.d` starts with `mzlab-cli file list RAW --json`, which lists those but not `.mzXML` or `.cdf`, and a `.wiff` adds `mzlab-cli file inventory FILE` and `mzlab-cli file pair FILE --json`, as chain 5 of `for-agents.md`):
1. `mzlab-cli sample list FILE... --json` (`sample-list/1`): the sample numbers and names of every file.
2. `mzlab-cli file convert FILE... --out MZML --name sample --json --dry-run`, then the same without `--dry-run` (`convert/1`): one `SAMPLE.mzML` per sample, so the names keep the sample id, the time and the condition; a renamed clash is a `note:` line. Select samples with `--sample LIST`.
3. `mzlab-cli sample table MZML/*.mzML > MZML/samples.json` (`samples/1`): role (`blank`, `t0`, `std`, `dark`, `sample`), time and series proposed from the names, one `auto:` line per file on stderr with the rule used. Check them: a `t0` without a series is shared by every condition; edit the JSON when a name misleads.
4. `mzlab-cli flow check PLAN.json --json` (`flowcheck/1`, exit 3 with the problems), `mzlab-cli flow run PLAN.json --in MZML --out RUN --dry-run --json` (`flowdry/1`: inputs found, instances with their canonical parameters; exit 4 = a missing input), then `mzlab-cli flow run PLAN.json --in MZML --out RUN --json` (`flowrun/1`, exit 0; 1 = an instance in error, the other outputs written).
5. One cell by hand, as evidence: `mzlab-cli trace xic FILE --mz M --da 0.5 --polarity + --mz-offset D --format csv > x.csv` (D = `mz_offset_da` of the row), then `mzlab-cli peak auto-lr x.csv --from RT_MIN --to RT_MAX --set sn=0 --set min_pts=2`: its tallest peak is the row's `area`, `height`, `sn`, `rt` (the table rounds area and height to 1 decimal).
Provenance: `RUN/prov.json` keeps the SHA-256 of every input and output. `mzlab-cli flow record` needs a `samples/1` role for every plan input, so it refuses this plan (its `samples.json`, `parent.json` and `targets.csv` have none: `err.mzrun.build`).

What `RUN` holds and what to check before reporting a number:
- `qt.csv` (targets): one row per file and target, never hidden; `state` `detected`, `forced` (a peak under `min_sn` or the shape minimum, numbers kept) or `absent`; `flag` (`no_peak`, `below_threshold`, `bad_shape`, `edge`, `in_blank`, `no_scans`); `sn`, `shape`, `peaks_in_window`. Report only `detected` areas as measured; say which are `forced`.
- `qt.log.json` (`quant-targets-log/1`): the automatic choices (`choices`: `key`, `value`, `reason`, e.g. `offset_reference.+` = `parent`, `smooth_half`) and the evidence of the m/z offset measured on the `parent` row of each file (`offset=auto`); check `evidence.n_scans` and `snr`: a blank has no parent, so its offset comes from a stray peak (1 scan); a file without a reference keeps 0 and a warning.
- `dig.json` (`tp.dig_lr`): ONE run digs every condition; `groups.conditions` lists each with its controls (`t0`, `blank`, `std`, `dark`) and the parent's first-order `k` (per min), `half_life`, `remaining` (on the test series `k` is 0.038 and 0.015 for rates of 0.035 and 0.015); `groups.rows[].cond[]` gives per condition `present`, `n_det`, `shape` (decay, rising, flat), `kin` (area per time) and the checks of `prev`; `present_in`, `only_in` say where a product is seen; `warnings` names what is missing (`condNoReplicates`).
- `exp.csv`: the aligned LR feature table with the samples' columns; `prov.json` and `report.json`: parameters, times and SHA-256 of every output.

Same bytes by one call: `mzlab-cli quant targets --targets MZML/targets.csv --offset auto --blank-pattern 'blank*' MZML/Blank_01.mzML MZML/t0.mzML MZML/Fe_t5.mzML MZML/Fe_t15.mzML MZML/Fe_t30.mzML MZML/Cu_t5.mzML MZML/Cu_t15.mzML MZML/Cu_t30.mzML --out qt.csv --log qt.log.json` writes the `qt.csv` and `qt.log.json` of the plan (tested).
Rows and `files[]` follow the order of the files given, so list them as `idx.in.source` does: a shell glob sorts them by name. Other settings: rerun the same `--out` with `--set qt.min_sn=5`, `--set dig.min_files=2` or `--set det.min_height=5000` (only the changed steps run again, `cached` in `prov/1`).

Variants: SIM/SRM files stored as chromatograms give `no_scans` rows in `quant.targets`; use the step `chrom.transitions` for them. Calibration from standards: the step `quant.curve`. The plan runs in the site too: import it in the Flow tab (`mzflow/2`), every step has a browser executor.
