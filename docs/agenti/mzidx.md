# `.mzidx`: the index of an mzML file (`mzlab/reader/mzidx.py`) or of a vendor file
A `.mzidx` is written once per file (`build(run, out)`) and read in slices (`open(path)`): the scan table plus, for each group of scans, the peaks sorted by m/z. Its users (`Run.table`, `PeakTable`) do not change: XIC, spectra and map read only the slices they need, and reopening does not reread the mzML data.

## Format (all little-endian, no compression)
```
0      HEADER, 64 bytes:  "MZIDX001"(8) | u32 version=3 | u32 flags=0 (bit 0 = READER_FLAG, a vendor file) | u64 meta_off | u64 meta_len | u64 scans_off | u64 scans_len | u64 total | 8 zero bytes
64     for each section, in the order of meta.sections, seven arrays each aligned to 64 bytes (zero padding):
         rt        n_scans × f8   minutes
         tic       n_scans × f8   TIC declared by the file
         scan_ids  n_scans × i8   index of the scan in the file
         sumint    n_scans × f8   total intensity of each scan, summed in table order (like np.bincount on the whole table)
         bp_mz     n_scans × f8   m/z of the highest peak of each scan (0 if empty; on a tie, the one higher in the table)
         bp_inten  n_scans × f8   its intensity
         fence     n_fence × T    first m/z of each block of 16384 peaks (n_fence = ceil(n_peaks / 16384))
         mz        n_peaks × T    all peaks, sorted by m/z (stable sort: on a tie, first the scan, then the order within the scan)
         inten     n_peaks × T    intensity, in the same order
         pos       n_peaks × i4   position of the owning scan inside rt/tic/scan_ids
scans_off  JSON UTF-8 (compact separators): list of rows, one per scan, in file order, with the columns of SCAN_COLUMNS:
         start,end (mzML bytes),level,rt,polarity,tic,precursor,collision_energy,filter,profile,parent,iso,act,res,an,pint,path,precursors,charge,native[,kind[,mob]]
meta_off   JSON UTF-8: {format:"mzidx", version, block, source:{name,size,mtime_ns,probe,sha256}, run:{nce,hr1,n_chromatograms[,scan_window][,chromatograms (mzML only)]},
                        keys:{"<level>/<all|+|->": section index}, sections:[{level,dtype,n_scans,n_peaks,n_fence,off:{rt,tic,scan_ids,sumint,bp_mz,bp_inten,fence,mz,inten,pos},crc32?}]}
total      file size: a file of a different size (truncated) does not open
```
- **`run.chromatograms`** (mzML index only; Rust builder and Python reference write it; empty when the file has none): the header of each `<chromatogram>` in file order, `[id, start, end, kind, q1, q3, ce, name, dwell, n]` (`start`/`end` = mzML bytes, `kind`: `tic`, `bpc`, `pda`, `pressure`, `srm`, `analog`, `other`; unknown numbers `null`).
  `chromlist.rs`: `scantable::read_in` reads them in the pass over the tail that counts them; `Index::open` seeds the `Layout`, so `lr_entry` does not scan the tail. An mzML index without a valid list is `error.badIndex`; nothing falls back to the file.
- **Versions**: 3 for an mzML and for a vendor file (3 with `READER_FLAG`). Versions 1 and 2 are `error.badIndex` and the site makes them again from the source (`manifesto.js`: `CORRENTI.idx`, `vecchio`); no converter.
- **`kind`** (21st column, only if the scan has a type): `PREC` (precursor ion, `MS:1000341` or `pr` of the Thermo filter), `NL` (`MS:1000326`, `cnl`), `NG` (`MS:1000325`, `cng`), `EMC` (`MS:1000789`), `TDF` (`MS:1000790`), `ER` (`MS:1000791`), only for MS2 scans or higher (`scantable::kind_of`); at every level `EPI`, `PI`, `EMS`, `Q1` from the `analyst scan type` userParam of the `.wiff` reader. `Scan::kind_name` gives the first six (a part of their own), `Scan::scan_type` the SCIEX experiments (any MS1/MS2 scan).
  An index with no types or mobility has 20 columns, as before; `idxread::Scan.kind`.
- **`mob`** (22nd column, only if the scan has a mobility as a scan attribute; the 21st is `null` if the type is missing): `[value, unit]` with unit `k0` (`MS:1002815`, 1/K0 in V·s/cm²) or `ms` (`MS:1002476`, drift time); `idxread::Scan.mob`. Per-point mobility arrays are not in the index: they are read from the scan (`Scansioni::mobilita`).
- **T** = `<f4` for the MS1 of a high-resolution file (`Run.hr1`), otherwise `<f8` (same rule as the in-memory table).
- **Sections**: one for each level × polarity (`all`, `+`, `-`: `+` takes scans of polarity +1 or 0, like `Run.table(level, 1)`); groups with the same scans share the section. `keys` says which.
- **Validity**: `source.size` and `source.probe` (SHA-1 of size, first and last 64 KB) describe the file (`source.mtime_ns` is 0; reuse checks as in `rust-mzidx.md`); `source.sha256` is the fingerprint of the whole file (from the OPFS copy or from `upload::impronte`, same value; `.mzflow` uses it).
- **Atomic write**: temporary file next to the destination, then rename; the header is written last.

## Index of a vendor file (version 3 with `READER_FLAG`)
A `.raw`, a `.wiff` (one index per sample) or a `.D` folder are indexed directly from the `Lettore` (`readers.rs`), without writing and rereading an mzML. Code: `crates/mzlab-core/src/mzidx_reader.rs`, `upload::prepare_lettore`, `mzidx::build_lettore`; test: `crates/mzlab-core/tests/readers_mzidx.rs`.
- **Head**: `u32 version = 3`, `flags` with bit 0 (`idxread::READER_FLAG`: the rows point to the members of the set, not to an mzML), other bits zero; in the meta `"version":3`. `idxread::Index::open` accepts only 3/0 (mzML) and 3/bit 0 (vendor file), anything else is `error.badIndex`; the Python reader only 3/0.
- **Rows**: the 20 columns of `SCAN_COLUMNS` except the first two: in place of `start,end` there are the position `[member,offset,length]` (`Posizione` of `Lettore::index`, `null` if the reader does not give it) and `k`, the scan number in `indice(c)`; the nativeID stays in `native`. `scanrow::scan_of_row` carries them into `posizione` and `k` of `idxread::Scan` (`start`, `end` = 0).
- **`source`**: the mzML keys (`name` = `upload::set_name`: `X.raw`, `X.wiff`, `X.D`; `size` = sum of the members, `mtime_ns`, `probe`, `sha256`) plus `members: [{name,size,sha256,probe}]` in `FileSet` order, `reader` (`upload::READERS_GENERATION`; older or missing: `native_attach` refuses it and it is rebuilt) and `sample: {id, nome}`; `lost: {declared, read, cause}` only on partial reading (`Losses::note`).
  With one member `sha256` and `probe` are its own; with several members they are the SHA-256 (SHA-1 for `probe`) of the member values, each followed by a newline, and then of the sample `id`. Fingerprints from `upload::impronte` before `readers::apri`.
- **Same as the mzML**: everything else is byte for byte the index of the mzML that `readers_mzml::scrivi` writes for that sample.
- Rows come from the scan, without text: `Rows::lettore` (`scantable/rows.rs`) builds the row from `Spectrum` + `SpectrumExtra` with the fields `Rows::spectrum` reads from the mzML head (`mzmlwrite::spectrum_head`, the test oracle and the path of a scan whose extras might change the text: `extra_inerte`, an `MS:1000...` in the id, the filter or the extras); TIC from the sum of intensities, filter and id as the writer writes them (with escaping), precursor, isolation window ±0.5, activation from the filter, resolution from `opentfraw.resolution`.
- The `Head` (analyzers, `nce`) comes from `Head::da_testata(&Header)` (`readers_mzml::testata`, a single `IC1`), without writing the document; with names that the text would break (`"`, `<`, `>`) it is written and reread. `n_chromatograms` counts the chromatograms the writer writes (known type, at least one point); the spectrum is the one the mzML would give back (arrays cut to the shortest, `mzidx_reader::spettro`).
- **Build**: `upload::index_reader` (the path of the site and the desktop) decodes every scan once per table and pass 1: `mzidx_reader::rows_before` gives `Table` and `Prima` (groups by level × polarity: peaks per bucket of 1 m/z, also rounded to 32 bit for MS1, and the peaks themselves as long as their capacity fits in `budget / 4`); `mzidx::build_after` derives the sections from them (union of the groups that admit, on equal m/z the earlier scan wins) and, if the peaks did not fit and there is no scratch file, repeats the decoding for every round of buckets.
- **Spillover** (`mzidx_spill.rs`, `upload::index_reader_with`): with a scratch file (trait `Spill`: `put`/`get` at offsets: `File`, `Cursor` or the callbacks of `build_mzidx_native`) the peaks beyond `budget / 4` in pass 1 go to the file as 20 B records (m/z f64, intensity f64, scan number u32) split into 64 m/z partitions (limits from the counts seen, 64 KB pieces, in scan order), and every round of buckets reads only the partitions that touch its buckets (and the bucket below for the 20 B MS1 records: at 32 bit an m/z moves up by at most one bucket).
- Rounds aligned to partitions: with scratch a round ends on the last partition boundary it contains (`mzidx_spill::allinea`), so every partition is read only once; the cap of a round stays `round_cap` (tests in `mzidx_spill_tests.rs`).
- Pass 1 in 32 bit: the MS1 groups of a high-resolution file (`hr1`, `<f4` sections) keep the peaks as `Peak<f32>` (12 B instead of 24: `Gruppo::f32`, `kept32`) and send them to the scratch already rounded, split by the bucket of the rounded value. `Prima::indovina` fixes it: for the mzML from the table before pass 1, for a reader from the first MS1 scan (`Rows::last_hr`) and if the table later says the opposite `build_after` throws away what pass 1 kept and the rounds decode again (tests `primo_ms1_*`). Same bytes.
- Sorting of the buckets (`mzidx_order.rs`, called by `Sec::flush`): stable LSD radix on the ordering bits of the m/z (and of the scan if `per_scansione`); for 64-bit peaks on the high 48 bits (about 1e-8 Th at m/z 500: HR ions repeated across scans do not make long runs of equals) and then comparison on the runs of equal keys; below 160 peaks `sort_by`. `Sec::emit` writes every column in fixed-width cells. Same bytes as the stable `sort_by` (tests `radix_is_the_stable_sort`, `hr_bucket_is_the_stable_sort`).
- Buckets in parallel (`sort_buckets`, native only; in the `.wasm` it stays sequential): in a round with at least 65 536 peaks the independent buckets are sorted on up to 8 threads (groups of consecutive buckets with an equal number of peaks); identical bytes (test `buckets_in_parallel_are_the_same`). Synthetic measurement (`SOLO=scratch DISCARD=1 mzidx_times 43000 560`, profile `desktop`): table + `.mzidx` with scratch 1.82 → 1.52 s; the rest is largely the first pass (~35 %), reading the scratch (~15 %) and writing the bytes (`emit`).
- Scratch record for the `f32` MS1 of a high-resolution file: 12 B (m/z f32, intensity f32, scan u32; `Parts::push32`, partitions separate from those of the 20 B records, same write order), because the values are already rounded as the section writes them; a record is added with one copy (`mzidx_spill::record`).
- Spillover, effects: decoding happens ONCE, whatever the size (`Stats.passes` = 1); the index bytes are those of the repeated-pass path (`tests/mzidx_rows_direct.rs`, same budgets). A round read from the scratch sorts equal m/z by scan (`Sect::per_scansione`): a peak whose bucket changes with 32-bit rounding sits in the neighbouring partition and would arrive before the earlier scans (test `equal_after_rounding_between_two_buckets`).
- Spillover also for the loaded mzML: `mzidx::build_mzml_spill` / `build_with_spill` (same `Spill`), in `build_mzidx` of the `.wasm` (`spill_put`, `spill_get`) and in the `idx-worker.js` worker (file `<name>.mzidx.sp.part` in OPFS for every build, mzML and vendor samples). Without a reserve (`build_mzml`) the repeated passes remain. Speed test: `cargo run --release -p mzlab-core --example mzml_times -- genera F.mzML 44000 1500` and then `-- F.mzML 64` (without and with the reserve).
- Coalesced writes on the site (`coalesce::Accorpa`): in `build_mzidx` and `build_mzidx_native` of the `.wasm` the output, the `.cen.mzidx` output and the scratch go through a wrapper that merges contiguous writes into 1 MiB blocks, with up to 8 pending blocks for the output (`Accorpa::flussi`: the section columns are written in turn, each resuming where it stopped; 557 writes become 178 on 422 MB of a `.raw`) and one for the scratch (every call to JS is an OPFS write with a check reread in `writeFull`).
- Blocks to JS as views (`lend` of `natives.rs`: `write`, `write_cen`, `spill_put`): `Uint8Array` on the engine memory from `wasm_bindgen::memory()` (no `unsafe`), valid only during the call: the callback writes it at once, does not keep it, does not call the engine. Test: `tests/test_mzidx_views.py` (all views, same `.mzidx`; keeping them without a copy gives a wrong index).
- Coalesced scratch: the scratch `put` calls merge also across the unwritten tail of a 64 KB piece (zero-filled, never read) and a `get` sends the pending block first; in the output a write that covers a pending block of another stream sends it first. Same index bytes (`crates/mzlab-core/tests/coalesce_build.rs`); app and CLI write to files as before.
- Decoding in helpers (site): with isolation `idx-worker.js` starts `creaAiuti` (`idx-aiuti.js`) and passes `aiuti` `{send, take, window}` to `build_mzidx` (`courier.rs`); the parser (`mzml::parse_corriere`, `help/courier.rs`, trait `Corriere`) sends the arrays of every spectrum as a job on a `SharedArrayBuffer` slot, an `idx-aiuto.js` worker decodes it with `decode_job` (`Decodificatore`, the same `decode_peaks` as the parser) and the answers are put back in file order. Window of 4 jobs per helper; a lost or refused answer = the spectrum is decoded on the parser.
- Number of helpers: `aiutiPer` (`idxpool.js`): alone `poolSize` (= min(4, cores − 1)), with other files the free slots, never just one (it costs more than it yields), 0 without isolation (same code with window 0). Same bytes at every N and as native (`courier_tests.rs`, `tests_e2e/e2e_indice_parallelo.py`).
- Fingerprints in parallel (native only): `upload::prepare_late` reads the scan table while a second thread computes SHA-256 and `probe`; `mzidx::build_mzml_late` asks for the `source` object only when it writes the metadata, at the end, so the hash does not delay decoding. Same bytes as `prepare` + `build_mzml_spill` (`tests/upload_late.rs`); the CLI `build_index_with` uses it when the SHA is not already known.
- CLI/Flow index (`flow_pace::build_index_with`): peaks beyond the budget go into a reserve file `NAME.mzidx.scratch` (removed at the end of the job), so the mzML is decoded once and not once per round; same bytes at every budget (`flow_pace_tests.rs`).
- Where the scratch lives: on the site `idx-worker.js` opens a second OPFS file `<name>.mzidx.sp.part` (removed at the end; if the worker dies the `.part` cleanup removes it); desktop: `<name>.mzidx.sp.part` in the cache folder, for the mzML and for vendor samples. The scratch file weighs ~20 B per peak, 12 B for the `f32` MS1 (24 M peaks ≈ 490 MB): it takes storage space while the build lasts. Without scratch (`index_reader`, `build_lettore`) the old repeated decoding remains.
- Reading the sources: `idx-worker.js` (mzML) and `buildNative` (members of vendor sets) read the copy in `files/` with a read-only `SyncAccessHandle` (`lettura-sync.js`, `openSource`); if it is not available (unsupported, file busy with a writer, size different from the Blob, file missing) they read the Blob with `FileReaderSync`. Test: `e2e_lettura_sync`.
- **Fingerprint in parallel** (desktop, CLI `index_reader`): `upload::with_parallel_prints` computes SHA-256, SHA-1 and `probe` in a second thread while `rows_before` decodes; members opened by the reader carry an empty SHA-1 (`without_sha1`) and `index_reader_with` asks for the fingerprints once the table is ready; in the CLI the thread stops after a cancel or an error, and does not start if `flow_set::digest` has already read every member (`known_prints`: only the `probe` values). On the site the fingerprint is taken during the copy into OPFS.
- `fase(3)` fires when the table is ready. `prepare_lettore` + `build_lettore` (two separate passes, same bytes) remain for tests and for measuring the table alone (`raw_times`, `mzidx_times`). Test: `tests/mzidx_rows_direct.rs` with the fake reader `tests/fake_reader/`.
- **Scan source** (`source.rs`): `Scansioni` (`spettro(riga)`, `intestazione(riga)`) and `Tracce` (`cromatogrammi`, `cromatogramma(id)`, `testata`), each with two implementations: the mzML by offset (any `ReadAt`, mzML rows; `MzmlTraces` over `Mzml`) and a sample of a `Lettore` (`ReaderSource`, vendor-file rows). The scan routes (`hrscans`, `hrroutes`, `hrscanbin`, `profspec`, `msnroute`, `scaninfo`, `sniff`) read through `Scansioni`.
- **Routes that read beyond the index** (head, chromatograms, method, `scaninfo`, scan window): they read a `ReadAt` that names its `Lettore` (`ReadAt::lettore`, `None` for an mzML). For a vendor file it is the sample `guscio` (`readers_mzml::guscio`: the `scrivi` mzML without spectra, with an empty `spectrumList`, the chromatograms and the polarities present in a comment before `</run>`) plus the reader; the text of a scan is `source::scan_text` (the head that `scrivi` would write). Test: `same_routes` (`tests/readers_routes/`): same JSON for the two ways.
- **Centroids**: `readers_centroids::centroidato(l)` gives the same reader with profile scans reduced to one point per peak (`centroidi`, parameters from at most 64 scans per sample, head `centroided`), like the `.wiff` conversion with "centroids": for `.wiff` the conversion goes only through the reader, plain or centroided; the `.raw` read by the reader has the vendor centroids.

## Build (`build`)
1. The scans are already in the `Run` table: with an `indexList` (indexedmzML) the spectrum positions come from there and only the headers are read (up to `<binaryDataArrayList`), never the binary data; without `indexList` the file is walked (`Run._spans`).
2. Every scan is decoded once (`Run.read`) and its peaks go, in groups of ~1 M peaks, into buckets of 1 m/z unit (0…9999, out-of-range values at the extremes); beyond `BUILD_BYTES` (64 MB, split among the sections) the buckets are dumped to a temporary file. Memory stays bounded: the whole file is never concatenated.
3. Bucket by bucket, in m/z order, it is sorted stably and written into the three arrays; the first m/z of every block enters `fence`.
The result is identical to the in-memory table (`Run.table_reference`): `tests/test_mzidx.py` checks it on all example files and on the synthetic ones.

## Reading
- `open(path)` → `MzIdx`: `meta`, `scans()` (the `Scan` objects as the mzML reader gives them), `table(level, polarity)` → `PeakTable` whose `mz`, `inten`, `pos` are `LazyArray`.
- `LazyArray`: `a[i:j]` reads the slice (up to 2 blocks from the cache in blocks of 16384 elements, beyond that directly from the file); `searchsorted` uses `fence` and reads a single block; masks, operators and `np.asarray` read it whole (temporarily).
- **Block cache**: LRU shared by all files, cap `CACHE_BYTES` = 64 MB (`CACHE_BYTES_SMALL` = 32 MB on tablet and phone, `set_cache_limit`). The cap lives only in `mzidx.py`. The blocks of the active file (`Run.activate()`, called by `/api/chrom`) are the last to go. TIC and base peak of every scan are in the index (`sumint`, `bp_*`): opening a file reads no peak.
- `PeakTable.iter_chunks()`, `sum_by_scan()`, `base_peaks()` walk the table in pieces (sums in the same order as `np.bincount` on the whole table, hence bit-for-bit equal).

## Where it lives
`Run.table` builds the index at the first request (declared TIC and scans come from the mzML, no need before) in `$MZLAB_CACHE` (default `~/.cache/mzlab`; `index_name`: SHA-1 of real path, size and date) and opens it; on reopening `Run` takes scan table, fingerprint and counts from the index and does not walk the spectra. If the index cannot be written, `Run.table` builds the table in memory (`table_reference`). `mzidx.trim(folder, limit)` deletes the oldest.

## On the site (`rust-worker.js`, `archivio.js`)
- **Storage**: OPFS, folders `mzlab/files/<name>` (the mzML files) and `mzlab/idx/<name>.mzidx`. Only the Rust workers (engine and index builders) touch OPFS; every write handle is opened for one write and closed at once; reading is a `File` (`getFile`) read in slices by the engine. Without OPFS (`FileSystemFileHandle.createSyncAccessHandle` missing) the page says `load.err.oldBrowser`.
- **Loading** (site): the page sends every `.mzML` as a Blob; `lr_put` writes it into OPFS in blocks (SHA-256 and probe taken during the copy and passed to `prepare_upload`), `prepare_upload` derives from the headers what the builder needs (level, polarity, RT, TIC, JSON rows, `source`, `run`, `hr1`), a worker of the **Rust pool** (`rust.md` and `measurements.md`; `idxpool.js`, `idx-worker.js`, `mzlab-wasm::build_mzidx`) builds the `.mzidx` and writes it into OPFS as `<name>.mzidx.part`; then `ARCH.promote` gives it the final name (never a half file with the real name) and the engine opens it.
  Only then does the upload answer go out (list with type read from the content): the load table fills as the indexes become ready.
  In the desktop app the native side builds it (`idxbuild.rs`, `rust.md`) reading the file in slices.
  The Python builder (`mzidx.build`) remains the reference of the parity tests, not an execution path.
- **Reopening**: at startup `lr_boot` opens every OPFS index (`lrOpen`, same file by name); the engine recognizes the index by size and fingerprint (`probe`) and takes scans, `sha256` and counts from the index: no spectrum reading, no 300 MB limit. A file with the same name but other content makes the index be discarded (rebuilt); an mzML without an index (interrupted load) is indexed again at startup.
- **Migration**: files saved in IndexedDB (`files`) by earlier versions move into OPFS at startup (`lrMigrate`) and are deleted from IndexedDB only after a successful write; those that do not move stay where they are. The names `qqq_lab`, `qqq.*` do not change.
- **Space**: the gear (site only) shows how much files and indexes take and "Libera" deletes the indexes of removed files (always first, even alone when the quota exceeds 80%); a deleted index rebuilds itself. `navigator.storage.persist()` is requested at the first save, with no message if refused. "Nuova sessione" and "Ricomincia da capo" empty OPFS.
- **Low space**: `ARCH.ensureRoom(bytes, name)` counts file and index (×1.8) and reserves the space until the end of `lr_index` (`ARCH.release`), without counting the same space twice. Chromium accepts writes beyond the quota and leaves the file shorter: `idx-worker.js` and `archivio.writeNow` compare `getSize()` with the bytes written (`error.quota`; `error.quotaWrite` if the browser declares space for the rest: `quotaError(total, written)`: MB written, of the file, declared free); an index that does not open is deleted (`error.badIndex`). Tests: `e2e_carica_grandi.py`, `test_archivio.py`.
- **Opening during reading**: no button to press; every file opens as soon as it is read (`OPENNOW`, also while `upload()` has other files being read, `UPBUSY` in `shell.js`) and phase and % (event `mzlab-index`, `waitStato`, keys `load.ph.*`) are in the progress rows of the side list; the names of unread files are in `MZLAB_LOADFAIL` and mzFinder reports them before "Dig".
- **In-memory mzML table** (`scantable::read`): every spectrum head immediately becomes its row (no list of heads) and `Table::drain_json` frees the rows while writing their JSON (`upload::from_mzml_table`): peak about 1.5 KB per scan (145 MB on 100 000). The bucket rounds of the builder use half the `budget` minus what the builder keeps anyway (row JSON, membership lists, per-scan arrays); a bucket that does not fit gives `error.memoryBudget` with `{fase: index, stima_mb, budget_mb, eccesso_mb}`.
- Memory test: `tests/mzml_big_memory.rs` (counting allocator, same bytes at every budget, with and without reserve); `mzml_times` prints the heap peak per phase.
- **Memory**: the index builders have a `budget` (64 MB, 32 on iPad/phone; `error.memoryBudget` if not enough); the engine keeps in memory the scan table, `rt`, `tic` and the totals of every file, not the peaks (`Run.table` and Python `CACHE_BYTES` are the reference).
- **Ion mobility in mzML**: `info.acq` adds "IMS" and `info.ims` ({unit, min, max, n}) when the file has a mobility (scan attribute or array, `Facts.ims`); `/api/scan` carries `mob`, `mob_unit` (per-point array) and `mob_scan` only for scans that have it.
- **Label of the parts of a mixed file** (`x.mzML#MS1`): written by the engine (`part_label` in `iteminfo.rs`, used by `lr.rs`): "Full Scan", "DDA" (MS2 all tied to a precursor), "MS2", "Precursor ion", "Neutral loss", "Neutral gain", "EMC", "TDF", "ER" (scans with a type, `Scan.kind`, form parts of their own; `acq` lists them before DDA/MS2) or "MRM", with the polarity suffix; saved notebooks with labels "· MS1" are converted there.

- **Proposal (to decide): optional `exp` column for `.wiff`**. The nativeID `sample= period= cycle= experiment=` gives the experiment but not its scan code (EPI, PI, EMS and Q1 are carried by the `kind` column, Prec and NL by their CV term; MS3, ER, Q3 are not) and the period is always 1 (the reader reads only `Period0`). An `exp` column (u16 period, u16 experiment, u8 code of `modes.rs`; 0xFF = absent) in the version 2 index would give the channels the periods > 0 and the codes without a term.
