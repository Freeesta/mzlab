# Workflow plans `mzflow/2` and `prov/1` (`mzlab_core::flow`)

Reads a workflow file, checks the whole plan against the `step/1` descriptors before anything starts, resolves every instance to its canonical parameters, runs the plan in a fixed order and writes the `prov/1` record. Pure Rust, no I/O and no clock: the caller owns the files and the time (`mzlab_cli::flow::FileRunner`). Contract `docs/studi/workflow/contract.schema.json`, study `docs/studi/WORKFLOW_MODULARI.md`. Nothing here changes a step result or shows in the UI; the `err.flow.*` keys are not in `lang/` until a screen shows them.

## Functions
- `flow::parse(bytes) -> Plan` (`parse.rs`): `mzflow/2`; a file with no `format` is read as `mzflow/2`; the keys of `mzflow/1` (`formato`, `programma`, `operazioni`) are still read (`Plan::operations` is kept untouched); anything else is `err.flow.format`.
- `flow::check(plan, registry, platform) -> Vec<Problem>` (`check.rs`): every problem, in file order, cycles last. `Problem{instance, port, error_key, params}`; keys: `err.flow.step.unknown|version`, `instance.duplicate`, `unavailable` (no module for the platform: `Platform::Native|Wasm`), `algorithm.unknown|unavailable`, `preset.unknown`, `param.unknown|type|range`, `port.unknown|missing`, `input.unknown`, `ref.unknown`, `type`, `cardinality`, `facet`, `cycle`.
- `flow::conversion_path(registry, from, to)`: the shortest chain of registered conversion steps (`Step::converts`); the check accepts a wire that has one.
- `flow::canonical(instance, step) -> Resolved` (`canon.rs`): algorithm default, then preset, then the differences written in the file; sorted keys, shortest numbers (`Resolved::text()`); `params_sha256()` is the SHA-256 of that text without the `noresult` parameters; `flow::cache_key(input hashes, step, algorithm, params_sha256)`: the key of the cache of a run folder (`mzlab-cli`, `flow_cache.rs`; `cli.md`; no item position in it); `flow::value_text` is the canonical JSON of a Value.
- `flow::line`, `apply_sets`, `line_route` (`line.rs`): the short line `mzlab-cli flow run … --set I.N=V` of a plan and a line's `--set` applied to it; `err.cli.set|line`.
- `flow::plan_order(plan)` and `flow::levels(plan)` (`order.rs`): Kahn's sort, ties in file order; `levels` groups what can run together; a cycle is `err.flow.cycle`.
- `flow::execute(plan, registry, runner, workers) -> Run` (`run.rs`, `run_sched.rs`): checks, then takes the ready jobs from `flow::sched` and runs them on `workers` threads (native only; in sequence on the wasm) as soon as the jobs they read are done, so a `per_item` step starts on a file as soon as it is made upstream. `Runner::run(&Job)` is the caller's.
  The record is written by level, so it does not depend on `workers`; a `many` output of a `per_item` job is keyed `inst.port[<input name>]`, never by index (naming and `Job::item_name`/`item_root`: `flow-live.md`). A failed instance gets an `error`; only its descendants are left out (`Run::skipped`).
- `flow::prov_json(agent, plan_sha256, run)` (`prov.rs`; `build_agent` makes the `Agent`, `cli.md`): the `prov/1` text; entities `file:NAME`, `INSTANCE.PORT[i]`; one activity per instance with `references` (citation keys of step and algorithm).
- `flow::prov_json_llm(agent, plan_sha256, run, Option<&LlmRef>)` (`prov.rs`): come `prov_json` più, se un assistente ha lanciato la corsa, il blocco `llm{log_sha256, turn, provider, model, level}` (`$defs/prov1`, chiave facoltativa); con `None` i byte sono identici.
- `flow::corsa_build(&prov, &[Uscita]) -> Corsa` (`corsa.rs`, `Corsa::json()`): the `corsa/1` report of a run (`docs/schemi/corsa-1.json`) from the `prov/1` Value and the named files of the run folder: engine, `plan_sha256`, `inputs` and `lists` (types `library`, `transform`, `structure`) with SHA-256, per instance the status (`ok|cached|error`), `ms`, `mem_mb`/`via` (align and gapfill), `params_sha256` and every parameter as `estimated` (with its proof) or `fixed`, `total_ms`, level counts of the `annot/1` files (`auto` apart from rows with `auto:false`) and the `report/1` file untouched.
- `mzlab-cli flow report RUNDIR [--out FILE]` (`flow_report.rs`) reads `prov.json` and the `.json` files beside it.
- `RAPPORTO_FLOW.render(el, corsa, {sections})` (`mzlab/web/rapporto-flow.js`, classic script, `// @ts-check`, English only, no `lang/` keys; nobody loads it yet: the "Report" button is the Flow screen's): lays out a `corsa/1` object in one column (summary, inputs and lists, plan and parameters, timing, counts, quality control); a toolbar turns each section on or off, "Download JSON", "Print" (left out of the print). The timing figure has its table right under it; levels counted `auto` apart; same JSON, same HTML.
  Test: `python3 tests_e2e/e2e_rapporto_flow.py` serves the module alone (no engine): sections, tables, escape, toggles, download, PDF, axe, `MISURA rapporto_flow` (< 3 s).
- `mzlab_cli::flow::{steps, table_step, FileRunner, run_plan, run_plan_cached}` (`crates/mzlab-cli/src/flow.rs`; `run_plan_cached` keeps the cache of the output folder): the registry (with `features.table@1` and the identification descriptors of `attributio()`), the runner of files and the whole run with its `prov/1`; `examples/flow.rs` is the thin caller. The steps it executes are the table `EXECUTORS` (list in `cli.md`); `run_plan` refuses a plan with a step outside it (`err.flow.step.native`). `flow::plan_json` writes a plan back (`plan.json` of `flow run`).
- `mzlab_cli::flow_ms2::{ms2_step, ms2_text}` (`flow_ms2.rs`, descriptor in `docs/schemi/steps-cli-1.json`): `spectra.ms2@1` turns the MS2 scans of mzML files (`source`, many) into one MGF `spectra` file: `TITLE` and `SPECTRUMID` = `<file>.<scan>` (the query id of `spectra.match`), `PEPMASS` (m/z and intensity), `CHARGE`, `RTINSECONDS`, `SCANS`, `IONMODE`.
  Parameters: `min_intensity` (weaker peaks go; an empty scan goes) and `max_isolation` (off when absent; a scan with no window stays). 
  The optional port `features` (the CSV of `features.table`) keeps only the scans of a feature (present in that file, precursor within `tol_da`, RT within `rt_tol`, closest in m/z) and sets `SPECTRUMID` and `FEATURE_ID` to its id, so the `annot.level` join works; replicate scans share the id. Charge, precursor intensity and window offsets (`MS:1000041`, `MS:1000042`, `MS:1000828/9`) are read from the text of each `<spectrum>`: `mzml::Spectrum` does not keep them.
- `mzlab_cli::flow_match::match_text` (`crates/mzlab-cli/src/flow_match.rs`): `spectra.match@1` on files. `query` is MGF/MSP/MassBank/JSON, `library` the same or a `.mzlib`; `precursor_da` > 0 replaces the ppm window with one in Da (unit-resolution queries; use `tol_da` 0.3-0.5; `mass_ppm` stays in ppm; the query port asks for MS2, not for HR); `name_contains` keeps only library entries whose name has the text (any case).
- `spectra.match@1` algorithms `spectral_entropy` (default, gates `min_score` and `min_shared`), `cosine` and `modified_cosine` (exact matches plus analogues of `search::analogs`); the engine is `mzlab-lib` (`search::identity`, `scores`).
- `spectra.match@1` algorithm `tree` (`flow_match_tree::tree_text`): `query` is the graph `msngrafo/1` of `spectra.msn_graph` and `library` an `msnlib/1` file (the query port also takes a `report`; the library is an input the user declares, never derived from raw files); `precursor_ppm` (or `precursor_da`, turned into ppm of the root of the graph), `tol_da`, `top_n` and `min_prove` feed `msngrafo::cerca`; `name_contains` keeps the entries whose id or private name has the text; `decoys` does not apply.
- `tree_output` of `tree`: `msncerca` (default) writes the `msncerca/1` text, the same bytes as `mzlab-cli msn-lib search`; `candidates` writes `candidates/1` (query = root of the graph; `score` = MS2 entropy similarity, which `annot.level` reads as an entropy; the tree and loss scores and the proofs in the `tree` block).
- `spectra.match@1` `decoys` (`none`, default, or `spectrum`; not with `tree`; an `.mzlib` is rebuilt from its targets with the decoys): a decoy per library entry (`decoy::with_decoys`), never listed, scored like the targets with the algorithm's own score (entropy, cosine, modified cosine: q counts the exact-precursor window); the header carries `decoys` and `fdr_note` (`lib.fdr.note`, a lower bound) and the best hit(s) of each query `decoy_q`, `decoy_targets_ge`, `decoy_ge`, `best_decoy` (other hits `decoy_q` null); q is the one of `decoy::search_fdr` on the batch.
- `flow_tablematch::table_match_job` (descriptor `mzlab_feat::steps::table_match`): `table.match@1` compares the MS2 of every row of a multi-sample `.mzfeat` with a library. Ports `table`, `samples`, `index` (many, MS2), `library`; `ms2_spectrum` (`best`|`consensus`) and `ms2_background` pick the row spectrum as `ms2_file` does (query id = row id); the other parameters and the `candidates/1` out are those of `spectra.match`. A filter view is refused (`err.flow.export.view`), a missing index gives `err.flow.tablematch.files`.
- `flow_lookup::lookup_job` (descriptor `flow_lookup::lookup_step`): `spectra.lookup@1` writes as MGF the entries of the `library` the user declares (`.mzlib`, MSP, MGF, MassBank) whose `by` field (`name` contains `value`, any case, or the whole name with `exact`; `formula`, `inchikey` (14 letters = first block), `accession` whole; `precursor_mz` within `ppm`) matches, the first `top_n` in the order of the library, peaks untouched; the MGF is a query for `spectra.match`. No built-in library, no network. Test `flow_lookup_tests`.
- `flow_chimeric::chimeric_job`: `spectra.chimeric@1` on an MGF `spectra` and `index` files (mzidx, many): each block is matched to its MS2 scan (RT, window centre) and gets `PURITY` (`fill_purity_with`) and `CHIMERIC`; with the `features` table (`.mzfeat`) also `INTRUDERS=id:dmz:drt;…` (`window`, `rt_tol`). `PURITY` is the share of the MS1 intensity inside the scan's own isolation window (from the index, not a fixed width) within 5 ppm of the precursor; `CHIMERIC` is purity < `purity_min` (0.8); wider windows flag more; `PURITY_BAND` low/medium/high.
- `flow_chimeric` (algorithms): `ms1_window` adds `MS1_COISOLATED=mz:rel;…` (top 3), `MS1_COISOLATED_N`, `MS1_CAPPED` (`ms1_window_metrics`, `chim_rel`, `chim_cap`). Peaks untouched; `window`/`rt_tol` belong to `intruders`; with `library_deconvolution` and the optional `library` port also `DECONV=name:share;…` and `DECONV_RESIDUAL` (`ms2_engine/deconv.rs`: non-negative mix of the library spectra within half of `window`; `tol_da`, `min_share`).
- `mzlab_cli::flow_insilico::insilico_text` (`flow_insilico.rs`): `spectra.insilico@1` on files. `spectra` is MGF/MSP/MassBank/JSON, `suspects` a local CSV list (`ms2_engine::insilico::read_candidates`); the `candidates/1` hits carry `source: insilico`, `algorithm: fragmenter`, the explained peaks and `mass_ppm`; `annot.level` skips them (a hypothesis, never library evidence). No network.
  Output: JSON `candidates/1` (`hits[]` with `query`, `id`, `name`, `inchikey`, `smiles`, `formula`, `score`, `shared`, `library_peaks`, `explained`, `mass_ppm`, `precursor_delta`, `source`, `algorithm`), queries in file order, best score first, at most `top_n`.
- `mzlab_cli::flow_formula::{ms1_text, ms2_text}` (`flow_formula.rs`): `formula.ms1@1` reads the CSV of `features.table` (`features`, accepts `report`) and the mzML files (`index`, accepts `mzml`); for each feature it takes the MS1 scan closest in RT, in the file where the area is largest, and runs `formula_id::identify` (parameters from the descriptor; `max_charge` and `require_c13` go to the isotope finder).
  Output `formulas/1`: `features[]` with `id`, `mz`, `rt`, `file`, `scan` and `result` (the `formula_id/1` text), or `error` for a feature that has no scan or that the search cannot treat; a wrong parameter stops the step. The step is not `per_item` because the table needs every file.
  `formula.ms2@1` reads the spectra (MGF/MSP) and the `formulas/1` files; every candidate whose ion fits the precursor within `ppm_ion` explains the cleaned peaks (`prep_ms2`) with `review::explain::explain` (`subformula`, with the decoy share) or `rearrange::attribute` (`h_rearrangement`). Output `formulas/1`: `spectra[]` with `candidates[]` (feature, formula, adduct, ion, `ppm_ion`, `frac_explained`, `fragments[]` with formula, `mz_th`, `ppm`, `loss`, `shift`), best first.
- `mzlab_cli::flow_level::{assess, level_text}` (`flow_level.rs`): `annot.level@1` (algorithm `cascade`) gives each query of the `candidates` and `formulas` files the level its evidence reaches. `assess` is the rule of `mzlab/web/livelli.js` read from `crates/mzlab-feat/data/livelli-1.json` (profile `mzlab`; `lr` caps at 4): the gates `prec`, `score`, `shared` (threshold of `picchi_min_pochi` when the library entry has fewer than 6 peaks) decide whether a library hit is 2a, the `scans` and `distinct` gates only 3a (confirm),
  a lower score above `entropia_provvisorio` is 3a, a modified-cosine analogue 3b, a single candidate formula 4, nothing 5.
  It is not the Attributio cascade of `attributio/annotate` (Campaign, CSI:FingerID, CANOPUS) and the parameters of the descriptor (the fields of that cascade) are not read. Level 2b is never given and there is no standard (L1) port.
  Output: JSON `annot/1` (`rows[]` with `id` = the query id, `level`, `why` (`2a`, `confirm`, `provvisorio`, `analogo`, `formula`, `none`, `empty`, `tetto`), the best hit `name`/`entry`, `analog`, and the `gates` with `value` and `threshold`).
  Only `spectral_entropy` hits can be the best hit (the gate `score` is the entropy); hits of the other algorithms with the same precursor are not ranked. `scans` is the number of queries whose best hit is the same structure (replicate spectra), `distinct` the lead over the best hit of another structure, `formulaUnique` one candidate formula for the query id in a `formulas` file.
- `mzlab_cli::flow_compare::{check, expand, compare_text}` (`flow_compare.rs`): `meta.compare@1` is native only and has no ports of its own.
  `check` is the checker of a plan that may hold comparisons, with the answers of the page (`F.validateExtra`): the plan without the comparisons goes through `flow::check` (a wire from `<id>.comparison` is `ref.unknown`), then per comparison `step.unknown` (also a missing `step`), `step.version`, `compare.few` (under two variants), `algorithm.unknown|unavailable` and `compare.sameVariant` (once per repeated variant; the parameters are compared sorted), appended after the other problems.
  Cases shared with the page: `crates/mzlab-cli/tests/data/flow_compare_cases.json` (rewritten by `MZLAB_UPDATE_FLOW_CASES=1 cargo test -p mzlab-cli --lib the_shared_cases`, run by `tests/test_flow_grafico.py` on `flow-check.js` + `flow-compare.js`).
  `run_plan` checks as written, then expands each instance of it into one instance per variant (`<id>~<label>`: the wrapped step `params.step` with the `algorithm`, `preset` and `params` of the variant, the same `in`) and a compare instance that reads their outputs, so every variant has its own activity, canonical parameters and cache key in the `prov/1` record.
  The wrapped step must have one output of type `candidates` or `annot`; the compare writes `comparison/1` (per pair of variants: keys in both, best values that agree, keys in one only, mean overlap and mean Spearman correlation of the ranked ids; per key: best value of each variant). The expansion alone refuses what `check` does not look at: `err.flow.compare.variants` (empty label, a comma in a label, a repeated label), `.step`, `.type` (the wrapped step has no single `candidates` or `annot` output).
  The compare instance takes the tolerances `mz_tolerance_ppm`, `mz_tolerance_da`, `rt_tolerance_min` (numbers ≥ 0, not used by the comparison yet). Outputs of the variants cannot be wired to other steps; only `<id>.comparison` can. Tolerances for feature tables come with a native feature-detection step.
- `mzlab_cli::flow_network::network_json` (`flow_network.rs`): `tp.network@1` on a `.mzfeat` with `tp/1` and `interp/1` (`rete/1`, `docs/agenti/rete.md`); the step descriptor is that of `mzlab-feat` (`steps::tabui()`), added to `steps()` of `flow.rs`.
- The executors `flow_match`, `flow_ms2`, `flow_formula` and `flow_level` take names and bytes (`flow_match::Named` = file name and content, or `&[u8]` for the JSON/CSV of a previous step) and return the text of the file they make: no path, no `std::fs`, so a runner that gets its files from elsewhere (the browser) calls them unchanged; reading and writing files, hashes and the clock stay in `flow.rs` (`FileRunner`).

## Tests
- `cargo test -p mzlab-feat --test flow`: the four blocks of `docs/studi/workflow/PROVE_SU_CARTA.md` give exactly the problems written in the test; types, cardinality, facets, ranges and cycles; canonical form (key order, `1e5` against `100000`, an explicit default, a `noresult` parameter); 1 and 4 workers give the same record but for `ms` and `heap_peak_bytes`; an error stops only the descendants.
- `cargo test -p mzlab-core --lib flow`: parse and order.
- `cargo test -p mzlab-cli --lib flow_ident`: a plan of `spectra.match` on a synthetic three-compound library (`flow_ident_tests.rs`, shared by the next identification executors): each algorithm finds the library spectrum, the modified cosine reaches an analogue 100 Da away and the cosine does not, same bytes on a second run, `top_n` and `min_score` obeyed; `decoys=none` gives the same bytes as no parameter and `decoys=spectrum` the q-values of `decoy::search_fdr` on a synthetic mix of 80 standards and 90 queries.
- `cargo test -p mzlab-cli --lib flow_ident` also runs `features.table` → `formula.ms1` → `formula.ms2` on a synthetic caffeine mzML and MGF: C8H10N4O2 is a candidate of the feature and explains the 138.0662 and 110.0713 fragments with both algorithms, an odd peak stays unexplained.
- `tests/test_flow_determinismo.py`: a synthetic plan on `tools/dati_sintetici.py` files run twice natively (1 and 2 workers) and once as `wasm32-wasip1` under node (`tools/wasi_run.mjs`) gives the SHA-256 constants written in the test; `prov.json` validates `$defs/prov1`.
- `mzlab_cli::flow_msngraph::{msn_graph_step, msn_graph_text}` (`flow_msngraph.rs`): `spectra.msn_graph@1` (`source` = one infusion, an mzML or any dataset a reader takes, e.g. a Thermo `.raw` (written as mzML in the work folder first); out `graph` = `msngrafo/1`) with the options of `mzlab-cli msn-graph` as parameters (names in `msn_graph_step`; `scelte` = `MZ=ION,...`); same bytes as the command.
  The root can be given by name: `molecule` (name, synonym, id or formula) is looked up in the optional input `molecules` (a `molecules/1` CSV the user supplies: no catalogue is built in, no network) and gives `FORMULA adduct` (`adduct`, default `[M+H]+`) and the SMILES; `formula` wins when both are set; a name not in the list, or matching several molecules, stops the step (`err.flow.param.type`).
  Tests: `cargo test -p mzlab-cli --lib flow_msnraw` (a synthetic mzXML stands for the vendor file).
- `mzlab_cli::flow_msnlib::{library_step, table_step}` (`flow_msnlib.rs`): `msn.library_export@1` (`graph` = `msngrafo/1` of `spectra.msn_graph`; out `library`, MSP or MassBank) writes one record per spectrum of the tree through `mzlab_core::msngrafo::export_text`, the writer of `msn-lib export` (`format`, `levels` all|ms2, `clean` = `--pulito`, `annotate` = `--annota`: sub-formula and neutral loss of each explained peak, `id`), so the bytes are those of `msn-lib add` + `export --tutti`; its out type `library` goes into `spectra.match`.
  `msn.table_export@1` (out CSV) has the tables `view` = `modifications` (one row per measure of each arc: neutral loss mass, formula, ppm, tree, activation, CE, scans), `nodes` (ion, proposed sub-formula, ppm, source) and `peaks` (`clean`). Both read the graph text and stop on a file that is not a graph (`err.msnlib.bad`). `cargo test -p mzlab-cli --lib flow_msnlib`.
- `mzlab_cli::flow_centroid::{centroid_step, job}` (`flow_centroid.rs`, descriptor in `docs/schemi/steps-cli-1.json`): `spectra.centroid@1` (`source` mzML, one per item; out `mzml`) is a file-to-file step before `index.mzidx`, not an optional input of `features.detect`: the index and the detector stay as they are, so a series already in centroids gives the same bytes with or without it (its mzML passes through byte for byte and keeps the sample name; test `flow_centroid_tests`).
  A profile mzML goes through `centroidi::mzml_to_centroids_with` (the conversion of the archive; parameters estimated on at most 128 scans). `fwhm` (Da) and `threshold` (sigma) replace the estimates and are reported as `estimates` when left out; the code has no other algorithm and no relative/absolute threshold. `cargo test -p mzlab-cli --lib flow_centroid`.
- `cargo test -p mzlab-cli --lib flow_ms2`: a synthetic DDA mzML (MS1, two MS2 scans; with a feature table only the scan at the feature stays and the matcher hit carries the feature id; charge, window and precursor intensity added to the text) gives the MGF with only the MS2 scans, the plan `spectra.ms2` → `spectra.match` finds the library entry with the id `dda.<scan>`, the thresholds drop peaks and scans, same bytes twice; the export equals `docs/schemi/steps-cli-1.json` (`MZLAB_UPDATE_STEPS=1` rewrites it; `tests/test_step_cli.py` validates it).
- `cargo test -p mzlab-cli --lib flow_level`: `tests/livelli_casi.json` (the cases `tests/test_livelli_schymanski.py` also runs through `livelli.js`) gives the same level and `why` natively, and the plan convert → features → match → formula.ms1 → formula.ms2 → level runs on a synthetic caffeine mzML, MGF and one-entry library: one spectrum is 3a (one scan), two replicate spectra are 2a.

- `cargo test -p mzlab-core --lib flow::corsa`: files and lists apart, estimated against fixed, level counts, stable text; `cargo test -p mzlab-cli --lib flow_report`: a synthetic identification run, same bytes twice, one byte of an input changes its reported SHA-256; `tests/test_corsa_schema.py`: a real `features.table` run validates `corsa-1.json`.

## Traps
- The MS2 spectra of a plan come from `spectra.ms2` (mzML, one MGF for all the files) or are an input file of type `spectra` (MGF/MSP); `spectra.ms2` does not group replicate scans or merge by precursor, and `spectra.insilico` is not wired to it by the check beyond the `spectra` type.
- `spectra.match` does not use `delta_formula_mda` of `modified_cosine` (the free formula search of the precursor difference belongs to `formula.ms1`); the `facets` of the inputs are not checked by the step.
- `convert.mzml` reads vendor files, not mzML; a plan of mzML inputs goes straight to `features.table@1`.
- `import.raw` (`flow_import.rs`) opens each dataset with the reader of the registry and hands the input on unchanged. A plan input `NAME@ID` is the sample `ID` of the dataset `NAME` (a `.wiff` with its `.scan`, a `.D`/`.d`/`.raw` folder): `flow run` finds `NAME` in `--in`, and `convert.mzml` and `index.mzidx` (`build_index_of`) read that sample.
- A conversion a wire needs is accepted by the check but not inserted into the plan: the plan must still name it.
- The features of `features.table` and the queries of `spectra.match` have different ids (`q<k>`, the query accession or the `<file>.<scan>` of `spectra.ms2`): `annot.level` joins on the query id, so a feature row with no spectrum of that id gets only its formula level; `spectra.ms2` with a `features` port gives the scans the id of their feature.
- The heap peak of `FileRunner` is the one of the process: exact with one worker only.
- A fact the inputs do not declare (`facets`, `type`) is not checked by the plan; the step checks it when it starts.

- **Ricetta dai livelli del piano**: `run::recipe_of_layers(primo_indice, livelli)` (`mzlab-feat-wasm`) costruisce la ricetta di una corsa Flow (ricetta del profilo con minimo stimato + `steps::recipe_map::apply` per ogni passo); `flow run` (`flow_base::rebuild`) e l'esecutore web usano la stessa funzione, `run::layers_from_json` legge i livelli `[{"step","params"}]`. Parità: `flow_run_tests::the_recipe_of_the_layers_gives_the_bytes_of_flow_run`.
- Regole per ridurre i conflitti nel Flow: una PR alla volta su `flow.rs`, `lib.rs` e l'elenco dei docs; ogni nuovo passo vive nel proprio `flow_*.rs` e in `flow.rs` resta solo la riga che lo registra (limite 500 righe); i file generati (es. `strumenti-1.json`) si rigenerano con lo strumento solo a fine fusione, mai a mano; prima di spingere, dopo l'ultima fusione di `main`, `python3 tools/pre_pr.py` completo.
- Conflitti sui file generati: `strumenti-1.json` si fonde da solo (vedi `llm.md`); i `steps-*.json` restano nell'ordine del registro (è l'ordine della catena e della palette), quindi due PR che aggiungono un passo in coda alla stessa famiglia confliggono su quel file: si risolve tenendo entrambe le righe o rigenerando con `MZLAB_UPDATE_STEPS=1`.
- Bassa risoluzione (parità con Tabui): `features.detect` usa la ricetta del PROPRIO file (come `detect_file` della pagina), allineamento e riempimento quella del primo. `tp.dig_lr` (`flow_digl.rs`, prova `flow_lr_tests.rs` sui 5 demo `FullScan`: tabella e JSON uguali alla pagina) prende `table`, `samples`, `parent` (formula, SMILES o JSON), `index` e usa `regole_tp_2.json`. `tp.link@2` legge anche le tabelle a risoluzione unitaria: i cancelli di `tp/1` e `parent_rt` usano il Da (`TpParams.ppm < 0`, `OFFSET_MAX` per il genitore).
