# Reader modules: one `.wasm` per vendor family

One `.wasm` per family (`aperti`, `thermo`, `agilent`, `sciex`, `waters`, `shimadzu`, `bruker`), loaded only when a file of that family arrives: it opens the files the engine does not read and writes their mzML into OPFS; the engine then reads it like any mzML. The engine `.wasm` does not contain the module readers (`mzlab-wasm` uses `mzlab-core` without `thermo` or `estesi`; `tests/test_lettori_wasm.py`); it contains only the external reader (`external.rs`) with which it reads a `.raw` through the `thermo` module, without mzML.

## Crates
- `crates/mzlab-core`, Cargo feature `thermo` (default; brings `opentfraw`, `raw`, `rawfilter`, `rawlettore`, `metodo_raw`; `method_fields.rs` holds the neutral types `Ident`/`Campo` that Agilent also uses) and `estesi` (empty): variants of the engine readers served only by the modules, behind `#[cfg(feature = "estesi")]`. `mzlab-wasm` does not turn it on (`cargo tree -e features -p mzlab-wasm`).
- `crates/mzlab-lettori` (library, turns on `estesi`): one feature per family (`aperti`, `thermo`, `agilent`, `sciex`, `waters`, `shimadzu`, `bruker`) and `tutte` (desktop, CLI and tests). Each `ENTRY` sits behind the feature of its family; `famiglia()`, `registro()`, `riconosci`, `apri(fs, limits)` (the safest reader, wrapped by `SrmFromScans`), `open_bare(fs, limits)` (the same without `SrmFromScans`: sessions use it, the engine decides the SRM traces; the exception is the Thermo `.raw` with SRM scans, a TSQ, which is wrapped here too), `estensioni()`, `motivi(l, c)`.
- `tutte` is the default feature of `mzlab-lettori`: `cargo test -p mzlab-lettori` (the CI) tests every family; `mzlab-lettori-wasm` takes it with `default-features = false` and a single family.
  The round trip of `riconosci` exists because `readers::riconosci_in` wants a slice.
- `srm.rs`: `SrmFromScans` adds a `ChromKind::Srm` chromatogram per transition from the level-2 scans with an SRM/MRM/CRM filter and a precursor (`Q1_TOLERANCE`/`Q3_TOLERANCE`; it does nothing if the reader already has SRM chromatograms). Id `SRM SIC Q1=<q1> Q3=<q3>`, then ` ce=<eV>` and ` polarity=negative` if known (read by `mzmlhead::srm_id`). Point rule: Q3 = m/z of the point (in TSQ `.raw` files it is the CENTRE of the product window, rounded to 3 decimals; they are not intervals), Q1 = precursor of the scan.
  The CE comes from the `@cid25.0` of the filter or, if the filter lacks it (TSQ filters do and `srm_ce_by_event` is empty), from the transition table of `metodo/1` (`ms…transizioni`, paired by Q1/Q3); the polarity is that of the table (the scan of a v66 TSQ carries that of its event; a TSQ without scan events does not state it and the scan has polarity 0, not positive).
  Limits: a transition that the table has twice (two polarities) or lacks (table truncated by the file) keeps the CE and polarity of the scans, i.e. no CE and the event's polarity or none; TSQ scans without Q1 (empty filter) enter no trace.
- **Analog and PDA/UV traces (all families)**: the reader gives ONLY chromatograms, never UV spectra. A single-wavelength channel (or a TWC trace) is `ChromKind::Pda` (channel id, e.g. `UV_VIS_1`), pressure and temperatures are `Pressure`/`Analog`; the 3D UV spectrum (wavelength field per instant) stays out and goes in `metodo/1` as a `meta.nonDecodificato` warning ("UV 3D field (PDA spectra)") and in `raw-not-extracted.md`. Reason:
  `mzml.rs` reads a `<spectrum>` with MS level 1 if the level is missing, but skips those with `MS:1000804` (UV, not a scan; so do `scantable.rs` and `mzml.py`). The 2D UV matrix is read by `mzml_dad.rs` (`Mzml::dad`, a `DadData` as for the `.wiff`): a `dad_matrix` array (`MS:1000786`, f32, zlib, with `userParam` `wl_start`, `wl_step`, `n_wl`, `n_rt`, `rt_start`, `rt_stop`) in the PDA `<chromatogram>`, or `MS:1000804` spectra with `MS:1000617` and `MS:1000515` arrays; with the 1D trace only, the UV routes say `err.pda.none`. Times are in minutes like the TIC.
- **Thermo**, versions (`vendor/opentfraw/src/robust.rs` `VERIFIED_VERSIONS`, `RawFileReader::open`): only the versions verified on real files open (57, 63, 64, 66); every other number, including 8, 47, 60 and 62 whose schema the code knows, is `err.file.rawVersion` (`version`) until a real file verifies it; no reading with the nearest schema.
- **Thermo**, cut files and unreadable streams: a file cut after the index (almost finished copy) opens with all the scans and their levels but without the trailer, with the note `meta.nonDecodificato` "Scan trailer: records not found" and exit 0 [eseguito, TH-12]; cut before the index gives `err.file.rawTruncated` (`stage`, `size`, `needed`, `readable`, `declared`).
- **Thermo**, unfinished run: a RawFileInfo without controllers (no run-header address; acquisition never closed) or a run header that declares zero scans (`last < first`) is `err.file.rawUnfinished` with `detail` and `size` (`opentfraw::Error::NoRun`), on site and app, also for a finished run that recorded no scans [eseguito, TH-14]; the reader does not read a header at offset 0 nor write an empty mzML (`robustness_thermo_openings.rs`).
- **Thermo**, text of `err.file.rawUnfinished`: the two possible causes (interrupted acquisition, hence no scan index, or a run without scans), that nothing was opened or written and the next step if the acquisition was in progress (copy again at the end of the acquisition or re-export from the instrument PC), without the `detail`, which the CLI writes in brackets after the key (`error_text_tests.rs`).
- **Thermo**, damaged file: a count or an address past the end of the file, unreadable UTF-16 or type code (also inside a structure: `opentfraw::Error::Stage`) are `err.file.rawDamaged` with `detail` and, if known, `stage`, never the reader's "refusing to allocate" as text; `err.file.raw` stays for foreign magic and signature (`thermo_error`, `robustness_thermo_openings.rs`, `error_text_tests.rs`).
- **Thermo**, non-essential streams: scan events, error log, trailer and unreadable instrument/status logs are skipped with `meta.nonDecodificato`. Every other error is `err.file.raw` with `detail` naming structure, version and bytes (`raw::thermo_error`); never a panic. `cargo run -p mzlab-lettori --features thermo --example thermo_diagnosis FILE.raw` prints the structures and the result of `open` without data.
- **Thermo**, v66 event table (`reader.rs` `v66_body_sizes`): events of uniform size (Q Exactive, Exploris, Ascend), of fixed sizes (Eclipse, Fusion Lumos) or "counted" (body = 96 + 56 bytes per reaction; the average size can be an integer, which is why the counted path matching different counts wins over the uniform one).
- **Thermo**, before v66 an event has as many scan windows as it declares (SIM) and the filter text writes m/z with 2 decimals for the LTQ family, 4 for the others. Known limit (TH-01): the Stellar (events of 270-278 bytes with a final UTF-16 string and a `sid=` block) has an unreconstructed layout: the only real file gives `warn.raw.eventsRefused` (0 scans of 3 read with their event) and the conversion stops with `err.file.mzmlInvalid` (a spectrum without MS level) [eseguito].
- **Thermo**, reaction chain: `PrecursorInfo::reactions` (`vendor/opentfraw/src/reaction.rs`) gives for each step of an MS2…MS8 precursor, activation (EThcD/ETciD = ETD + supplemental), energy (NCE unit only if the trailer says so, otherwise unknown: to confirm with RFR), NCE steps and raw flags; `rawreader.rs` writes it in `opentfraw.reaction.N.*` only for chains of at least two reactions.
  The filter (`scan_filter.rs`) carries in each clause the activation of its step (MS3 CID then HCD = `…@cid35.00 …@hcd30.00`; MS2 and chains with a single activation as before); `ReactionInfo::multiple` marks simultaneous precursors (MSX, multiband) and `PrecursorInfo::sps_mz` the SPS-MS3 precursors of the trailer. Mzml, index and `metodo/1` stay equal; `unknown_double`/`unknown_long2` of non-final reactions are unconfirmed (`raw_double`, `raw_long2`) and activation codes other than CID/HCD are proven only on constructed events: not verified against RFR.
  Activation, unknowns, refused event tables and the precursors of a Thermo scan: `docs/agenti/lettori-thermo-precursori.md`.
- **Thermo** (`rawreader.rs`, `method_raw/`): `RawReader::cromatogrammi` gives the TIC and the analog channels of `RawFileReader::analog_traces` (also the 16-byte value/time pair layout of Dionex: `vendor/opentfraw/MODIFICHE-MZLAB.md`);
- **`.raw`: profile and centroids**: like msconvert (default setting) a `.raw` gives the file's centroid list if present, otherwise the profile (`resolve_scan_arrays` in `vendor/opentfraw/src/mzml.rs`); `SpectrumRecord::scan_mode` says what `mz`/`intensity` really hold and `Spectrum::profile` is true only for a true profile, even for an "FTMS + p" acquisition. `readers_centroids::centroidato` does not touch a scan with `profile` false. Tests: `tests/raw_centroids.rs` (skips without `MZLAB_DATI`) and `readers_centroids.rs` (fake reader).
- **`.raw`: reads** (`rawreader/stream.rs`, `Stream`): a window that after a jump restarts at 4 KB and doubles up to 64 KB while reads continue without jumps; the header of a packet and the centroid list behind a skipped profile do not read 64 KB of profile (each `read_at` on the site is a JS call). `con_blocco` (`vendor/opentfraw/src/scan_data.rs`) zeroes only the block that grows. Test: `rawreader_stream_tests.rs` (`a_skipped_profile_is_not_read`).
- **`.raw`: profile decoding** (`vendor/opentfraw`, `ScanDataPacket::read_profile_into`, for tests `pacchetto::decodifica_profilo`): each profile block goes from the read buffer to m/z and intensity without a `Vec` per block or a `Result` per value, with the coefficient conversion chosen once per scan; centroid list and labels are read as in `ScanDataPacket::read`, which refuses the same packets. Bit-exact test against `read` + `to_mz_intensity_into`: `crates/mzlab-core/tests/raw_profile_direct.rs`.
  `method_raw/tsq.rs` = TSQ transition table, `method_raw/lock.rs` = `ms.calibrazione.lock_mass` (mode `Use lock masses`, `Pos/Neg List Name` lists with the masses, and from the trailer number and correction in ppm as an interval; the data are not corrected), `method_raw/detectors.rs` = `rivelatori` from the Chromeleon script (`UV_VIS_n` channels: nm, band, reference; 3D field; frequency). Details and limits in `docs/agenti/metodo.md`.
- `crates/mzlab-lettori-wasm` (`wasm-bindgen` bridge, same per-family features, no engine reader linked): common interface `famiglia()`, `estensioni()`, `probe(names, sizes, read)` → `{formato, campioni:[{id,name,scans}], motivi}` with `motivi` ⊂ `srm`, `pda`, `variante` (an LC/MS `.D` or one with nested types in the xsd: `mzlab_lettori::reasons_together`); `to_mzml(names, sizes, read, c, sink, progress)` writes the mzML in 1 MiB pieces with `readers_mzml::scrivi` (each piece is an OPFS write of the page).
  Also the sessions (`session.rs`, `Sessions`; exports `open`, `samples`, `index`, `scan`, `scan_header`, `chromatograms`, `chromatogram`, `method`, `file_header`, `missing`, `close`) for the packages that read without going through the mzML.
  `to_mzml` writes the `indexedmzML` (offsets and SHA-1, no step `processingMethod`) with `readers_mzml::Conversione{steps: Some(&[])}`, the form of `mzlab-cli convert`: `tests/test_lettori_parita.py` compares the SHA-256 of the two files for all 8 families (thermo, bruker, andi: files of the `sintetici.rs` example). The `indice` feature of `mzlab-core` brings the index code into the modules (the engine does not): aperti and andi have the caps of `build_lettori_wasm.sh` raised.
  `to_mzml_with(…, c, dad, compression, sink, progress)` = `to_mzml` with the optical matrix only if `dad` and the compression of "Download .mzML": "Download .mzML" of a `.wiff` sample (also read by the engine) goes through here in the engine worker (`rust-nativo.js` `toMzml`, module `sciex`, `dad` false), the file of `mzlab-cli convert --compression` byte for byte (`tests/test_wiff_scarica_mzml.py`); the engine alone does not write what `estesi` carries.
  A sample that the module converts at load (`shell.js` `moduloToMzml`, `CONV.sources`) is downloaded rewritten with `to_mzml_with` in every compression, "standard" included (op `toMzml` of the worker with `dad` false and `compression`; `conversione.js` `again`): the file of `mzlab-cli convert --compression C` (`test_wiff_scarica_mzml.py`, also `dadmetodo` with a DAD; `tests_e2e/e2e_numpress_modulo.py`). The load file, with the optical matrix, stays only for the UV panel.
  One copy stays on OPFS: the mzML that the module writes in `conv/` is copied by the load into the engine store (`files/`); once the read succeeds `CONV.settle` moves the reference to that copy and removes the one in `conv/` (`e2e_impronta_opfs`). What stays per project is the engine mzML (the engine reads only mzML) and the `.mzidx` index (about 2× the source).
  **Binary transport** (`crates/mzlab-core/src/transport.rs`, `PROTOCOLLO` = 2, `protocol()` of the module): `index` is a single column-wise `Uint8Array` (rt, tic, base peak, precursor f64 with NaN = absent, position 3×f64, u32 index of the filter in a table with each text once, id offsets, level u8, polarity i8, then the texts).
  `scan` is a single `Uint8Array` with a fixed 24-byte head (level, polarity, profile / f64 intensity / precursor flags, points, RT, precursor, `testa_scansione`) followed by f64 m/z and f32 intensity (f64 only if the file has them at 64 bit). Id and filter do NOT travel: the engine takes them from the index row.
  `scan_parts` gives the same scan without the block: `[head, Float64Array m/z, Float32Array (or Float64Array) intensity]`, the two columns viewed on the module memory, valid until its next call; `JsModule` copies each once into the `Vec` of the scan (`scan_from_parts`, same `Spectrum` as `decode_scansione`). A module of an old build without `scan_parts` stays on the block.
  The module uses `Lettore::scan_data` (default `scan`; `RawReader` resolves it from the index row and from `opentfraw::extract_arrays`: no trailer, filter or precursors re-read). The engine refuses a module of another protocol (`err.file.wiffLoad`, `detail: protocol`).
  The session `open` uses `open_bare`; `file_header` gives `Lettore::mzml_header` as JSON (or `null`).
  `member_js` of the `thermo` module reads with 3 blocks of 256 KB (`mzlab_core::blocks::BlockCache`, the least recently used is replaced and not zeroed, the read overwrites it; the other families have a single block, for their caps): `opentfraw` asks for few bytes at a time, each `read` is a synchronous `File.slice` and alternates packets, trailer and index; `raw_times --blocks N` counts the reads. `Members` and `error_json` are copied from `mzlab-wasm/src/natives.rs`.
  With `read_ahead(READ_AHEAD_MAX)` a read that continues a block, or falls after its end by less than its length, fills the same place with a double block, up to 4 MiB; a distant read restarts from 256 KB. An OPFS read costs a fixed part per call: scanning a `.raw` goes from about 1300 to about 100 reads.
  Memory of the `thermo` module on the `.raw`: trailers stay in the file (`GenericRecordStream`, groups of 64 records read on demand; `for_each` for passes over the whole file), scan events sit in a compact table (`ScanEventTable`, shared preambles), `indice` becomes binary columns (see above). On the 595 MB BAF (56 061 scans): 33.5 MB after `open`, 48.0 MB after `index`, peak 122 MB over all steps.
  `python3 tools/bench_raw.py FILE.raw [--family thermo] [--steps open,index,...] [--keep DIR]` builds the module (cargo + `wasm-bindgen --target nodejs`), runs it in Node and prints for each step a JSON row with ms, WASM memory (`memory.buffer.byteLength`), bytes and SHA-256 of the result; `crates/mzlab-core/tests/raw_equivalence.rs` (with `MZLAB_DATI`; the BAF from `MZLAB_RAW_BAF`) compares the SHA-256 of `.mzidx`, mzML and `metodo/1` with the fixed ones (an intended change fixes them again) and the three trailer reads field by field.
- **External reader of the engine** (`crates/mzlab-wasm/src/external.rs`, trait `Module`, `ExternalReader<M>` implementing `Lettore`; `JsModule` calls the session object; `Replies` converts the answers (JSON, and the two byte blocks of `transport.rs`), native test with a fake `Module` in `external_tests.rs`; test with real files `crates/mzlab-lettori-wasm/tests/external_thermo.rs`).
  The engine opens it with `native_external(open)`; `open(names, sizes, read)` (`lettore-esterno.js`) answers with the module session (`samples`, `index`, `scan`, `scan_parts` if the module has it, `scan_header`, `chromatograms`, `chromatogram`, `method`, `file_header`, `missing`, `close`) or `null`; `protocol()` of the session gives the transport version that the engine checks at opening.
  The module is loaded in advance (`prepara`, async) because the engine cannot wait for a download; load error: `err.file.moduleLoad` ("the reader of this format did not download", not "the engine did not load"), also from the modules worker (`lettori-worker.js`) and from `rust-nativo.js` for the `.wiff`.
- The desktop (`mzlab-desktop`: `natives.rs`, `idxbuild_nat.rs`) uses `mzlab-lettori` with `tutte` and `mzlab_lettori::apri`: no cap, no module to load.

- **Shimadzu** (`crates/mzlab-lettori/src/shimadzu/`, feature `shimadzu`): `.qgd` (scans, SIM, MRM) and `.lcd` (LCMS-2020 scans/SIM, triple quadrupole MRM as SRM chromatograms); `riconosci` from the OLE storage names, Q-TOF/9030 refused with `err.file.shimadzu`; `soloModulo` `.qgd` and `.lcd`. Format and limits: `docs/agenti/shimadzu.md`.

## Build and caps
`tools/build_lettori_wasm.sh <site/static>` (called by `tools/build_feat_wasm.sh`, which `pages.yml`, `release.yml` and `sito-rust.yml` already run) builds one family at a time (`--no-default-features --features <family>`) in `wasm-lettori/<family>/` and writes `wasm-lettori/manifest.json` `{family: {sha256, byte}}`. A family without readers (`con_lettori` in the script) is skipped. `wasm-opt` runs with extra passes (`--converge --low-memory-unused --vacuum --dae …`, at the end of the script) that remove about 2.5 % from the module.
Caps after `wasm_opt -Oz` (B) with the measure in brackets: `aperti` 416 768 (416 663), `andi` 291 584 (263 817), `thermo` 626 688 (557 319), `agilent` 455 936 (429 536), `sciex` 374 272 (331 552), `waters` 325 888 (298 004), `shimadzu` 323 072 (286 020), `bruker` 455 168 (429 412), `valida` 479 744 (470 309, the mzML validator); they do not rise (`tests/test_lettori_wasm.py`). `conv/1` and the single `Conversione` path sit in every module and fix `aperti`, `andi` and `sciex` at the measure rounded to 256 B. The module downloads only when a file of its family is opened.

## `valida` module: "Validate mzML"
- A separate `.wasm` (feature `valida` of `mzlab-lettori-wasm`, which brings `mzlab-core/valida`; the readers sit behind the `lettura` feature, which every family turns on, and are not in the `valida` module): a single export, `validate_mzml(name, size, read)`, the JSON text of `mzlab-cli validate --json` for one file (`mzml_validate::json_un_file`). It sits outside `aperti` because the PSI-MS table (265 KB) would take it over the cap.
- Page: "Validate mzML" entry in the menu of an `.mzML` file in Data (`lista-file-menu.js`), route `api/mzml_valida?name=` (`lr.js`) and a window with the table (severity, message, position) in `valida-mzml.js`; the module downloads only then (`LETTORI_MOD.valida`, op `valida` of `lettori-worker.js`, file read from OPFS). App: same route, rpc `lr_valida` (`rpc_lr.rs`) with the same core function. Tests: `tests/test_valida_wasm.py` (node = CLI, byte for byte), `crates/mzlab-desktop/tests/rpc.rs`, `tests_e2e/e2e_valida_mzml.py`.

## Page
- `lettori-famiglie.js` (module of `carica.js`): global `LETTORI_FAM`, one row per family: `ext` (every extension it reads; `crates/mzlab-lettori/tests/robustness.rs` checks that those of the readers are there), `membri` (path parts that recognise the family), `errori` (the engine error keys for which the sample goes to the module), `soloModulo` (the extensions only the module reads).
- A `.d` folder belongs to Bruker or Agilent: the members decide (`analysis.tdf`, `analysis.tsf`, `analysis.baf` → `bruker`, row before `agilent`; `acqdata/` → `agilent`), never the extension; `agilent-d.js` (`BrukerD`) sends Bruker folders to the module (`docs/agenti/bruker.md`).
- `lettori-worker.js` (module worker): for the family the message names it downloads `wasm-lettori/<family>/mzlab_lettori_wasm_bg.wasm`, checks the SHA-256 of the manifest, keeps the modules already loaded; answers `probe` and `toMzml` (writes with `rawSink` of `rust-opfs.js`, progress `{scans, scansTotal, written}`); a running `toMzml` does not listen: the page stops the worker (`cancel`).
- `lettori-modulo.js` (`// @ts-check`): global `LETTORI_MOD` with `extensions()`, `famigliaDi(names)`, `retriable(key)` (→ family or `""`), `stand(name, members, c, family, size?, shown?)` (`shown`: the file dropped when the placeholder is the whole `.wiff` pair; the module error is reported under that name, not under "<stem>.mzML"; `e2e_wiff.py` with `tof`), `mzmlName`, `probe(family, members)`, `toMzml(family, members, c, dest, onProgress, signal)`, `loaded`. The worker is born at the first request.
- **Rule R**: `moduloToMzml` (`shell.js`, in `upload0` after `rawToMzml`) sends to the module of its family (a) the files with a `soloModulo` extension, (b) a sample the engine refuses with an error of `errori` (`agilent-d.js`, `waters-raw.js` and `wiffToMzml` make a `File` with `mzlabModulo` of it through `stand`), (c) a set for which `probe` gives `motivi`, but only if the worker is already started (`sonda: true` in the `sciex` row: `wiff-varianti.md`), (d) with `?lettori=modulo` every `.D` folder (path test).
- Loading rows in `moduloToMzml`: the conversion row of each file is removed at the end of its conversion; the ready file passed to `onFile` takes back its row in `upload0`, which stays with the count of missing scans (`data-cvmiss`, `M.missing`); at the end of the batch only the rows of the files never passed on (cancelled, failed) are removed.
  The mzML goes into OPFS, enters `upload()` like any mzML, sits in `CONV` ("Download .mzML" does not reconvert); "Converting" rows of `CONVROWS` in the side list (× stops that file: `ConvUI.stop`; "Cancel" above the rows stops everything), no panel in the work area. `fileKind` does not refuse the `soloModulo` extensions. Load error: `err.file.wiffLoad` (`family`, `detail`).

## Adding a family or a format
The reader is born in `crates/mzlab-lettori/src/` behind the feature of the family (a cfg `ENTRY` in `lib.rs`), its row in `lettori-famiglie.js` (the extensions, and in `soloModulo` those the engine does not read), the name in `con_lettori` of `build_lettori_wasm.sh`; the cap of the family is already there.
