# Progressive startup (current state)

- **Page immediately visible**: header, `#start` and `#drop` show without waiting for the engine; `#loading` (veil, phrases, ion) is hidden at startup and after startup never turns on to add files or to open a tab (`setTab` does not use it); it remains only for the LR/HR world switch (`open-now-raro.js`) and the tour example (`loading()` in `explore.js`); `e2e_nessun_velo`.
- **`AVVIO`** (`mzlab/web/avvio-progressivo.js`, loaded before `carica.js`): state `pending | ready | failed`, a single transition out of `pending`. `pronto()` is the gate of `upload()` in `shell.js` (`true` ready, `false` failed or cancelled); drops before the engine stay queued and start in order. Without `browser.js` or on a phone it starts `ready`.
- **Status line** `#avvio-fase` (`role=status`) under the bar: startup phase (`qqPhaseCur`); after 10 s of `pending` «Full reset» appears (`qqHardReset` → `QQRESET.run("all")`); it disappears when the engine is ready or failed.
- **Saved session**: the synchronous hint `mzlab.session` (`NOMI.KEY`) never paints the landing: it shows `#opening` in «restoring» mode (key `load.session.restoring`, height reserved like the landing) in the panel area, with the sidebar, until `api/state` answers (`segnaSessione`, `applicaIndizioSessione`, `rimuoviScheletro`); `reset.js` clears it and during the reset nothing rewrites it (`QQ_RESETTING`: `flushAll`, `segnaSessione(true)`, `segnaRiga`, `ricordaRiga` do nothing).
  The row of «+ panel» buttons (`#tools`) is already in the first paint of the restore, as the last session left it (`mostraRigaRipristino`, class `riga` on `#v-data`, buttons disabled; `finisciRiga` when the engine is ready or the restore failed): `AVVIO.segnaRiga` remembers it (`mzlab.session.row`: buttons, label and width of `#fsel`, side panel width; written at `pagehide` by `ricordaRiga`; never in HR; without memory the row stays hidden). Test: `e2e_riga_ripristino`.
- **Startup error**: `fail(key, params)` of `browser.js` sets `qqFailed`, leaves `{key, params}` in `qqFailInfo` (picked up by `AVVIO` if the module was not there yet) and calls `AVVIO.segnaFallito`. 
  This removes skeleton and status line and shows the banner `#avvio-errore` (fixed at the top, `role=alert`, non-modal): message, «Copy details» (version, key, phase, technical text without paths or URLs, no file names) and «Full reset» (`QQRESET.run("all")` via `qqHardReset`). 
  `AVVIO.errore` and the banner text are the same string; unknown key or missing catalog → «Calculation engine startup failed».
  A string is a key only if it has the form `a.b.c` without spaces.
- **Files dropped before the engine**: `upload()` (`shell.js`) with `AVVIO` in `pending` immediately puts one `CONVROWS` row per file (state `engine`, «Waiting for the engine», no percentage, in the side list; `waitRows`).
  - When the engine is ready the normal path picks up the same rows (`add` does not recreate a live row: no jump); a file discarded by `keep` has its row removed.
  - × on a waiting row leaves it out of the batch (`CONVROWS.skip`); «Cancel» in the `#drop` note removes the rows; when the engine fails they become error rows with the banner text.
  - On the desktop the engine is immediately ready and the state does not appear. Test: `e2e_righe_subito`.
- **`#drop` after a failure** stays visible only to show the error: `upload()` does not queue and does not launch (`pronto()` → `false`).
- **Cases** (`load.err.*` messages): old browser `oldBrowser`; missing engine or WASM that does not download `engineMissing`/`engineStart`; storage blocked by another tab `load.blocked` (status line) then `resumeTimeout` (banner); no saved file and no blocking tab: when the limit expires the line says `load.slow` and the page waits (slow first visit, `e2e_avvio_lento`); `?riparti=1` deletes the saved files before the restart.
- **Reset finished by the new engine** (`browser.js` → `lr.reset(scope)` → `lr_clear`): `?riparti=1` (full reset, app cold start) removes files, indices and notebook; `?riparti=file` finishes the «Files» reset that the old page could not finish (database blocked by another connection, OPFS folder held by a synchronous handle: `opfs` entry in `QQRESET.last.errors`) and, in the app, always finishes it (files and notebook are in the native store).
  Removes files, indices, warm data and tiles and, in the database, only `RESET_FILES` of `qqq-db.js`, written once (page, worker, `Store::clear_files` of the app that receives it in the message): drawing, lists, molecules stay. «Files» in the app keeps the run marker (`mzlab.run`): the reload is not a cold start. Tests: `e2e_reset`, `e2e_shim`, `tests/test_boot_reset.py`, `crates/mzlab-desktop/tests/rpc.rs`.
- **Startup order**: `index.html` immediately requests styles and `preload` of the startup chain scripts, even the first ones in the head (`reset.js`, `telefono.js`, `sito.js`; `browser.js` is added by `build_site.py`): Chrome's early scan does not look beyond `nomi.js` nor see those written with `document.write` or after an inline script, and without `preload` each cost a network round trip. `features.js` has no `preload`: Chrome did not use it and downloaded it twice. The language catalog is a single file in the site only (`languages.md`).
- **Page scripts** (`carica.js`): the ~170 tags of list `L`, then `shell.js` and the modules, enter in slices of 48 with a `setTimeout` between one slice and the next; `async=false` keeps the execution order. All together they were a long task of 110-180 ms at CPU ×4 (every insertion starts its fetch). No `carica(n)` call names a script of `L`, so none skips the queue.
- **On-demand scripts** (`carica(n)` after startup): once the whole list has finished executing, the script enters with `async=true` and `fetchpriority=high`, so a panel opened by the user does not wait in line behind the on-demand scripts requested earlier (stuck behind the mzFinder warm-up). Whoever depends on another on-demand script waits for it with `.then`. Before the end of the list it stays `async=false`.
  `browser.js` starts the engine (modules `rust-bridge.js` and `.wasm`) only at `DOMContentLoaded`, to avoid contending for bandwidth and CPU with the first paint; at that moment it also puts a `preload` (`as=fetch`, cors) of the `.wasm`, which thus comes down together with the bridge modules instead of after, and the `fetch` of `compileOnce` takes that response (a single download). Tests: `e2e_avvio_shell`.
- **Outside list `L`, on first use** (same `mzlab/web/` in site and app): `xlsx.js` (`dlx`/`dlc` in `carica.js` are placeholders; `csvBuild` in `tabella-picchi.js`, `zipStore`/`xlsxBuild` in TP_Mine wait for `carica`).
- **Outside `L` (continued)**: `paletta.js` + `ricerca.js` (Ctrl/Cmd+K in `carica.js`, button in `barra.js`; `PALETTE.open` requests `ricerca.js`), `tavola-periodica.js` (`QQQRef.open("pt")` in `tables.js`), `infusione*.js` (`TIPOF.infusione` in `tipo-file.js`, awaited by `bootSession0` before every non-MRM file (even a DDA has a tree) and by `TIPOF.viewer`). `banco.js` stays in `L`: `BANCO.on()` is read synchronously in 20 places.
- **Startup regression ceiling**: `e2e_budget_avvio`, in the `--fumo` Chromium Linux round of every PR (requests and KB before the first paint, blocking files, CLS, long task with CPU ×4, best of 5 reloads, up to the drop area and up to the last script of list L of `carica.js`; margins written in `BUDGET`). It needs the site with the engine (`tools/prepara_sito.py`): without it, it reports the engine error banner and stops. Measurement: `tests_e2e/misura_primo_paint.py`, table in `measurements-speed.md`.
- **Tests**: `tests/test_avvio_progressivo.py`, `tests/test_avvio_fase3.py` (Node with fake DOM), `tests_e2e/e2e_avvio.py`, `e2e_avvio_lingua.py`.

## Fast startup: rule for every page

Applies to Data, mzFlow and Drawing (Tabui excluded): interface immediately, the rest in the background.

- **Budget** with warm cache: first paint ≤ 300 ms, interactive ≤ 1 s; with cold cache no ceiling, but the shell appears anyway before any `.wasm`.
- **Immediate shell**: the page's HTML and CSS with placeholders (panel skeleton, bar, titles) and small classic scripts; no `.wasm`, catalog JSON, model or heavy library on the path to first paint and interactivity.
- **Everything else lazy**: `.wasm` modules, catalogs (`steps-cli-1.json`, `tools-1.json`), data and heavy scripts load in the background or at first use of what requires them.
  - `.wasm`: `WebAssembly.compileStreaming`/`instantiateStreaming` (response with `application/wasm`), instance in a Web Worker where the pattern already exists (`rust-worker.js`), never on the main thread.
  - Large JSON: `fetch` in parallel, parse in a worker or at idle; never sequential `fetch` when they are independent.
  - Idle prefetch (`requestIdleCallback`, falling back to `setTimeout`) of what the user will almost certainly use; never before the first paint.
- **Sober indicators**: a placeholder or a status line (`role=status`) for every incoming part, no blocking veil; a control that depends on a part that is not ready stays disabled with `aria-disabled` and activates when loading finishes. `prefers-reduced-motion` respected.
- **Cache**: resources with a versioned name or ETag, never reloaded if unchanged; the service worker contract in `data.md` applies.
- **Measure** with Playwright (Chromium already installed, never `playwright install`), on the built site (`python3 tools/build_site.py`, then delete `site/`): `PerformanceObserver` for `paint` (first-contentful-paint), a `performance.mark` marker at the page's interactivity, `performance.getEntriesByType("resource")` for the waterfall (bytes, order, duration); two rounds, cold cache (new context) and warm (same context, second load). Report the before/after table in the PR body.
- **E2E test «shell before wasm»**: the page exposes the `shell` markers (shell visible and interactive) and the end-of-instantiation time of every `.wasm`; the test blocks the `.wasm` requests (`page.route`) and checks that the shell appears and responds to the keyboard, then unblocks them and checks that the lazy parts activate. Example: `tests_e2e/e2e_flow_avvio.py`.
- **Installed web app (PWA)**: in the manifest and in the `apple-mobile-web-app-title` meta the name is «mzLab Web» (`WEB_APP_NAME` in `tools/build_site.py`: name + «Web»), the icons `app-icon-*.png` and `apple-touch-icon.png` have the «web» badge (`tools/generate_icons.py`, `web_badge`); the desktop app stays «mzLab» with its icons. The tab title does not change. An already installed PWA may keep the old name until reinstalled.
