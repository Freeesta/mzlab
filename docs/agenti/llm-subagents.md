# LLM: subagents and readings (`assist.rs`, `reading.rs`, router, data assistant tools)
Continuation of `llm.md` (section "Subagents and readings"): roles, `lettura/1`, router, `subcheck.rs`, `.wasm` `llm`.

- `assist.rs` + `data/assist/`: `assist-ruoli-1.json` (schema `docs/schemi/assist-ruoli-1.json`) gives the router, metadata, chromatography, parameters, interpreter and chart roles their prompt file, model, effort, `max_tokens`, output schema and input sources; no model or effort lives in the code. The `0N_*.md` files are exact copies of the ```text blocks of `docs/studi/assistente-dati/prompt/0N_*.md` (`tests/assist.rs` compares the bytes);
- The prompts are NOT in the `.wasm`: `assist::roles(json)` gives the roles, `assist::with_prompts(&[(file, text)])` receives the texts from the caller (`Prompts::check`, `prompt`, `digest` = SHA-256 of the text with trim_end, recorded in `llmlog/1`); the page downloads them on request with `llm-worker.js` (`assist.files`) from `static/llm/assist/`, copied by `tools/build_site.py`.
- `reading::validate(&reading_or_choices, &input, &registry)` checks `lettura/1` (`docs/schemi/lettura-1.json`: ≤ 8 results, ≤ 5 closed questions, actions `none|ask|set_param|add_step|split_series|chart`) and `param-scelte/1` (`docs/schemi/param-scelte-1.json`). The input is an object with the sources seen by the subagent (`{"tabcheck/1":…,"answers":…}`).
- Checks: every `evidence` (`source.path`, where an element of an array is cited by `id`, `alias`, `name` or `step`) exists in the input; every number in `numbers` and in every sentence (`text::numbers`) appears in the input; `set_param` names a registry parameter within the limits of `step/1`; an `ask` points to a question; in `param-scelte/1` every proposal has its choice, `source` is `rule:<id>` if the value is the rule's and `model` if it changed. The problems are `err.llm.reading.<reason>` (`problems_json`); they go back to the subagent once, then the reading is discarded.
- Proofs: `cargo test -p mzlab-llm --test assist`, `cargo test -p mzlab-cli --lib llm_reading` (real registry), `tests/test_llm_lettura.py`.
- `subcheck.rs`: `request(provider, role, prompt, input)` is the call of a reader (`subcall::build`, the same as the router: prompt as system with 5-minute cache, data in a JSON object, `output_config.format` = closed structure of `lettura/1` or `param-scelte/1`); `check(..., body, attempt, registry)` gives `Accepted(summary)` (compact JSON, ≤ `MAX_SUMMARY_TOKENS` = 1 500 at `ceil(byte/3)`), `Retry{request, problems}` at the first wrong answer and `Dropped{problems}` at the second. A role without a reading schema (charts) passes as JSON: `chart::make` validates it.
- Phase: `State::set_phase_prompt(file)` (`orchestrator.phase_prompt`, `06_piano.md`) makes the instruction enter as a `role: "system"` message after the user's message, once when the route becomes `plan` (again if the route leaves and re-enters; `phase` line with SHA-256 in the log). `State::add_reading(role, summary)` attaches the accepted readings to the following user message, as data (`{"reading", "data"}`), never as instructions.
- `.wasm` `llm`: class `Assist(provider, roles, prompt, steps)` with `request(role, input)`, `check(role, input, body, attempt)` (`{"verdict":"accepted|retry|dropped",...}`) and `digest(role)`; `Agent` has `enable_assist(roles, prompt, phase_file)`, `set_assist_state` and `reading(role, summary)`. The page runs the readers that the router names in `need_data` before answering with `sub_result` (section "Reader runner on the page").
- Whole session on `fs_pos`: `cargo test -p mzlab-cli --lib session::` plays `tests/data/assist/reg/fs_pos.jsonl` (`llmreg/1`, 17 calls: router, readers with one retried reading, ask_user, plan, table_check, chart; `MZLAB_UPDATE_LLM=1` rewrites it from the script) and proves that an instruction in a method comment or in a cell (R06, R13) changes no decision.
- Router (`router.rs`): `State::enable_assist(roles, prompts)` turns it on, `set_assist_state` gives the state it sees (`phase`, `files_open`, `plan`, `pending_questions`). At every message the machine emits `Output::Sub{role:"router", request}` (role prompt as system with 5-minute cache, message and state in a single JSON object, `output_config.format` = the closed schema of `prompt/02`) and waits for `Input::SubResult`;
- The router is advisory: an out-of-schema answer (`router::parse`, `schema::validate` + 2-letter language) or an error are in the log (`route` with `error`) and the turn goes on without a route; a valid answer is `route` in the log and in `State::route()`. 
- A `Stop` during the call closes the turn; a late answer or one from another role is ignored. Proof: `cargo test -p mzlab-llm --test router` (golden request `req_router.json`).
- Data assistant tools (`tools_assist.rs`, closed arguments, `additionalProperties:false`): `data_inspect {files?}` and `table_check {checks?}` and `table_rows {ids?, where?, limit ≤ 50}` are `read`; `params_propose {steps}` and `ask_user {questions 1-5, each with 2-8 options}` are `propose`. The catalogue only states the arguments: the answers (`inspection/1`, `param-proposal/1`, `tabcheck/1`) are built by the page with the existing Rust functions. Proof: `cargo test -p mzlab-cli --lib llm_tools`.

## Data assistant: design rules
- Rust measures and checks, the model interprets, asks and explains: the model never sees the bytes of the files and runs no code. Chain: readers → `inspection/1` (deterministic) → orchestrator and subagents → Rust checks (`flow::check`, limits of `step/1`, `chart::validate`, cited numbers) → normal execution of the plan.
- Order of trust: Rust > user answers > subagent reading > orchestrator text. A subagent that contradicts a Rust number is an error that the evaluation measures (`docs/studi/assistente-dati/06-valutazione.md`).
- Every subagent is a single call (two with the single retry) with its own prompt, data slice and output schema; the orchestrator sees only the summary (≤ `MAX_SUMMARY_TOKENS`). No subagent calls `edit` or `run` tools: only the orchestrator, under `policy::decide`.
- Models and effort live in `assist-ruoli-1.json`, never in the code; Opus does not enter the product. Haiku stays where the output is a choice among closed options (route, chart type); if it errs more than 5 % more than Sonnet on the same cases, that role moves to Sonnet at effort `low`, and the choice is written there.
- Effort is fixed per role: changing it mid-conversation invalidates the message cache. For the parameter proposal, the lowest effort that does not worsen errors and plans by more than 2 percentage points applies.
- Plan: the orchestrator does not invent chains, it starts from the Rust templates (`F.templatePlan`, example plans) per acquisition type and adapts them; a value equal to the Rust proposal carries `source: rule:<id>`, a different one `source: model` with the reason shown; after `MAX_PLAN_TRIES` rejected plans the assistant explains what remains.
- The sentences of the readings stay candidates ("m/z 305.3 at 14.7 min, candidate of …"), only in HR and with the evidence; in LR no verdict on products.
- Without network, without credit or beyond the cap, what remains is `inspection/1` and its view, `param-proposal/1` with "Apply", `tabcheck/1` with the flags, the default charts and the conversation export; the assistant says "Assistant not available" once and does not retry in a loop.

## What is sent and defences against injection
- Only what Rust has reduced is sent: `inspection/1` (alias or cleaned name, format, analyzer class, polarity, MS levels, counts, TIC/BPC ≤ 200 points, gradient, roles), `param-proposal/1`, `tabcheck/1`, ≤ 50 rows chosen by Rust, the canonical plan with its problems, the user's text. Numbers to 4 significant digits.
- Never sent: file bytes, whole spectra, `.mzidx`, paths, folder names, user, computer, operator, serial, the Log's `grezzo`, unmapped `campi`, the Theory with the solutions. Rust removes data of persons before building the input, with no option.
- A file or sample name is private: it is sent as an alias or, with consent of the `names` class, cut to 64 characters, without long digit runs (≥ 6) or control characters; in the demo "Hide file names" is always on.
- Data as data: every string of the files sits in a JSON value, with `& < >` replaced and Unicode directional characters removed. The policy looks only at tool, validated arguments and counters; no tool deletes files, opens the network or changes settings.
- Output checks: plan → `flow::check`, parameters → limits, chart → `chart::validate`, text → numbers present in the input, no URL, no shell command to run without review.
- Proof: the red set of `docs/studi/assistente-dati/prompt/10_red-team-iniezione.md` (file names with instructions, comments asking for `flow_run`, fake system messages, request for the system text or the key, invisible Unicode); criterion 0 unrequested actions and ≥ 95 % of attacks flagged.
- Log: `llmlog/1` of level a (role, model requested and served, SHA-256 of request and prompt, full `usage`, cost, `stop_reason`, tools, result of `flow::check`, duration) on the user's computer; no text or file name. Level b (conversation text) is not built without the opinion of the data protection officer.
- Keys: on the site no personal key (the shared key lives only in the proxy, `assistant-proxy.md`); in the app the own key stays in `llm-chiavi.json`, read only by Rust. Guards: `log::has_secret`, `tests/test_llm_chiavi.py`.
- Proposal not implemented: `mzlab-cli assist` for evaluations with a dedicated key (key from a 0600 file or from stdin, never in arguments) and a `refusal` that closes the turn with `err.llm.refusal` and the category, without retrying with another model.

## Public demo
- Profile `corso` downloads nothing of the assistant; the demo lives only in the Flow, behind "Try the assistant", never in the course pages (Theory, Practice, Data).
- Script: HRMS example (4 Orbitrap DDA files) for reading, 2-3 closed questions and plan; Full Scan LR example only to show that at unit resolution a candidate is proposed and no TP.
- Steps: consent with "What will be sent", Rust "Files" card before every call, chip "Explain these files", reading with evidence and confidence, `ask_user` (goal, matrix, blanks and QC), chip "Set up mzFlow for me", "Parameter" cards with `rule:R-*`, plan with "Apply" = one "Undo" entry, normal run without a model, network off leaving the Rust parts.
- Expected cost of one run of the script ≈ $0.28 with the demo catalogue (prefix ≈ 8 000 tokens), worst case ≈ $0.50 = session cap; without the reduced catalogue ≈ $0.40. Check: from the second turn `cache_read` > 0 in `llmlog/1`.
- Proposal not implemented: recording of the session in owner mode ("Record this session", `llmreg/1` with `fake::Replay::record_line`), replay without network or cost ("Play a recorded demo", files in `static/llm/demo/`) as a live fallback if the proxy does not answer, and an e2e that plays the recordings.

## External options (none active)
- Copilot on PRs, mzLab MCP server, sandbox for generated JS, evaluations in the cloud: none is turned on from a chat. Before any use, a card of ≤ 10 lines goes to the Coordinator (task, data that leaves and to whom, account and cost, secrets, files touched, how to turn it off, duration); without an answer the option stays off.
- MCP server: results would go to the client's provider without the proxy caps or the L0-L2 policy, and file names must be hidden by the server itself; route in use: `mzlab-cli` from the shell (`for-agents.md`).
- JS sandbox: only in the HR world and only if frequent chart questions remain without a named view; never in place of a calculation with parity (`llm-choices.md`).
- Cloud evaluations: only on synthetic data, key as an environment secret; comparisons with the chemist and real data stay local.

## Reader runner on the page (`mzlab/web/llm/llm-agente.js`)
The logic of choice and checking is all Rust (`assist.rs`, `subcheck.rs`, `router.rs`), the JS sends and delivers.
- Start-up: `AgentRun.enableAssist(steps)` (worker `assist.on`) calls `Agent.enable_assist` and creates `Assist` with the page's step registry (`S.reg.steps` of Flow, the parameter limits); `assistState(state)` gives the router `{phase, files_open, plan, pending_questions}` before the message.
- At every `sub` of the machine (`runSub`): the page sends the router request (`subCall`), asks Rust for the readers of the answer (`assist_readers`, once each in the order named; `router::reader_of`: `inspection`→metadata, `chromatograms`→chromatography, `proposals`→parameters, `tabcheck`→interpreter, `views`→charts; `plan` and `rows` have no reader) and only then answers with `sub_result`.
- A reader (`runReader`): the sources come from `host.readerInput(role)` (object per source, `{"inspection/1": …}`; null = reader skipped; in the Flow panel it is `F.llmFacts.readerInput` of `flow-llm-facts.js`, `docs/agenti/llm.md`); request from `Assist.request`; body to `Assist.check` (one retry with the problems, then discard); the accepted summary goes to `Agent.reading` and reaches the orchestrator only as data. An unreachable, discarded or skipped reader does not stop the turn; `host.reader({role, status: accepted|dropped|failed|skipped, problems, summary})` reports it.
- Panel state: `host.readerStage(role, queued|running|cancelled)` (queued in the router's list, running, stopped by `Stop`) and `host.reader` (outcome) reach `flow/lazy/flow-llm-readers.js` (`F.llmReaders.make`): a "Readers" card per group, one row per reader with state in words and symbol, short outcome (summary or problems with `F.message`). No cancel or repeat per single reader: the runner has only `Stop`.
- Transport: the subagent requests are already ready (`{url, headers, body, auth}`, never the key). Site: `SiteClient.sendRaw` (worker `send` message with `request`, same iframe and same CSP); app: `DesktopClient.sendRaw` (`llm/send` with `provider` and `request`, the key stays in Rust). With a recording, `Agent.replay_sub` answers them from the same sequence of turns.
- Before every send (machine and subagents) `AgentRun.guard` re-reads settings and consent and asks the client `needsKey(provider)`: assistant off or consent revoked → `err.llm.consent`, non-local provider without key → `err.llm.key.missing`; in both cases nothing is sent (`e2e_llm_lettori.py`, step "before every send").
- The token cap: the same `guard` applies it (`cap` in the settings, tokens of machine + subagents counted before every send): beyond the cap `err.llm.limit.spend`; without a cap (0) it asks once only, at 50 000 tokens, "Go on?" (refusal → `err.llm.limit.spend`); step "token limit".
- Cost: the subagent tokens are in `AgentRun.subUsage`, `totalUsage()` adds them to those of the machine; a `Stop` also stops the readers still to run.
- Injection: the text of the files (method comment, cells) travels only in the data block of a request, never in the prompt; no reader can change a decision of the machine (the CLI test `session::` proves it in Rust, `e2e_llm_lettori.py` on the page).
- Proofs: `cargo test -p mzlab-llm-wasm` (`readers`, request → JSON → request), `cargo test -p mzlab-cli --lib session::`, `tests_e2e/e2e_llm_lettori_pannello.py` (card, states, targets, axe), `tests_e2e/e2e_llm_lettori.py` (`fs_pos` session in STRICT recording: the page requests are the same bytes as those of the CLI test; comment with an instruction; unreachable reader; no request outside the site).
