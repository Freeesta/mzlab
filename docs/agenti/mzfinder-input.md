# mzFinder input: one `.mzidx` per file and the transformation list in Rust
Neighbouring areas: `mzfeat-wasm.md` (the `.wasm` files and the pool), `mzidx.md` (format).

## Index of each file (`TP_Mine/files/finder-idx.js`)
- The worker `tpmine-worker.js` keeps in `held` the Blob or ArrayBuffer of every file the page sends it (`put`). Before `classify` it calls `ensureIdx(names)`: for every file sent without a `.mzidx` in OPFS `mzlab/idx/` (or with an index that records a different size in `meta.source.size`) it builds one.
- The builder is the main program's: `prepare_upload` of `wasm/mzlab_wasm.js` (scan table, the `.wasm` compiled once), the pool of `idxpool.js` / `idx-worker.js` (one file per worker, in slices from the Blob) and `ARCH.promote` (from `<name>.mzidx.mzf.part` to the real name). No separate indexer: the bytes are those the Data tab would write (`tests_e2e/e2e_tpmine_ingresso.py` compares them).
- Pool size: `indexPool(navigator, poolSize)` (`finder-idx.js`) and the feature pool (`tpmine-worker.js`) use `smallDevice` like the engine pool: at most 2 workers and 32 MB per builder on a tablet or phone, otherwise min(cores − 1, 4) and 64 MB. The two pools never run together (`ensureIdx` finishes before the feature steps), so no shared gate; the feature steps share the page budget (`shareOf`, `memory.md`). Test: `tests/test_finder_pools_small.py`.
- A sample of a vendor file (`.raw`, `.wiff`, `.D`: in `files/` it is a small placeholder, `native-reading.md`) enters mzFinder with "Reload from Data" as a placeholder (`put` with `nat:true`): the worker reads its v2 `.mzidx` from the Data tab (`stubIndexed` in `finder-idx.js`: same recorded size, first MS1 scan not profile) and writes no mzML.
  If the first MS1 scan is profile, mzFinder reads a separate centroid index, `<name>.cen.mzidx` in `idx/`: the page builds it for a sample already in Data (`ask("cenidx")` → `rb.nativeCentroidIndex` → `lr_index_cen`, the same builder with `centroid:true`) and `ingress.idxName(name)` gives the name to use (`idxBase` in `tpmine-worker.js` and `finder-lr.js`); the Data tab index is left alone, and `lrFree`/`lrSpace` count the `.cen` as its own.
  **Sample chosen from Tabui** (`loadMaker`, which raises `window.MZLAB_CEN_IDX` during `upload`): `lr_index` carries `cen:true`; if the first MS1 is profile (`first_ms1_is_profile`, `natives.rs`) `build_mzidx_native` also receives `write_cen` and `upload::index_reader_twice` builds `.mzidx` and `.cen.mzidx` from ONE decode (`rows_before_double`).
  Each scan is decoded once by `Centroidato::grezza` and centroided by `scansione`; budget and scratch are halved, `mzidx_spill::Meta` alternates the slots. `idx-worker.js` writes `<name>.cen.mzidx.part` and `rust-worker.js` promotes it if the reply has `cen`, otherwise removes it. The bytes are those of the two separate builds (test `double_index_equals_the_two_apart`).
  **Validity of the `.cen`**: `stubIndexed` (`finder-idx.js`) reuses a `<name>.cen.mzidx` only if the recorded size matches and it was written after `CEN_FROM` (`lastModified` of the OPFS file, date of the `.raw` reader that does not re-centroid the file's lists): an older `.cen` has wrong peaks and is rebuilt. When a reader's peaks change, `CEN_FROM` is moved. The Data index has no date of its own: if it wrongly says profile, it goes through the rebuilt `.cen`.
- **Direct loading** ("Choose files..." `#tp-pick`/`#tp-in`, `loadMaker` in `20_tpmine.js`): `.mzML` files go to the worker as before; `.raw` and `.wiff` + `.wiff.scan` go through `upload()` of the Data tab (a single archive in OPFS, v2 index, phases of `nativo-fasi.js`), also appear in the Data list, and Tabui receives the new placeholders (`put` with `nat:true`) once the index is ready.
  The `.tp-lr` rows under "1 · Files" show the phases from the `mzlab-index` message and disappear at the end; the page stays usable. Files already in Data are not loaded twice. Test: `tests_e2e/e2e_tpmine_diretto_nativo.py`.
- The SRM traces of an MRM sample come from the page's engine (`rb.nativeSrm` → `native_srm` → `mzlab_core::srm`) and reach `finder_lr_mrm` as bytes (size −1). A sample without an index asks the page for the mzML (`ask("mzml")` → `rb.nativeToMzml`, written only once) and follows the path of any mzML. Test: `tests_e2e/e2e_tpmine_nativo.py`.
- **Always centroids**: before the index `ensure` looks at the head of the file (`headIsProfile`: the first spectrum with MS:1000128); if it is profile it reduces it with `Engine.mzml_to_centroids` of the main `.wasm` (`centroids/convert.rs`, HR and LR), replaces the Blob in `held` with the copy (same name) and sends the page `{type:"notice", key:"tpmine.centroided"}`, which shows a short notice. The index is that of the copy: it has another recorded size, so the Data tab rebuilds it if it reopens the same name.
- Files already indexed by the Data tab (taken with "Reload from Data") pass with no work. If the build fails (no OPFS, disk full) `classify` replies with an error.
- The worker keeps the received files in `held`: they are the source of the `.mzidx` files and of the MRM bytes.

## User transformation list (`legacy/transf.rs`, `finder_transformations`)
- The list text (lines `name;change[;note]`, `#` comments, `lit:` = expected level 2 of the rule, a prediction scale and not a Schymanski identification level) is read by `crates/mzlab-feat/src/legacy/transf.rs` (an equal vector keeps the first name). `finder_transformations(rules, text)` in `crates/mzlab-feat-wasm/src/finder.rs` merges the text into `regole_tp_2.json` and returns the merged JSON; a wrong line gives an error naming the wrong line.
- `tpmine-worker.js` (`runRust`) applies it only if the text is not empty and passes the merged rules to `hypotheses`: the default text does not change the rules, so the Dig is identical. Parity: `tests/golden/finder_transf.json` (frozen replies), `crates/mzlab-feat/tests/legacy_transf.rs`, `tests_e2e/e2e_tpmine_transf.py`.

## Transformation table (`TP_Mine/js/43_trasformazioni.js`, `window.TPTR`)
- Under "Transformations" (the `<details>` of `#tp-tr`, hidden like mzFinder) there is a table: rows grouped by class (oxidations, additions, losses, halogens), columns [on/off] · Name · Change (formula with subscripts) · Δm · Note. The text of `#tp-tr` stays the only source: the table reads it with `finder_transf_rows` (`legacy/transf.rs::describe`, in the `finder` `.wasm`: rows, monoisotopic Δm, class, per-row errors) and a click rewrites a row (a switched-off row = `# name;change`). "Edit as text" shows the textarea in place of the table (the row still writes `name;change;note`).
- "Add" (name, change, note) validates the change in Rust, shows Δm while typing and appends the row at the end; a wrong change is not added and the message (`.tr-msg.err`) says why. Repeated rows with an equal vector follow the `merge` rules (keeps the first name).
- `TPTR.change(label)` / `changeText` make the names in the "Change" column readable (`rottura+hydration` → "cleavage + hydration", `loss_of_c2h2+loss_of_c2h2` → "2 × loss of C2H2", `+H2O3` with subscripts): presentation only in `21_tpmine_hr.js`; the engine labels (`hypo.rs`) do not change. Tests: `tests_e2e/e2e_tpmine_transf.py`, `cargo test -p mzlab-feat --test legacy_transf`.
