## CI: measurements of the Rust jobs and discarded cuts
What is measured and why it is not done; how the CI works: `ci-fast.md`.

- **Measurement of the Rust jobs** (median over green PRs, warm caches, seconds): `rust` (feat) 107, `rust-core` 172, `rust-misc` 155, `rust-wasm` 186, `rust-lint` 30, `deny` 23; total workflow time 563. The Rust path is the slowest among `rust-core`, `rust-det` and `rust-wasm`: lowering only one moves the bottleneck onto the others.
- **Cuts evaluated and discarded**: splitting `rust-wasm` (under 60 s), a fourth test group between `rust-core` and `rust-misc` (about 0) and a separate `sito-wasm-lettori` job (one more runner, with the queue weighing more).
- **Cuts discarded with a local measurement (4 CPU)**: `rust-det` (native build + WASI, `release` with LTO): touched sources 356 s, with `ci_cargo_mtime.py restore` 3 s; with LTO off and opt-level 3 296 s (-17%, but it is no longer the product profile).
  Cargo holds the lock of the build folder: two `cargo build` in parallel on the same `target/` (native and wasip1) queue up (373 s against 356 s). `rust-core` (159 test binaries, 505 s of compile CPU): opt-level 1 builds from scratch in about 137 s against 200 s but the tests last 144 s against 121 s, balance about -40 s from a full build and +23 s from a clean cache; discarded.
  When a base crate (`mzlab-core`) changes every downstream binary recompiles: the gain from the mtimes stays on commits that do not touch `crates/` or touch only leaves.
- **Single upstream build, estimated and discarded**: one job per commit that compiles core+feat+cli (native and wasm32, product profile) and publishes `target/` as a cache per sha, reused by det, solo311 and wasm. Those jobs compile the same thing in parallel (det 290 s, solo311 380 s on heavy runs); with the upstream job the path becomes cold build (about 210-250 s) + cache restore (about 45 s measured for `target`) + the rest of the consumer (20-60 s), i.e. 280-350 s: no gain in waiting time, only runner minutes.
- **Open proposal (product code)**: every change to a base crate recompiles downstream `mzlab-feat` (99 s cold), `mzlab-cli` (75 s) and `mzlab-core` (58 s), all with LTO and a single codegen unit, in every job that builds the product profile.
  Reducing the fan-out would remove the recompilation, not move it: `mzlab-cli` should depend only on the crates it really uses, the leaf functions (spectral library, chemistry, LLM) behind features or separate crates, and `mzlab-feat` should not recompile for a change in a leaf. Measurement to do first: `cargo build --timings` for a typical commit of main and how many crates it invalidates.

## WebAssembly: discarded levers
Measurements and build state in `wasm-potential.md` (§3 numbers, §4 browser support). Each one discarded; retry only with the condition written.
- **Wasm threads**: in stable Rust `wasm32-unknown-unknown` has no `atomics` (needs nightly, `-Zbuild-std`, `wasm-bindgen-rayon`) and GitHub Pages sends no COOP/COEP (a `coi-serviceworker`-style worker needs a reload on first visit and `require-corp` everywhere). Between files the pool already scales x4 (1, 2, 4 workers in 444, 449, 456 ms). Retry if `atomics` arrives in stable and the hosting sends COOP/COEP.
- **memory64**: Safari only Technology Preview; 64-bit pointers cost extra bounds checks; budget and spill are already under 4 GiB (`memory.md`). Retry if Safari ships it and a real file exceeds 4 GiB.
- **Relaxed SIMD**: results differ between CPUs (FMA, min/max, dot), breaks bit-for-bit determinism. Not retried.
- **Exception handling**: needs `panic = "unwind"` and therefore `-Zbuild-std` (nightly). Retry with unwind in stable for wasm.
- **Explicit SIMD** (`core::arch::wasm32`, `portable_simd`): the hot loops are XML/base64/inflate (not vectorial) and AsLS/centroids (sequential dependencies); `portable_simd` is nightly. Retry if a profile shows a vectorisable loop at the top.
- **`DecompressionStream`** for the base64+zlib arrays: asynchronous and per array (thousands of a few KB), slower than inflate in wasm.
- **Double build** (baseline + fast, `wasm-feature-detect`): all targets have SIMD128; it would cost ~600 s of CPU in CI per PR, double the bytes in `site/` and the e2e tests.
- **O2 / Os**: O2 like O3 (slower centroids, 547 KB); Os halfway (499 KB, HR read 1168 ms in Node).
- **`wasm-opt` level**: `-O3` against `-Oz` after rustc O3 within noise (537 against 535 KB): only rustc's `opt-level` counts; `-Oz` stays.
- **`wasm32v1-none`** (`no_std`) and **`-Zbuild-std`** (nightly): not suited to an engine with `std` and a pinned toolchain.
- **Other proposals**: tail calls, extended-const, multi-memory, JS String Builtins, WasmGC: no effect on Rust code.
- **Cache of compiled `Module` in IndexedDB**: no longer supported by browsers; V8 caches by itself the code of cached HTTP responses (not those built by the service worker: `measurements-code-cache.md`); compilation 10-19 ms per module.
- **I/O**: the JS -> wasm copy (~10 GB/s) is < 1% of the mzML read (~80-140 MB/s); no lever.
- **`simd-json`** instead of `serde_json`: wants x86/NEON SIMD and is not faster in wasm.
- **`preload` of the `lang/<L>.js` catalogue from the language inline script** (instead of `document.write` only): discarded. Mirror 40 ms / 30 Mbit/s, Chromium, 6 alternating visits, medians: first-visit FCP 312 [272-337] → 341 [308-376] ms, start of `lang/<L>.js` 249 → 268 ms; no file downloaded twice. No gain (threshold 20 ms): the early scan already finds the file well enough.
- **`modulepreload` of `rust-bridge.js` and its 11 static imports in `wasmEarly()`**: discarded. The modules start earlier (`rust-supervisor.js` 696 → 420 ms) but the engine stays 3450 [3206-3536] → 3460 [3426-3684] ms: it limits the `.wasm` download, not the module cascade. Warm 742 → 746 ms.
