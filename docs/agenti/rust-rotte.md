# Motore Rust nella pagina: rotte e file Thermo
Stato attuale; parte del motore Rust (`docs/agenti/rust.md`).

## Motore Rust nella pagina (`?motore=rust`)
- Predefinito: il motore Rust è acceso (`rustOn` in `browser.js`); `?motore=python` o `localStorage qqq.motore = "python"` lo spengono (`?motore=rust` lo accende esplicitamente). Spento, `rust-bridge.js` non viene nemmeno caricato.
- **Un file, un lettore**: per ogni file intero (non una parte `#` di un file misto) il worker Rust apre il suo `.mzidx` da OPFS (`mzlab/idx/<nome>.mzidx`, operazione `idxopen`; `Engine.open_index` in `mzlab-wasm`) e risponde senza leggere l'mzML. L'mzML si apre (`openMzml`, `stats.mzml`) solo per ciò che chiede gli spettri (`api/spectra`, la prima volta) o quando il file non ha indice (niente OPFS) o non ha scansioni (MRM). `rust-bridge.js` smista: `chrom`, `filters`, `scanlist`, `nearest_scan` (`Engine.route`, che dà il JSON di Python o la stringa vuota = risponde Python) e `xic` (`Engine.index_xic`, un elemento di `traces` per file); `ref=` (differenza) e `kind` diverso da `tic`/`bpc` vanno a Python.
- Il lettore dell'indice sta in `mzlab-core`: `idxread.rs` (`Index<R: ReadAt>`: intestazione, metadati, tabella delle scansioni, array per scansione, `search` = `np.searchsorted` con la cache a blocchi di 16384, `sum_window`/`max_window` sommano nell'ordine della tabella come `np.bincount`), `routes.rs` (`Routes::handle`, `xic`; `Query`, che decodifica come `URLSearchParams`), `scantable.rs` (la tabella delle scansioni letta dalle sole intestazioni dell'mzML, senza regex: `scantable::read(&mut ReadAt, size)` dà le righe di `SCAN_COLUMNS` come JSON, `nce`, `hr1` e il numero di cromatogrammi; prova `tests/scantable_parity.rs` contro le righe scritte da Python, tutte uguali su sintetici ed esempi), `rois.rs` (`build_rois` e `extract_trace` di `ionfamily` dall'indice: stesse assegnazioni e stesse somme; prova `tests/rois_parity.rs` contro `tools/roi_riferimento.py`; le righe con lo stesso centro non hanno un ordine fisso in numpy e il test le ordina; non ancora collegate a `api/origin`), `json.rs` (lettore e scrittore minimi, `round` come `round()` di Python, `fmt_g` come `format(x, "g")`). Gli errori sono chiavi i18n; `Ok(None)` non è mai un errore: dice «risponde Python».
- Parità: `crates/mzlab-core/tests/routes_parity.rs` confronta le rotte con `tools/rotte_riferimento.py` (`dispatch` di Python su file sintetici ed esempi: tutti i livelli, finestre di m/z, `bpc`, `filt`, `prec`, filtri, `scanlist`, `nearest_scan`, XIC; indici e conteggi identici, numeri entro 1e-9); salta senza python3 e numpy (`MZLAB_GOLDEN_STRICT=1` fallisce). `e2e_rust` (sito e `.wasm` costruiti) confronta Rust e Python nel browser e prova che nessun mzML (salvo l'MRM) sia stato letto da Rust per disegnare i TIC.
- `browser.js` passa a `rust-bridge.js` ogni GET `api/chrom`, `api/xic`, `api/spectra`, `api/filters`, `api/scanlist`, `api/nearest_scan`, `api/scan_axis`, `api/ms2tr`, `api/fileinfo` (intestazione `X-Engine: rust`). Lo stesso `api/spectra` di Rust serve solo file a risoluzione unitaria con tutti i centroidi (`is_unit_resolution`); tutto il resto, e ogni caso che Rust non sa rispondere identico (MRM, parti `#` di file misti, profilo, HR), va a Pyodide.
- `rust-worker.js` (modulo) carica `static/wasm/` (costruito solo da `pages.yml`) e tiene un insieme di `ArrayBuffer` restituiti da `recycle`; il bridge li rimanda dopo aver costruito il JSON.
- Supervisore (in `rust-bridge.js`): se il worker muore, lo termina, ne crea uno nuovo, riapre i file dalla sessione (`api/explore`; indice e, se serve, mzML) e mostra `error.engineRestarted`; una seconda morte entro 1 minuto spegne Rust per la sessione (`error.engineFallback`). `window.MZLAB_RUST` = `{enabled, disabled, stats, crash()}` per i test. Test `e2e_rust`; `python3 tools/bench.py` misura i due motori, tabella in `docs/agenti/misure.md`.
- **Flusso senza Pyodide** (`lr.js`, `lrOn` in `browser.js`; predefinito con il motore Rust, `?lr=0` o `qqq.lr = "0"` lo spengono): `lr.js` risponde, con il JSON di `api.py`, a `upload`, `state`, `session`, `explore`, `meta`, `remove`, `new`, `notebook`, `spazio`, `method_warnings`, `gradient` (nessuno) e `formula`;
  le operazioni `lr_*` di `rust-worker.js` scrivono i file in OPFS, costruiscono l'indice (tabella delle scansioni con `prepare_upload`, indice con un worker del pool `idx-worker.js`), aprono l'indice e producono riga d'elenco (`lr_entry`) ed elementi di sessione (`lr_items`); IndexedDB `qqq_lab` tiene il taccuino. Il bridge risponde anche a `spectrum`, `mrm` e `scaninfo`; ogni elemento della sessione (anche ogni parte di un file misto) ha il suo slot.
  Qualsiasi altra richiesta (o un `.dam`, un file senza indice, un errore) fa avviare Pyodide una volta (`needPython`: avviso `lr.python.loading`, `lr.freeze()`, avvio del worker classico, che riapre da OPFS file e indici con `resume`, poi `explore` con la sessione di `lr.session()`); da quel momento `lr` è spento e il percorso è quello classico. `window.MZLAB_LR_MISS` elenca le richieste che hanno mandato il flusso a Python, `MZLAB_LR_ERR` l'errore di avvio.
  Prova: `tests_e2e/e2e_lr.py` (richieste di rete contate, JSON uguale a Pyodide, ricarica, avvio a richiesta) nel job «sito» di `sito-rust.yml`, che lancia tutti gli e2e del sito col `.wasm`; gli e2e del percorso classico (`e2e_pool`, `e2e_mzidx`, `e2e_avvio`) usano `?motore=python`.

## Inventario delle rotte `api/...` (chi risponde oggi)
**Rust** = risponde il motore dall'indice o senza file (`Routes` in `mzlab-core`, `lr.js`, `lr-map.js`, `lr-origin.js`); **Python** = Pyodide, parte alla prima richiesta (`MZLAB_LR_MISS` la elenca); **JS** = `lr.js` da solo. Una rotta esce da Python quando ha parità (`tools/*_riferimento.py` + `crates/mzlab-core/tests/*_parity.rs`) e la prova `e2e_lr`.

| Rotta | Dove sta | Note |
|---|---|---|
| POST `upload`, `explore`, `meta`, `remove`, `new`; GET `state`, `session`, `notebook`, POST `notebook`, `spazio` | Rust/JS (`lr.js`) | tabella delle scansioni e indice in OPFS; un `.dam` o un file senza indice manda tutto a Python |

| GET `chrom` (`tic`, `bpc`, finestra `mz0`/`mz1`, `filt`, `prec`), `xic`, `filters`, `scanlist`, `nearest_scan`, `scan_axis` | Rust | dall'indice (`routes.rs`, `axisroutes.rs`); parità `routes_parity` |
| GET `chrom` con `ref=` o `kind` pda/analogici, `xic` con `ref=`, `mrm` con `ref=` | Python | differenza (`differenza.py`) e tracce analogiche |
| GET `fileinfo`, `scaninfo`, `mrm`, `ms2tr` | Rust | `fileroutes.rs` (testa dell'mzML dal Blob + indice), `scaninfo.rs`, `axisroutes.rs` (`ms2_transitions`: coppie precursore > frammento dall'indice); `mrm`/`fileinfo`/`scaninfo` leggono l'mzML |
| GET `spectrum`, `spectra`, `dda` | Rust | centroidi a risoluzione unitaria, profilo non HR e HR (`profspec.rs`, `hrroutes.rs`); restano a Python profilo con sezioni in singola precisione, sottrazione di fondo, `scanbin`, `spectra` HR, `scan`, `scanavg` |

Le rotte POST `workflow/validate`, `export/mgf` e `export/msp` non esistono più: restano le funzioni di `workflow.py` come riferimento dei test.

**Aperture di un file LR senza Pyodide.** In `mzlab-core`, con parità su Python: tabella delle scansioni (`scantable`), indice (`mzidx`, pool di worker), tipo/tempo/concentrazione dal nome (`project`), `Item.info` (`iteminfo`), `file_parts`, `sniff`, cromatogrammi e metadati (`mzmlhead`), le rotte dell'indice. Lo stato della sessione sta in `lr.js`; `sito-rust.yml` costruisce il sito col `.wasm` ed esegue gli e2e del motore sulle PR.

Per non leggere il file, a Python bastano: nome, dimensione, SHA-256 e impronta (dall'indice: `source`), tipo/tempo/concentrazione dai nomi (`project.py`) e, per i file HR, `hr_profile` (dalla tabella delle scansioni).

## File Thermo `.raw` (solo con `?motore=rust`)
- `Engine.raw_to_mzml(nome, size, read, sink)` (`mzlab-wasm`): il `.raw` si legge a blocchi di 1 MB da `File.slice` (`BlockReader` con `Seek` e l'ultimo blocco in memoria, mai il file intero nella memoria WASM) e l'mzML esce a pezzi verso `sink`, che la pagina tiene come parti di un Blob. Operazione `raw2mzml` di `rust-worker.js`, `convertRaw(file)` di `rust-bridge.js` (errore: `json` con `error_key`, `err.file.raw`).
- `rawToMzml` in `index.html` converte i `.raw` prima di `upload()`: il file prosegue come `NOME.mzML` e Python lo legge come ogni altro (la risoluzione sta nel `userParam` `opentfraw.resolution`, letto da `_resolution` in `reader/mzml.py`). Senza motore Rust resta la avviso unico con la guida «Non hai file mzML?» (`dati.md`); `#dropraw` dice sulla schermata di carico che i `.raw` sono accettati.
- Avanzamento e scarico (`conversione.js`, `ConvUI`, `CONV`; `tests/test_conversione.py`, `e2e_conversione` con motore simulato): durante la conversione il pannello nella schermata di carico dice «i di n: nome», la fase (lettura → conversione → scrittura, da `convPhase`: byte del `.raw` letti e byte dell'mzML scritti), la percentuale, i MB e il tempo trascorso, con `role=progressbar`. Il worker WASM manda `{op:"progress", id, total, read, written}` (al massimo ogni 150 ms) e `convertRaw(file, onProgress)` li passa alla pagina. Ogni mzML convertito sta in `CONV` (nome → Blob): «Scarica mzML» in tabella di carico e nella lista dei file, «Scarica tutti» (in sequenza, senza zip). Browser: download normale; app desktop: finestra di salvataggio nativa (`window.MZLAB_SAVE_MZML` → comando Tauri `save_mzml`, permesso `dialog:allow-save`; Blob con `mzlabId` = numero dell'mzML sul disco).
- Parità: `crates/mzlab-core/tests/raw_parity.rs` confronta il `.raw` con l'mzML di msconvert (m/z 1e-6, intensità 1e-4, relativi) solo se il repository privato dei dati c'è (`MZLAB_DATI` o `mzlab-dati` accanto); mai un `.raw` nel repository pubblico. `cargo run --release --example raw2mzml -- IN.raw OUT.mzML` converte da riga di comando. Il passo `.raw` di `e2e_rust` si salta senza dati.
- Il precursore selezionato può differire da msconvert di qualche scansione MS2 (correzione monoisotopica dell'OpenTFRaw); lo spettro MS2 non cambia.
