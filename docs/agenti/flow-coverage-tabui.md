# Coverage of Tabui (mzFinder) by mzFlow
Package to close the gaps: `flow-package-tabui.md`.
Snapshot of the code to decide whether Tabui can be retired: for each Tabui function, the mzFlow step or model that covers it and whether it can run today. "Executable" = the step has an executor in `EXECUTORS` of `crates/mzlab-cli/src/flow.rs` (`flow::executable`), so it runs with `mzlab-cli flow run` and with "Run on this computer" of the desktop app (`flow/run`, same engine).
The site runs some of the steps with the web executor (`F.runners.web`, "This browser", `docs/agenti/flow-web.md`): `index.mzidx`, `features.detect|align|gapfill`, `tp.generate`, `tp.link@2`, `tp.filter@2`, `tp.position`, `tp.network`, `tp.review`, `tp.dig_lr`, `export.table_csv`, `export.mztab`, `table.filter` and the MSn steps; the others stay on the computer (`via: "computer"`). `F.runners` has `cli`, `web` and, in the app, `desktop`.

## Checks made on the code
- The CLI registry (`flow::steps()`) contains the base chain, `features.table`, `spectra.centroid`, Attributio, `spectra.ms2`, `meta.compare` and the whole Tabui family (`mzlab_chem::step::tabui()`); a step without an executor gives `err.flow.step.native` (`tp.generate` now runs).
- The steps in the registry but without an executor (`features.ms2_link`, `spectra.chimeric`, `spectra.insilico`, `annot.regulatory`, `annot.hazard`) give `err.flow.step.native`.
- Executors today (29, plus `quant.calibrate`, `msn.library_export` and `msn.table_export`, outside Tabui's flow, and with `tp.dig_lr`, Tabui's LR Dig: JSON identical byte for byte on the 5 FullScan demos): `convert.mzml`, `spectra.centroid`, `index.mzidx`, `features.detect`, `features.align`, `features.gapfill`,
  `features.estimate`, `features.table`, `table.drift`, `table.stats`, `table.pca`, `table.kmd`, `table.plausible`, `export.table_csv`, `export.mztab`, `spectra.match`, `formula.ms1`, `formula.ms2`, `spectra.ms2`, `spectra.msn_graph`, `annot.level`, `tp.generate`, `table.filter`, `tp.link@2`, `tp.filter@2`, `tp.position`, `tp.network` (with a `tp/1` given as a file), `tp.dig_lr`, `meta.compare`, `export.inclusion` (reads the `.mzfeat` of `tp.link` or a JSON; adduct per polarity).
- Tests in the browser: `e2e_flow.py` (plan, models, file views) and `e2e_flow_web*.py`, `e2e_flow_tp_*.py` (web steps, texts identical byte for byte to `flow run`).

## Polarity and resolution
- `tp.generate` (optional port `index`), `tp.link@2` and `tp.dig_lr` read polarity and unit resolution from the files (`mzlab_feat::nature`, the same rule in `flow run` and in the browser) when the plan does not write `polarity`/`nominal`; the value used ends up in `estimates` of the provenance. A negative set is searched as [M−H]⁻, an LR one merges the hypotheses by nominal m/z (like the Dig). Connect `index` to `tp.generate` in LR and negative plans.
- At unit resolution the `tp/1` gates and the `tp.network` edges use windows in Da (`LR_TOL`); the LR Dig reads the parent's adduct. Test: `flow_bentazone_tests.rs` (bentazone C10H12N2O3S, synthetic, ±, HR and LR).
- Times in names: `T2p5` = 2.5 (also `T0p5`, `T10p25`).

## Export
`export.table_csv` and `export.mztab` call `table_file`, the same function the page asks the table `.wasm` for (`export_table`): same bytes for columns, order, names and number format, proved by `flow_bentazone_export_tests.rs` on a table detected from the plan (positive and negative) and by `flow_export_tests.rs`. The polarity that `table_file` writes (mzTab-M, MS2) is decided by the files when the plan does not write it: ``export_job` reads it from the indexes of the table chain (the table recipe, like the page's, does not write it).

Known differences: the table reads the `samples/1` as it is (`flow_table::samples_text`; its group is the role for non-samples, derived when read); the export of a `table.filter` view writes the kept rows (`origine` of the view); the `tp.link@2` table (TP status columns) is not an input of `export.table_csv`.

## Bentazone model
The "Bentazone / transformation products" model (palette, under "More templates"): the whole TP chain. `templatePlan` connects `index` to `tp.generate` (polarity and resolution are decided by the files) and `tp.network` to the rows and samples of `tp.link` (a `tp.filter` view is not a table); test: `tests/flow_modelli_partenza.js` and `flow_bentazone_tests.rs` (same wiring, executed).
