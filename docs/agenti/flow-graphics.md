# Graphical Flow

Page to build, check and export an `mzflow/2` plan (format and check: `rust-flow.md`; descriptors: `rust-step.md`). It does not run the chain: the plan is exported and launched with the `mzlab-cli` (example `flow`). Canvas rules: `flow-ux.md`; correspondence with mzmine: `docs/agenti/flow-mzmine.md`.
- **Access**: always, in the site and in the app, inside the Tabui `QTOOLS` machine (`flow/js/flow-tool.js`: "Flow" tab after Draw); it is not in the lab variant (`window.MZLAB_LAB`). English only, no keys in `lang/` (like Tabui); `tools/controlla_i18n.py` skips `flow/`.
- **Shipping**: `tools/build_site.py` (`pack_mzfinder`) puts in `static/mzfinder/` the four lists `steps-1.json`, `steps-attributio-1.json`, `steps-tabui-1.json`, `steps-cli-1.json` (from `docs/schemi/`; `F.registry` keeps the first definition of an id and leaves out `meta.compare`, which the page handles) and the `flow/lazy/*.js` files among the `lazy` of `indice.json`; no new `.wasm`, no ceiling touched.
- **Files** (`flow/lazy/`, global `FLOW`): `flow-registry` (data types with family and letter, ports, `fit` ok|adapt|no, conversion path), `flow-check` (faithful port of `flow/check.rs` and `parse.rs`: `F.check`, `F.normalize`), `flow-plan` and `flow-inputs` (model: add, connect by itself, remove, move, parameters, canonical export, import, inputs, `F.goal`), `flow-ui` (DOM, icons, English texts for every `err.flow.*` key, style), `flow-palette`, `flow-form`, `flow-chain`, `flow-compare`, `flow-page` (list view)
- **Canvas files** (`flow/lazy/`): `flow-names` (names in plain words, categories, add-on components `F.ADDONS`, templates `F.TEMPLATES`), `flow-fix` (base plan, add/templates, needs with one-click remedy, canvas model and column layout), `flow-canvas` (220×64 cards, SVG lines, zoom and pan), `flow-inspect` (step panel), `flow-shell` and `flow-shell-css` (Canvas | List | Plan tabs, top bar, "Add analysis" menu, templates, runners `F.runners`).
- **Validation**: `F.check` gives the same errors (`key`, `params`) as the Rust check. Parity on `crates/mzlab-feat/tests/data/flow_check_cases.json` (read by `crates/mzlab-feat/tests/flow_cases.rs` and by `tests/flow_grafico_nodo.js`, launched by `tests/test_flow_grafico.py`); to regenerate the expected answer: `MZLAB_UPDATE_FLOW_CASES=1 cargo test -p mzlab-feat --test flow_cases`.
- **Goal**: `F.GOAL_STEPS = ["annot.level"]`; `F.goal` says whether the chain reaches it and which inputs (`spectra`, `library`) must be declared, because no step produces them.
- **Plan**: ordered list, each port chooses its source in a `<select>` (`many` ports use labels); a step that has nowhere to take a file from adds it to the inputs. Type conversions (`converts`) are marked ⇄ and never inserted silently. The plan has no `ui` field: no positions.
- **Parameters**: form generated from the descriptors (default value, unit, limits, "More" for `x-advanced`, empty estimate if `x-estimate`); the file keeps only the differences from the default; algorithm and preset are menus; a `planned` algorithm gives `err.flow.algorithm.unavailable`.
- **Comparison** (`meta.compare@1`): on a step with at least two available algorithms the "Compare algorithms of X" button adds a comparison with the same inputs and one variant per algorithm, plus the tolerances (`mz_tolerance_ppm`, `mz_tolerance_da`, `rt_tolerance_min`). The page checks it by itself (`F.validateExtra`: at least two variants, different variants, known step and algorithms) and removes it before the parity check (`F.withoutCompare`); `flow_compare::check` in Rust gives the same answers.
- **Bar** (`flow-shell.js`): one row, Canvas|List, Auto-run, Terminal and "⋯" (Plan (JSON) Advanced only, Download plan); inspector at 50 % (240 px – 70 %), width kept for the session.
- **Canvas** (default tab): opens with the BASE already connected and valid (`index` → `detect` → `align` → `gapfill`, one `raw` input; `F.basePlan`): configurable, not removable. Everything else is an add-on from the "Add step" menu (`F.ADDONS`: all the Attributio steps — mixed spectra, formulas, library comparison, predicted fragments, retention time, level, regulatory lists, aquatic hazard — and the TP search) or a template (`F.TEMPLATES`: sets of components, one click gives a complete chain).
- **Needs and modes**: a missing need is written on the card in plain words with the button that adds it (`F.friendly`, `fixFor`); removing can be undone. Simple mode (default) folds the base into two nodes and hides the raw inputs; Advanced shows every step, every input and the full palette.
- **Step panel**: on the right, explains the step ("What this step does"), shows "Uses / Feeds into" and the parameter form (base and advanced). The same plan holds in three views (Canvas, List = the earlier editor, Plan = JSON).
- **Runners** (`F.runners`): "Command line" (shows the command) and, only in the desktop app (`window.MZLAB_DESKTOP`), "This computer" (`flow-desktop.js`): the Run button shows "Run on this computer", which sends the plan to the native route `flow/run` (`docs/agenti/rust-desktop.md`) and writes for each step "waiting", "done in N s", "skipped" or the error reason (from `prov/1`).
  The files open in the Data tab become the raw inputs of the plan (`F.runPlanFromData`, `flow-samples.js`: the first placeholder `raw`/`mzml` input is replaced by one input per file, connected where it was; the copy does not touch `S.plan`); a file the app does not have (`err.flow.input.missing`) is excluded, the run restarts with the others and the note says "N files excluded" with the names.
  Sample lists (`S.samplesJson`) travel as text in the `files` field of `flow/run` (`stage_inputs` in `flow_stage.rs`): they must not be registered. If a file is in profile mode (`ST.files[].spectrum_mode`) and the chosen algorithm of a step admits only centroids (`applicability.spectrum_mode`), the note warns; the note proposes `spectra.centroid` before `index.mzidx`. Index and conversion of the files remain those of the Data tab.
- **Results of a node** (`flow-results.js`): a view registers by data types (`F.registerView({id, title, types, open})`); a node whose steps produce a type with a view shows in the panel the "Results" block: the files of the last run (`S.results[instance]`, filled by "This computer") and "Open a ... file..." for a file chosen from disk (also on the site). The view opens under the canvas (`#flx-root .flx-res`, closable, focus on the title).
- **Views**: the CSV/TSV table (first 200 rows, 30 columns, `F.parseCsv`) for the types table, annot, tp, candidates, formulas, library, with "Columns: what is filled in" above it (`F.tableSummary`: filled and empty cells, minimum and maximum of the numeric columns, over the whole file); `F.viewFor(type, item)` chooses the view that `accepts(item)` the file, then the one without `accepts`; other views (review, report, groups) are added with `registerView`. On the desktop the text of an output file comes from the `flow/read` route (≤ 4 MB).
- **Identification views** (`flow-views-attributio.js`): the JSON `candidates/1` (hit), `annot/1` (level, why, "value / threshold" thresholds) and `formulas/1` (best per feature, or candidates per spectrum with a table of explained fragments) become tables (`F.readCandidates/readAnnot/readFormulas`, `F.drawTable`); an MGF (`F.readMgf`) gives the spectrum list, a selector, the stick chart (`F.sticks`, colors from CSS variables) and its peak table.
- **MSn graph** (`flow-views-msn.js`): the JSON `msn-graph/1` of `spectra.msn_graph` (type `report`, opened by `flow-report.js`) opens in two views ("Graph" and "Tables" buttons); "Tables" = the modifications (one row per edge and measurement: ions with subformula, neutral loss, mass and ppm, tree, activation, CE, scans) and the ions, like the columns of `msn.table_export` (`F.readMsnGraph`, `F.openMsnGraph`). Test: `tests/flow_msn_view.js`.
- **Graph view of the MSn graph** (`flow-msn-graph.js`): the same SVG as the "Fragmentation graph" tab (`drawGraph` with `opts {t, sel, mode}`), Tree/Radial; on click the Data panel (`nodePanel`) and "Use" (writes `scelte`, `F.msnChoices`); "Open in Data" opens the tab; download JSON, SVG and PNG (`msngrafo-immagine.js`); HTML: `msn-manual.md`.
- **Campaign folder** (`flow-campaign.js`): the results tab of the `annot.level` node offers "Open a campaign folder..."; the cascade runs with the Attributio engine (`ATTRIBUTIO_CORE.pool`, no new `.wasm`) and the `campaign` view shows the level table (`ATTRIBUTIO_TABLE`) with CSV and XLSX export; "Open in Bench 2b" on a row opens `ATTRIBUTIO_BANCO` under the table and a saved decision redoes the cascade.
- **Attributio inside Flow**: Attributio no longer has an entry of its own. The folder picker uses `showDirectoryPicker` when available (the campaign keeps `dir`): Review and Bench 2b write `feature_decisions.csv` into the folder; with the `webkitdirectory` input the file is downloaded ("Download decisions").
- **Feature table from disk** (`flow-views-features.js`, view `feattable` of type `table`): a `.mzfeat` chosen from disk (the results picker accepts it and the element carries the `File`) is read in the page (`PIPEV.readFeat`), opens the table session (`PIPEQC.open`, table `.wasm`) and mounts the virtual table with the expanded row (`PIPET.mount`); read-only. File names and polarity come from the meta (`F.featMeta`); the row's XICs serve the `.mzidx` of the series in the browser and say when they are missing.
- **Campaign exports** (`flow-campaign.js`): the "Export" menu (`ATTRIBUTIO_EXPORT.mount`) offers the six engine exports (proofs, Schymanski folder, publication table, quantification, gradient, SIRIUS) on the same files of the campaign.
- **Settings fingerprint** (`flow-digest.js`, `F.settingsDigest`): the "Settings digest" button of the campaign view asks the engine for the `evidence` export, reads `settings_hash` (12-digit sha1 of the thresholds) and `settings` from `evidence_<campaign>.json` and shows them with "Copy"; no new route.
- **Not done in Flow**: Attributio regulatory and hazard views (the hazard registry is not in Rust: the Schymanski folder writes "Not assessable"); campaign report, QC and statistics (the run report is a separate package); with the real engine these are not proven: Bench 2b, the MS2 searches, the exports other than the Schymanski one, and the feature table from `.mzfeat` with the XICs.
- **Campaign MS2** (`flow-campaign.js`): under the table sits the `ATTRIBUTIO_MS2` panel (library search, in silico ranking, hydrogen shifts, RT prediction, co-isolated features) on the same files; it is only evidence for the chemist, it changes no level and writes nothing in the campaign.
- **End of run** (`flow-run-end.js`): `F.afterRun(S)` opens the result by itself when the run finishes (in the app, `flow-desktop.js`): a `.mzfeat` as the "Feature table" view (read with `load()`, the `flow/read` route with `encoding: "base64"` answers `{base64}`; other answers leave the results button), otherwise the first CSV preview. 
- **Roles and result legend**: `F.samplesFor(S, names)` gives `PIPEQC.open` and `PIPET.mount` the roles (`samples/1` kept in `S.samples[input name]`, by file stem); with no `samples` input, no content or missing files the roles are `null` and a row says so. With roles the "Not in blank" chip starts active. `F.legend({states, levels})` is the common legend (levels and "auto" with a dashed outline), `F.current` is the page state.
- **Import data tab** (`flow-import.js`): `F.addFilesBox`: "Add files"/"Add a folder" press `#pick`/`#pickdir`. Metadata: the `F.samplesEditor` grid (`flow-meta-grid.md`) on a `samples` input (or on `S.metaInput`); "Upload table" (CSV/TSV/XLSX; `flow-xlsx.js`: first sheet) goes through `F.metaImport` (op `csv_read`; `F.META_HEADERS` renames the old headers). Tests: `flow_xlsx.js`, `e2e_flow_import`, `e2e_flow_meta_grid`.
- **Sample list in place** (`flow-samples.js`): the `samples` input is edited with the `samples/1` metadata grid (`F.samplesEditor` = `F.metaGrid`, `flow-meta-grid.js`; details in `docs/agenti/flow-meta-grid.md`).
- **Sample list: document and remedy**: the `samples/1` document lives in `S.samples[name]`; `F.samplesSet` computes its canonical SHA-256 (`CDOC.canonical`) and writes it in `input.sha256`; "Download JSON" saves the canonical JSON. The remedy "Add sample list from Data" (`flow-fix.js`) adds and fills in one click; the steps that have `samples` today ask for it as optional.
- **One selection** (`flow-select.js`): `F.select(id, from)` / `F.onSelect(fn)` / `F.selected`; `F.watchRows(host, name)` publishes the click on `tr[data-id]` and marks with a thick outline (`.flx-sel`, `aria-current`) the chosen row in the other views; `openResult` resets it.
  Mounted on Feature table, campaign, network and the Products view (`tptab/1`, `gruppi/1`): `F.drawTable` takes `ids` (row of `tptab/1` = `row` of `gruppi/1` = row of the Feature table; the row becomes focusable and is chosen with Enter or Space) and `members` (the rows of the sets, marked with a dashed outline `.flx-member` when the selection is one of their members); the "Product" menu of the conditions chart follows the selection and publishes it.
  There is no UpSet chart in the page: the sets are a table.
- **Starting templates** (`F.TEMPLATES` in `flow-names.js`, `F.templatePlan` in `flow-fix.js`), each with the "Good for:" line. First row: "Find transformation products", "Feature table" (base only), "Untargeted analysis" (formulas, library, level), "Fragmentation tree of a standard" (field `steps`: own plan without the base, `spectra.msn_graph` → `msn.library_export` and `msn.table_export`; `help` line "Fragmentation rules: CID vs HCD"); under "More templates" (`details`, flag `more`): Targeted check, TP time series, Standards check, Blank-corrected table.
- **"Unit-resolution feature table"** (`lrtable`, first row): base + `features.estimate`, `table.filter` (`blank_ratio` 3, `dup_da` 0.3), `export.table_csv`; preset `lr` on `features.detect` (`presets`, `tail`); no HR steps. Note `F.UNIT_NOTE` in tab and panel. Test: `e2e_flow_lr_template.py`.
- **Feature table open, Quantification**: the feature table step is selected at first draw and after every template. "Quantification" (calibration curves per compound) is missing: there is no step in the registry.
- **Templates: settings and tests**: a template can give initial settings (`params` by step id) and the sample list comes from the connection of the `table.filter` step. Test: `tests/flow_modelli_partenza.js` (every template is a valid plan), `e2e_flow` (`MISURA clic_modello`).
- **Family in the Feature table** (`flow-views-features.js`, hooks `extraCols`/`extraTabs`/`redraw` of `PIPET`, `docs/agenti/mzfeat-table-view.md`): `F.familyLoader(session, redraw)` reads `riga/1.family` once per row, only for the rows that come into view (4 in parallel, delayed redraw); the "Family" column gives the number of ions (empty until read, sortable) and the "Family" tab lists m/z, RT and role of the ions, the reference first.
- **Family: limits**: with the per-ion table (`family` null) the tab says so. The proofs of the edges (`famiglia/1`) are not in the `.mzfeatf` nor in `riga/1.family` (only ions and roles): the "Show proofs" button (`lazy/flow-family-proofs.js`) chooses a file of the table and asks the pool (`ATTRIBUTIO_CORE.pool`, which also has the `feat` `.wasm`) `family(file, recipe)`: op `family` of `feat-worker.js` → `family_record` on the site, route `feat/family` in the app.
- **Show proofs**: shows the edges (ions, Δm/z, ΔRT, type, r, proofs with threshold) of the families of the file that have an ion of the row; `error.badRecipe` and `error.featMemory`/`error.memoryBudget` have clear text; on a phone the tab says it is a feature meant for computers.
- **Issues and estimates** (`flow-issues.js`): the "Issues" box under the canvas (`F.issuesPanel`, hidden when there is nothing to fix) lists every need of the plan with the step, the one-click remedy and "Show".
- **Estimated values and reuse**: an unwritten `x-estimate` parameter shows "estimated" with ⓘ (where from and how) and "Use fixed", which writes the default value. In the app, before Run, the line "N steps reused, M to compute" comes from `flow/reuse` (`probe_plan`, only the cache keys); after the run a step with `cached` says "reused (nothing changed)"; the site has no cache. Test: `e2e_flow`.
- **Report and network** (`flow-report.js`): the "Run report" view (type `report`, JSON `run-report/1`) loads `rapporto-flow.js` on first use and uses `RAPPORTO_FLOW.render`; in the app the "Report" button of the run (`F.lastRunReport`, route `flow/report`) opens the `run-report/1` of the last run, on the web the JSON is chosen from disk. The "Network of the products" view (type `transform`, JSON `rete/1`) mounts `TPRETE_VIEW` (`TPLAZY.load("rete-vista.js")`), publishes `F.select(row)` and follows the single selection. Test: `e2e_flow`.
- **Review view** (`flow-review.js`, "Review" button of the campaign view): queue of the features at 2b, 3a, 3b, one at a time, with proposal and proofs in words (fragments, library, RT, purity) and a fragment table; A accepts, S skips, R rejects the identity, E opens Bench 2b, arrows move. The note is asked only if level or identity change (or for 2b); the decisions replace `feature_decisions.csv` in memory ("Download decisions" downloads it) and the table is redone on exit. Tests: `tests/flow_review.js`.
- **Product views** (`flow-views-tabui.js`, type `tp` and `annot`): a `tptab/1` JSON gives the table of the products (state, kinship, route, areas, t0/blank) and, if it has `gruppi`, presence × condition matrix, bar chart of the area of a product per condition with its table, sets and kinetics of the parent; `gruppi/1`, `interp/1` (row by row, site classes) and `reatt/1` (table of atoms with f(+), f(0), f(−)) are recognized by the `schema`/`format` field (`F.openTabui`). - **Accessibility and motion**: buttons with `aria-label`, keyboard (Enter on the palette, up/down arrows to reorder), colors from the `--t-*` variables (Okabe-Ito) with shape and letter per data family, `prefers-reduced-motion` and `data-a11y-reduce` turn off animation; targets ≥ 24 px (40 on touch). - **Choices for v1** (to confirm, all easy to change): tab in the Tabui machine; canvas with automatic columns (no free dragging nor dragged links: links are born by themselves and changed in the list); no `ui` in the plan; color, shape and letter per data type; visible conversions; fixed goal `annot.level`; `meta.compare` checked in the page (the Rust check is in the CLI, not in the `.wasm`).

## Startup
- **Rule**: nothing heavy before first draw. The Flow tab (`flow/js/flow-tool.js`) is the `early` script of `indice.json`: the loader (`tpmine-loader.js`) runs it right after the index, before the data files and the other Tabui scripts (it uses none of them), so the tab exists while the rest downloads.
- **Order**: (1) click on the tab: static skeleton (`#flx-sk`, `aria-busy`, bar, tabs and canvas of the real shell's size, colors from the page variables, buttons off); (2) `CORE` (registry, check, plan, inputs, UI, palette, form, chain, names, canvas, inspector, `flow-issues`, style, shell) and the four `steps-*.json` lists in parallel, then `FLOW.shell` replaces the skeleton; (3) at idle (`requestIdleCallback`, fallback `setTimeout`) `LATE` arrives (results, review, campaign, views, desktop and web runners), awaited by `FLOW.whenLate`.
- **In the background**: as soon as `flow-tool.js` registers (not at idle) `TPLAZY.loadNow(...CORE)` starts (download all together, execution in order, one tag after the other) and the fetch of the four lists: the first click already finds modules and lists and draws the shell at once. At idle (`requestIdleCallback`) `LATE` downloads at low priority. `TPLAZY.load` and `loadNow` execute one after the other; `loadNow` reserves all the names at once. The loader never uses `async=false`: those tags end up in the page's single ordered queue behind `shell.js` and the `carica.js` modules.
- **Hooks**: the shell calls the late modules only if they exist (`F.resultsCard ?`, `F.samplesEditor ?`) and redraws when `whenLate` resolves; `Run` waits for `whenLate` with `aria-busy` on the button alone. A new module goes in `CORE` only if the first draw calls it without a guard, otherwise in `LATE`; the test `test_flow_is_shipped_with_the_descriptors` wants every file in `flow-tool.js`.
- **Test**: `e2e_flow_avvio` opens with `wait_until="commit"` (`load` does not arrive while they are held) and holds with `route` the modules, the lists, the `.wasm` and `shell.js` and checks the order (skeleton and buttons present, no module executed, `FLOW.resultsCard` absent after the shell, `Run` waiting, then everything works); it counts requests and nodes.
- **Tab and page**: `tpmine-loader.js` (list `L` of `carica.js`) downloads when the page is usable or at the first click on a tab; the tabs (Tabui at once, Flow with its `early` script) appear as soon as ready (`showTabs()`) and the click on Flow opens the view as soon as the `early` script runs (`openLate`). A click that arrived before the loader is held by `first-paint.js` (`MZLAB_LATE_CLICK`) and `turnOn()` repeats it. Before `shell.js`, `openView()` shows the section, emits `tpview` and `syncView()` aligns `S.view` with `setView` as soon as the page is ready.
- **Assistant** (`flow-llm.js`, `flow-llm-tools.js`): "Assistant" button and panel to the right of the canvas, only with the "research" profile, assistant on and consent; every assistant edit is an `S.undo` entry labeled "by assistant"; details in `docs/agenti/llm.md`.
