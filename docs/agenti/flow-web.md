# Flow web runner ("This browser")

- **Where**: `flow/lazy/flow-live.js` (live session: client of the scheduler `api/flow/sched/<op>`, derived events, `F.live = {run, preflight, attach, change, state}`), `flow-live-jobs.js` (runners `F.liveJobs`: `index.mzidx`, `features.detect`, `features.align`, `features.gapfill`), `flow-web-run.js` (pool helpers, `F.runners.web = {name, available, run, preflight, small, highMb, kit}`; `run` calls `F.live.run`), `flow-web-ui.js` (Run panel, `F.webRunUi`), `worker-flow-web.js` (worker that loads the `feat` `.wasm` and answers the estimate).
- **Scope**: Lives in the Tabui package and is not in the desktop app (`window.MZLAB_DESKTOP`: there it is "This computer"). Texts in English like the rest of the Flow (`flow/` is outside `tools/controlla_i18n.py`).
- **Live**: the `flow-live*.js` modules are in `LATE` of `flow-tool.js` (never in the first draw). On every `flow:changed` (300 ms wait) the page sends the plan to `update`, runs the commands (`cancelJob` of the pool for expired jobs), asks `next` with the pool's free slots and starts the jobs: no job choice in JS.
- **Live reuse**: A detection or alignment that the plan already has in OPFS under its `plan_key` is `cached` (reused). Opening Flow with the `.mzidx` in OPFS starts the detections without a click on Run; changing an alignment parameter does not redo the detections, changing a detection one cancels only those in progress, returning to the previous value reuses.
- **Steps**: `features.detect` (one job per `.mzidx` file of `mzlab/idx/`, those of the files open in Data, otherwise all), `features.align` and `features.gapfill`; `index.mzidx` observes the Data index (event `mzlab-index`, never a second index) and is "reused" if it is already there. The `feat-worker.js` pool aligns and fills gaps in a single call: `gapfill` reports the table of `align`. The other steps of the plan are left out (`stato: "skipped"`, `via: "computer"`). Proof steps are not there (they need the Pipeline panel's parent and rules).
- **Recipe and tables**: the pool's `{"fill", "layers"}` text is written by Rust (`job_layers_text`, `flow_job_recipe` of `rotte`; `recipeOf`) with the lineage of `flow run`: only the job's branch, preset and `algorithm` included. Each alignment and fill keeps its own table (`x.tableKey`); an alignment read only by fills makes the first one's (`fill` true), which finds it ready, and the record redoes it with `filled` false.
- **Mixed series**: `features.align` and `features.gapfill` refuse a series with positive and negative files (`err.flow.align.polarity`, params `positive`, `negative`) or with unit and high resolution (`err.flow.align.resolution`, `unit`, `high`): the rule is `mzlab_feat::nature::one_kind_of` on the indexes, called by `align_job` of `flow run` and by `align_series_to` of the `feat` `.wasm`, so key and names match on both sides; the user splits the series or aligns each group in its own branch. Proof: `gap_a_series_of_mixed_*` (`flow_neglr_tests.rs`), `e2e_flow_neg_lr.py mix-pol mix-res`.
- **Events** (`document` `flow:web-step`, and the `onEvent` option of `run(S, opts)`): `{passo, stato, mb, via, parte, di, modo}`; `stato` = `waiting|running|done|reused|skipped|refused|error`; `via` = `browser` (the step runs here) or `computer` (a computer is needed); `parte`/`di` = file k of n; `mb` = memory (Rust `estimate_series` for the alignment, worker peak for detection); `modo` = `memory|slabs|refused` (or `reused`). `F.webStepText(ev)` writes them in words.
- **Estimate**: `estimate.rs` of `mzlab-feat-wasm` (module `hr`): `estimate_series(files, recipe, budget_mb)` gives `{mb, via, files, rows}` of the alignment (`slabs::stima`), `estimate_detect` `{mb, via}` of the detection (`trace_stima`, op `detect` of `worker-flow-web.js`). `preflight()` estimates the alignment before Run with the detections in OPFS.
- **Budget and large permission**: `mem_mb` of `next` is `MZLAB_RUST.budgetMb`. An alignment or detection estimate `refused` but in the high level (`highMb()`): job `blocked` with `by: "permission.memory"`, `window.mzlabAskMore` only at Run, one answer for all; "Use more memory" runs the step at the high level (`setBudget`; detection: third argument of `detectAll`). Above the high level: `refused` with `error.featMemory` `{fase, stima_mb, budget_mb, libero_mb}`.
- **Large memory**: A step > 512 MB takes the Web Lock `mzlab-mem-grande` and closes the worker at the end of the step.
- **Tabui context**: the Flow tab starts from the early scripts, before the loader fills `QTOOLS.ctx.files`; `F.tpCtx(nome)` (`flow-web-run.js`) waits for the file before the pool (`feat-worker.js`) and `tp.generate` (`regole_tp_2.json`), otherwise a Run right after opening gave `error.featFailed`. The `error.feat*` texts are in `F.message` (`flow-ui.js`, English only).
- **Resume**: every output is in OPFS under the `plan_key` of its job (`mzlab/flow/live/<plan_key>.mzfeatf|.mzfeat`, with `.recipe` next to the table; the last table also in `mzlab/flow/series.mzfeat`); a file of a key that no longer exists (OPFS cleared) restarts the scheduler (`restart`) and the job is redone. After a worker dies the pool redoes the job once; a finished detection stays saved. The pool gives an id to every job (`detectAll`, `align`) and `cancelJob(id)` stops only that job's worker; the worker progress is `{job, frac}`.
- **Phone and tablet** (`F.runners.web.small()`: `MZLAB_PHONE`, iOS/Android, iPad): the panel writes "Flow is made for computers…"; Run stays off if the estimate (also from `preflight`) exceeds the high level, with the reason beside it (`#flx-web-why`).
- **Proof**: `tests_e2e/e2e_flow_web.py` (needs `cargo` and `wasm-bindgen`, otherwise SKIP): events of every step, `series.mzfeat` with the same SHA-256 as the native example `native` on the same recipe text (`recipeOf`; the equality of that text with `flow run` is proven by `flow_run_tests::the_recipe_of_the_layers_gives_the_bytes_of_flow_run` and, with two branches and a preset, by `flow_detect_algorithm_tests`), second run that reuses, refusal with budget 0.001 MB, note on phone; `cargo test -p mzlab-feat-wasm --test estimate_series`.
- **Table at end of run** (`flow-run-end.js`, `F.webAfterRun`/`F.webTableItem`; `flow-results.js`): on a successful run with `features.align|gapfill` the table `mzlab/flow/series.mzfeat` read with the pool's OPFS reader (`pool.fs`) enters the step's results as `{label, load}` and `F.afterRun` opens it as a "Feature table" view (focus on the title, `role=status` note); without file or step only the text stays. After a reload the step's "Results" panel offers "Open series.mzfeat" if the file is in OPFS. Proof: `tests_e2e/e2e_flow_web_tabella.py`.
- **Live proof**: `tests_e2e/e2e_flow_live.py`: detections start by themselves, the pool's jobs counted through a gate (no redo after an alignment change, only the detections in progress cancelled after a detection change, no pool call when the value returns), measurement `flow_live_primo_detect` (opening Flow → first detection in progress, 822 ms).
- **MSn steps** (`flow/lazy/flow-web-msn.js`, `F.webMsn = {run, one, infusion, STEPS}`; every plan, even of MSn steps only, runs in the scheduler with the `msn` runner; `run` is the scheduler-free reference of `e2e_flow_msn.py`): the infusion is the plan's file open in Data (`F.runPlanFromData(S).names[0]`); graph, library and tables come from the routes `api/msn_grafo` and `api/msn_grafo/export` (`formato=massbank|msp&libreria=1`, `vista=`) of the `msngrafo` `.wasm`, i.e. the same functions as `mzlab-cli`.
- **TP steps** (`flow/lazy/flow-web-tp.js`, `F.webTp = {STEPS, generate, estimates, indexPaths, linkInputs, digInputs, post}`; runner `tpGenerate` of `flow-live-jobs.js`, result `<id>.ipotesi.json` in OPFS with the plan key): `tp.generate` calls `tp_parent`/`tp_generate` of the `hr` `.wasm` (`mzlab-feat-wasm/src/run_tp.rs`, the same code as `flow_generate.rs`, so byte identical to native) with the rules `regole_tp_2.json`; for a SMILES the groups come from the `grafo` `.wasm`.
- **Nature of the series in the browser**: what the plan leaves unwritten, the browser runner takes from the OPFS indexes of the series (`F.webTp.indexPaths`) with the Rust rule of `flow run` (`mzlab_feat::nature`): tp.generate asks the pool for `series_estimates` of the proofs `.wasm` (`polarity`, `nominal`; also when tp.link and tp.filter make the hypotheses again; kept as `estimates` on the job's file), tp.link (`link_evidence`) and tp.dig_lr (`dig_polarity`) decide the polarity inside the `.wasm`. What the plan writes wins.
- **Facets of the files in the check**: `F.learnFacets` (`flow-page.js`) asks the proofs `.wasm` for the facets of the OPFS indexes (op `series_facets` of feat-worker.js, `mzlab_feat::nature::facets`, the rule `flow run` applies in `fill_inputs`) into `F.fileFacets`; `F.validate` puts them on each scan input that writes none (what the plan writes wins), so formula.ms1 on LR files or tp.dig_lr on HR files is refused before running. `F.message` names the step, the input, what it needs and what the files are.
- **Facets in the record**: `flow-web-prov.js` asks `series_facets` once per input file and writes them into the plan it hashes (`plan_sha256`) where the plan writes none, as `fill_inputs` does for `plan.json`.
- **Proof of the nature of the series**: `tests_e2e/e2e_flow_neg_lr.py` (plan without polarity and unit mass by default, `NEG_LR_WRITTEN=1` with them), browser = `flow run` in HR+, HR-, LR+, LR-, and the page check refuses the same steps as `flow run --dry-run`.
- **tp.link@2 in the browser** (`F.webTp.linkInputs`, runner `tpLink` of `flow-live-jobs.js`; `.mzfeat` in OPFS as `<plan_key>.tp.mzfeat`): the hypotheses are redone by the `tp.generate` step they come from (a hypotheses file stays on the computer); `linkEvidence` of the pool (op `tp_link_evidence` of the `hr` `.wasm`: `run_tp.rs`, the same `link_evidence` as `flow_link.rs`) looks for the hypotheses and builds `tp/1` on the alignment table, `linkInterp` (op `tp_link_interp` of the `interp` `.wasm`) writes `interp/1`.
- **Proof of tp.link@2 in the browser**: `tests_e2e/e2e_flow_tp_link.py` (synthetic identity series, `.mzfeat` with the same sections as that of `flow run` (only the source names in the header change), second round from OPFS). The warning `warn.flow.link.noT0` is not yet reported by the browser.
- **tp.filter@2, tp.position, tp.network in the browser** (`F.webTp.post`, runner `tpPost` of `flow-live-jobs.js`): they read the `<plan_key>.tp.mzfeat` of the `tp.link` they come from (the `table` port of `tp.network` accepts the same `tp.link`; a `tp/1` given as a file stays on the computer) and ask the pool for the op `tp_post` (`interp` `.wasm`, `table` for the network). The code: `tp_refilter` and `tp_position` of `interp.rs`, the same functions as `flow_refilter.rs` and `flow_position.rs`; the network is `rete_build` of the `table` `.wasm`, like `flow_network.rs`.
- **tp.dig_lr in the browser** (`F.webTp.digInputs`, runner `tpDig` of `flow-live-jobs.js`, result `<id>.dig.json` in OPFS): the pool calls the op `dig_lr` (`feat-worker.js`): `tp_dig_inputs` (`hr` `.wasm`, `run_tp::dig::dig_inputs`, the same code as `flow_digl.rs`) looks for the hypotheses in the saved peaks, then `finder_lr_dig` (`finder-lr` `.wasm`) and `summary`.
- **export.table_csv and export.mztab in the browser** (runner `tableExport` of `flow-live-jobs.js`, pool `tableFile`, `export_table_auto` of the `table` `.wasm`): the alignment table with the roles of `samples`; polarity and `campioni/1` are decided by `pol::of_table` and `pol::samples_v1`, the same functions as `flow run`. Text in OPFS, byte for byte equal. The browser's detections carry the plan input's name (`.mzML`) as in the CLI, so the mzTab-M ID (table hash) coincides. Proof: `e2e_flow_web_export.py`.
- **table.filter in the browser** (runner `tableFilter` of `flow-live-jobs.js`, pool `tableView`, `table_view_auto` of the `table` `.wasm`): the view of the alignment table with the parameter rules (`filterspec::spec_from_json`, the same function as `flow run`), kept in OPFS as `<id>.json`; equal bytes. A table that is not the plan's alignment stays on the computer. `features.table` (whole chain in one step) has no web runner of its own: the same CSV is given by the base chain and `export.table_csv`. Proof: `e2e_flow_web_export.py`.
- **spectra.ms2 in the browser** (`F.webIdent.ms2`, pool `ident`, `flow_ms2` of the `hr` `.wasm`: `ms2_text` of `mzlab-feat/src/flow_ms2.rs`, the `flow run` function): the mzML that the engine has in memory (`MZLAB_RUST.blobOf`, ≤256 MB; read estimate: `memory.md`), one file per call, joined texts; the `features` table is the plan's `export.table_csv` CSV. MGF in OPFS as `<id>.mgf`. An mzML not open, too large or `features` from a file stay on the computer. Proof: `e2e_flow_web_ident.py`.
- **qc.mass_accuracy in the browser** (`flow/lazy/flow-web-qc.js`, `F.webQc`, `mass_accuracy` of the `hr` `.wasm`: the same `massacc::check` as `flow run`): `raw` from `index.mzidx`, `table` from `features.align`/`gapfill` (OPFS), `samples` and `references` plan files; `massacc/1` report and corrected table (`massacc-<sha>.mzfeat`) identical to the native ones. Details: `docs/agenti/qc-mass.md`. Proof: `e2e_flow_qc_mass.py`.
- **spectra.match (not `tree`) and spectra.lookup in the browser** (`F.webIdent.match` and `.lookup`, `flow_match` and `flow_lookup` of the `lib` `.wasm`: `flowmatch::match_json` and `lookup_json`, like the CLI): the query is the MGF of a plan `spectra.ms2` or a plan file, the library is the text given to the plan (`S.samplesJson[nome]`, "Library file…" in the results; a `.mzlib` stays on the computer for the lookup); the key includes the library hash. `tree` goes to `msn`. Proof: `e2e_flow_web_ident.py`, `e2e_flow_web_lookup.py`.
- **table.match in the browser** (`F.webIdent.tableMatch`): two calls like `tp.link`: the pool (`ident`, `table_match_rows` of the `table` `.wasm`, like `flow run`) makes the MGF of the alignment rows from the `.mzidx` in OPFS, then `flow_match` of the `lib` `.wasm` searches the plan's library. A table that is not the plan's alignment, without `samples`, `index` or library stays on the computer. The run record (`prov/1`, `corsa/1`) stays with the base chain: these steps do not enter it. Proof: `e2e_flow_web_ident.py`.
- **formula.ms1 in the browser** (`F.webIdent.ms1Formula`, `formula` `.wasm`: `flow_ms1_rows` one mzML at a time from the files open in Data and `flow_ms1_join` in table order, `mzlab-feat::flow_formula_ms1` like `flow run`): inputs `features` (the plan's `export.table_csv` CSV or a plan file) and `index` (mzML open in Data); the module loads only here; without inputs or above 256 MiB of mzML the step stays on the computer. Key: `spec.key` + CSV hash. Proof: `e2e_flow_web_ident2.py`.
- **formula.ms1, ion**: an `ion` not written in the plan does not reach the `.wasm`, so each file gives its own (`[M-H]-` on negative files), as in `flow run`. Proof: the negative case of `e2e_flow_web_ident2.py`.
- **formula.ms2 and annot.level in the browser** (`F.webIdent.ms2Formula` and `level`, `attributio-all` `.wasm`: `flow_formula_ms2` and `flow_level`; texts of `mzlab-feat::flow_formula_ms2` and `flow_level`): `formula.ms2` takes the MGF of `spectra.ms2` and a plan `formulas/1` file (that of `formula.ms1`), `annot.level` the `candidates/1` of `spectra.match` and the same `formulas/1` file (rules of `livelli-1.json`, profile `mzlab`; level 2b is never given); the key includes the hash of the inputs. Proof: `e2e_flow_web_ident2.py`.
- **table.drift, table.plausible and features.group in the browser** (`flow-web-drift.js`, `flow-web-plausible.js`, `flow-web-group.js`; `flowtab` `.wasm`: `flow_drift`, `flow_plausible`, `flow_group` like `flow run`): `table` = alignment (or gapfill) in OPFS or its `table.filter` view (`F.liveJobs.tableOf`, `flow_table_of_view`); `table.drift` needs `samples` and `design`; otherwise `blocked` (`platform.computer`). Module only if it runs; proofs `e2e_flow_web_{drift,plausible,group}.py`.
- **spectra.insilico in the browser** (`F.webInsilico.run`, `flow-web-insilico.js`; `attributio-all` `.wasm`, `flow_insilico_pieces` and `flow_insilico`: `mzlab-feat::flow_insilico`, the `flow run` function): `suspects` is a CSV list, a `screen/1` or the package catalog downloaded with one click; with neither the step is `blocked` with `input.insilico`. - **screen.suspects in the browser** (`F.webSuspects.run`, `flow-web-suspects.js`; `table` `.wasm`, `flow_screen_suspects`: `mzlab-feat::flow_screen_suspects::screen_text`, the `flow run` function): the alignment read from OPFS, the plan's suspect lists (a `.mzsus`, kept in `S.samplesJson` as `b64:`+base64, or a CSV; "Suspect list…" in the results; never included nor downloaded), the MGF of `spectra.ms2` and a plan `formulas/1`; the key includes the hash of each list. Missing input or table not in OPFS: `block` `platform.computer`. Proof: `e2e_flow_suspects.py`.
- **"Bentazone" and "TP series" templates from the site**: the plan that `F.templatePlan` builds runs entirely in "This browser" (centroid, index, detection, alignment, gapfill, TP and `table.filter` of the series) with texts byte for byte equal to `flow run`; in "TP series" the row filter reads the alignment table (`gapfill.table`), not the `filtri/1` record of `tp.filter`. Proof: `e2e_flow_web_modelli.py`.
- **File order**: `build` (`flow-live.js`) orders the files like the plan's `raw`/`mzml` inputs (name or stem), the others follow by name: like `flow run`. Proof: `e2e_flow_lr_template.py`, `e2e_flow_dig_lr.py`.
- **Results of the three steps**: the text (`filtri/1`, `sites/1`, `rete/1`) is in OPFS like the MSn results. `tp.filter` redoes the hypotheses from the originating `tp.generate`.
- **Proof of the three steps in the browser**: `tests_e2e/e2e_flow_tp_post.py` (same synthetic series; texts byte for byte equal to those of `flow run`, second round from OPFS). The MSn tree votes stay out of `tp.position` (they are not in the file).
- **tp.review in the browser** (`F.webTp.post`, `kind: "review"`, op `tp_post` → `tp_review` of the `interp` `.wasm`; `interp/review.rs`, same code as `flow_review.rs`): the chemist's decisions (`tpdec/1`: row key `m/z@RT` to 4 decimals and 0.05 min → level and note ≤200) are a `transform` input written in place (`flow/lazy/flow-decisions.js`: `F.decisionsSet`, `F.decisionsEditor`, added from the "+ input file…" menu), with SHA-256 like the parent.
- **review/1**: the `tp.review` step writes, for each decision, the proposed level (`proposal.sublevel` of `interp/1`), outcome of the `LIVELLI.decide` rules (2b only on 2a/3a/3b/4, 1 only with a marked standard) and counts; a refused decision is listed and not counted. `review` view (`F.readReview`). Proof: `tests_e2e/e2e_flow_tp_review.py`.
- **Parent** (`flow/lazy/flow-parent.js`: `F.parentSet`, `F.parentEditor`; never a file): the field is the molecule search box (`molecole-campo.js`, route `cerca` with `ampia`: name, synonym, formula, InChIKey or m/z, ranking, a one-letter error forgiven only if there is nothing else).
  A formula or an m/z asks what it is: neutral molecule M (default) or an ion of the engine's adduct table (route `addotti`, conversion `ione`). The plan keeps the NEUTRAL molecule: the `structure` input is the JSON `{name, formula, smiles, inchikey, mass, typed:{text, adduct}}` (an m/z has no `formula`: `tp.generate` asks for one), or text (SMILES, formula, hand-written JSON). It is read by `read_parent` (same code for CLI and browser; extra keys are ignored). Proof: `tests_e2e/e2e_flow_parent.py`, `e2e_flow_tp_web.py`.
- **MSn steps, parameters and events**: the parameters become the route keys (`pick` → JSON `scelte`…, `flow-web-msn.js`); an imported old plan goes through `api/flow/line`. The events are those of the other steps (`via: browser`); the texts are in OPFS (`mzlab/flow/<id>.json|msp|txt|csv`) and the panel offers them as links.

- **MSn steps, errors**: `err.flow.msn.open` (infusion not open in Data), `err.flow.msn.desktop` (engine memory refusal: use the desktop app or the CLI), `err.flow.msn.molecule` (name without ion: the molecule list is not read in the browser). `err.flow.msn.library` (no entry in the OPFS `msnlib.json` library).
